# 읽고, 찾아보고, 계산해서 검증하는 Agent

NLP 5조 · 3인 팀 연구 안내 · 2026-10-29

## 01. 우리가 함께 만들 것은 무엇인가? {#start}

**관심 분야의 소식을 모으고, 원출처로 사실과 왜곡을 조사한 뒤, 유용한 후속 업무와 추적까지 연결하는 Agent를 구상한다.** 첫 연구 단위는 한국어 주장과 근거를 대조해 판정·오류 위치를 설명하는 과정이다. 여기서 어느 행동 선택이 정확도와 비용을 바꾸는지 비교한다.

이 문서의 독자는 프로젝트를 오늘 처음 접하는 팀원이다. 먼저 전체 구상과 한 가지 사례를 따라가고, 여섯 태스크 중 탐구하고 싶은 질문을 고른 뒤, 그 질문에 답해 줄 논문을 읽자.

Mission에는 **Opportunity Execution**(기회 활용 준비), **News-to-Artifact**(검증한 정보로 자료 제작), **Event & Change Manager**(일정·변경 관리), **App Trust & Safe Trial**(앱 조사·격리 체험)이 있다. 논문의 실험 수치가 뉴스에서 과장되었다면 왜곡 문장을 짚고, 실제로 쓸 만한 데이터가 공개되었다면 비교표나 분석 파일을 만드는 식이다.

이 큰 구상에서 **50개 사례로 검증할 중심 기능을 선택하고**, 같은 사례에 고정 절차와 적응형 Agent를 적용하자. 헌수님의 Phase 1–7 중 팩트체크·왜곡 조사와 Mission 생성 판단을 정량 평가에 연결하고, 선택한 Mission 하나를 작은 시연으로 이어갈 수 있다.

### 한 문장으로 보는 fact-checking

팩트체크는 **확인 가능한 근거를 조사해 주장의 사실 여부를 검증하는 일**이다. 자료의 출처·내용·시점도 함께 확인한다. “이 정책은 훌륭하다” 같은 평가보다 “이 정책은 7월부터 시행됐다”처럼 근거로 확인할 수 있는 내용을 대상으로 삼는다. 모델의 최종 출력에는 지지·반박·근거 부족 판정, 그 판단을 뒷받침하는 출처, 짧은 설명이 함께 들어간다.

**설명용 사례** — 입력: “A시의 2025년 도서관 대출량은 2024년보다 20% 늘었다.”

| 단계 | Agent가 관측하거나 수행하는 일 | 남기는 결과 |
|---|---|---|
| 주장 이해 | 지역=A시, 지표=대출량, 비교 기간=2024→2025, 변화율=20% 추출 | 확인할 조건 |
| 자료 검색 | 공식 표에서 2024년 100만 건, 2025년 110만 건 확인 | 표의 행·열·출처 |
| 비교 가능성 확인 | 두 값의 지역·집계 범위·단위가 같은지 점검 | 비교에 쓰는 값 |
| 계산 | (110−100)÷100×100 | 10% |
| 판정·설명 | “20% 증가”와 계산 결과 대조 | **반박 — 증가율은 10%**, 두 값과 계산식 인용 |

핵심 연구 질문은 다음 선택에서 생긴다. **표 하나로 충분한가? 주석을 더 읽어야 하는가? 추가 검색을 해야 하는가? 계산은 어느 값으로 해야 하는가?** Agent는 도구의 결과를 보고 이 중 다음 행동을 선택한다.

### 지금까지의 대화가 이 주제로 모인 이유

우리는 Kiwi·BM25·임베딩 검색의 차이, ReAct의 도구 선택, 근거를 읽고 설명을 만드는 과정을 함께 다룰 태스크를 찾았다. 팩트체크는 이 관심을 **하나의 입력과 채점 가능한 출력**으로 연결한다. RSS는 검증할 주장을 모으는 입구, 공식 문서·API는 근거, 검색기·계산기는 도구가 된다.

세 사람이 같은 질문을 공유하자. **“Agent가 상황에 맞춰 행동을 바꾸면, 정해진 순서의 파이프라인보다 어디에서 더 정확하거나 효율적인가?”** 아래 여섯 후보는 이 질문을 서로 다른 데이터와 행동으로 실험하는 방법이다.

| 수업·실습에서 익힌 것 | 프로젝트에서 맡는 일 | 직접 관찰할 수 있는 변화 |
|---|---|---|
| 토큰화·Kiwi·BM25 | 한국어 주장과 근거 문서를 어휘로 검색 | 조사 제거 전후의 근거 회수율 |
| 임베딩·dense retrieval | 표현이 다른 문서에서 의미상 관련 근거 탐색 | BM25와 dense·hybrid의 Recall@k |
| RAG | 검색한 근거를 모델 입력에 넣어 설명과 판정 생성 | 근거 교체에 따른 판정·인용 변화 |

### 학부 프로젝트 크기로 만드는 방법

출발점은 **한 도메인, 검증할 주장 50개, 도구 3–4개, 비교 시스템 2–3개**다. 이미 공개된 모델과 검색기를 조합하고, 우리가 직접 만드는 부분은 태스크 정의·평가 데이터·행동 정책·오류 분석이다. Colab GPU는 임베딩 색인과 reranker 추론에 활용할 수 있다.

이렇게 하면 세 사람이 데이터·검색·Agent를 나누어 구현하면서도 같은 50개 사례로 결과를 설명할 수 있다. 가장 작은 파일럿은 **주장 5개를 읽고, 근거를 표시하고, 한 번의 검색→도구→판정을 끝까지 연결하는 것**이다.

### 과제 점수와 우리 결과물을 연결하기

| 과제 요소 | 강의안의 요구 | 우리 팀이 만드는 것 |
|---|---|---|
| 중간 주제·데이터 | AI Agents로 풀 수 있는 태스크, 평가데이터 50개 | 선택한 T1–T6의 입출력·성공 조건, 직접 작성한 사례 |
| 중간 발표 | 태스크 설명 1장 + 관련 논문 15장 | 문제 사례 → 선행연구 지도 → 비교할 정책 → 평가 설계 |
| 중간 평가 | 논문발표 4 / 태스크 3 / 평가척도 3 | 왜 이 태스크인지, 어떤 논문에서 무엇을 가져왔는지 |
| 기말 제출 | 공개 GitHub, 슬라이드 10장 | 실행 코드·데이터·설정·결과·재현 안내 |
| 기말 평가 | 데이터 50개 직접 작성 5 / 분석 2 / 개선 실행 3 | 첫 결과 → 오류 유형 → 수정 → 재실행의 비교 |

문헌 발표의 중심은 **논문끼리 어떤 질문이 달라지고, 그 차이에서 우리의 실험이 어떻게 나오는가**다. 예를 들어 Fathom으로 고정 RAG를 설명하고, FIRE로 반복 검색을 설명한 뒤, 같은 한국어 50개에서 어떤 행동 정책을 비교할지 제시할 수 있다.

## 03. 선택할 수 있는 명확한 Task 여섯 가지 {#tasks}

각 후보에서 입력·출력·도구·50개 구성·채점 대상을 함께 고른다. 화면의 비교표에서 우선 관심 있는 두 후보를 나란히 살펴보자.

### T1 · 공식 수치 주장을 계산으로 검증하기 {#task-T1}

**Task 정의:** 한국어 수치 주장과 기준 기간을 입력받아, 공식 표·통계 자료에서 비교할 값을 찾아 계산하고, 주장과의 일치 여부 및 근거를 출력한다.

- **입력:** “A시의 2025년 대출량은 전년 대비 20% 증가했다.” + 지역·기준일.
- **출력:** 지지/반박/근거 부족, 지표·기간·단위, 사용한 값, 계산식, 근거 ID.
- **Agent의 선택:** 지표를 선택한다 → 부족한 연도나 주석을 더 찾는다 → 계산 함수를 고른다 → 결과를 비교하고 종료한다.
- **도구:** 문서 검색, 공식 표/시계열 조회, 단위·증감률 계산, 원문 구간 열기.
- **50개 구성:** 단일 수치 확인 10 / 증감률 15 / 비율·분모 10 / 기간·단위·집계 범위 10 / 범위 안에서 근거 부족 5.
- **비교군:** 고정 검색→LLM 판정 / 고정 검색→계산 도구→판정 / 관측에 따라 추가 조회하는 Agent. 마지막 두 조건의 차이로 행동 선택 효과를 본다.
- **주 지표:** 판정 Macro-F1, 계산에 쓸 지표·기간·단위의 정확 일치율, 계산 정확도, 사례당 도구 수.
- **채점 예:** 100→110이면 “10%, 반박”이 정답이다. 수치만 맞고 다른 지역의 표를 인용했다면 판정 점수와 근거 선택 점수를 따로 기록한다.
- **핵심 논문:** QuanTemp FC23, TSVer FC26, TAT-QA E30, ProgramFC FC11.
- **구현 규모:** 중간. 공식 자료 공급원을 하나 정하고 표 형식을 고정하면 작은 계산 함수로 시작할 수 있다. GPU는 선택한 검색 모델에 따라 사용한다.
- **배울 것:** 숫자 연산보다 어려운 ‘무엇을 계산할 것인가’를 언어 이해·retrieval·tool use로 연결하기.

### T2 · 여러 조건이 붙은 주장을 나누고 다시 합치기 {#task-T2}

**Task 정의:** 두 개 이상의 사실 조건이 포함된 한국어 주장을 입력받아, 검증할 하위 주장을 만들고 각각의 근거를 수집한 뒤 원래 문장의 논리 관계에 맞춰 종합 판정한다.

- **입력:** “A시설과 B시설은 모두 2024년에 개관했고 주말에도 운영한다.”
- **출력:** 하위 주장 목록, 각 판정·근거, AND/OR 등 종합 관계, 전체 판정.
- **Agent의 선택:** 직접 판정할지 분해할지, 어느 조건을 먼저 확인할지, 누락된 조건을 다시 검사할지 선택한다.
- **도구:** 근거 검색, 문서 구간 읽기, 하위 주장 상태표, 종합 규칙 실행.
- **50개 구성:** 단일 주장 10 / 두 조건 AND 15 / 세 조건 이상 10 / 부정·예외 10 / 일부 조건의 근거 부족 5.
- **비교군:** 직접 판정 / 항상 분해 / 선택적 분해와 종합 점검 Agent. 같은 근거 검색기와 모델을 사용한다.
- **주 지표:** 전체 판정 Macro-F1, 필수 조건 보존율, 하위 주장 판정 정확도, 종합 오류율, LLM 호출 수.
- **채점 예:** A는 2024년, B는 2023년에 개관했다면 AND 주장은 반박이다. A만 조사해 전체를 지지하면 ‘검증 범위 누락’으로 분류한다.
- **핵심 논문:** LoCal FC17, ProgramFC FC11, Claimify E01, Decomposition Dilemmas E05, VitaminC P02.
- **구현 규모:** 중간. 프롬프트·상태표로 구현할 수 있고, 조건 누락·논리 관계의 사람 검수가 주요 작업이다.
- **배울 것:** divide and conquer가 도움이 되는 조건과, 나누는 과정에서 의미가 달라지는 조건을 실험하기.

### T3 · 특정 시점에 참인 주장을 검증하기 {#task-T3}

**Task 정의:** 주장과 `as_of` 날짜를 입력받아, 문서의 발표일·효력일·변경 이력을 대조하고 그 날짜에 맞는 사실 여부와 시간 근거를 출력한다.

- **입력:** “A시설은 6월 20일 현재 무료로 이용할 수 있다.”
- **자료 예:** 6월 1일 공지에 “7월 1일부터 무료 전환”, 이전 요금표에는 유료라고 적혀 있다.
- **출력:** 반박, 기준일 6월 20일, 무료 전환 효력일 7월 1일, 공지·이전 요금표 인용.
- **Agent의 선택:** 최신 공지를 볼지 과거 버전을 볼지, 날짜가 충돌하면 원문이나 변경 이력을 더 읽을지 선택한다.
- **도구:** 날짜 필터 검색, 문서 버전 조회, 날짜·기간 비교, 시간선 구성.
- **50개 구성:** 특정 시점의 상태 15 / 발표일과 시행일 15 / 변경 전후 10 / 기간 중첩·반복 5 / 시간 근거 부족 5.
- **비교군:** 날짜 없는 의미 검색+판정 / 고정 날짜 필터+판정 / 시점·효력일을 확인하는 Agent.
- **주 지표:** 판정 Macro-F1, 유효 시점 근거 선택률, 시간 조건 정확도, 미래 근거 사용률, 호출 수.
- **채점 예:** 최신 문서에 ‘무료’가 있어도 적용일이 7월 1일이면 6월 20일 주장은 반박이다. 이 사례는 검색 성공과 시간 해석 성공을 분리해서 채점한다.
- **핵심 논문:** Time Matters FC24, ChronoFact FC25, TSVer FC26, AVeriTeC FC03.
- **구현 규모:** 중간~높음. 버전과 날짜가 명확한 공지·정책 자료를 모으는 작업 비중이 크다.
- **배울 것:** 시의성 있는 검색, temporal reasoning, ‘지금 아는 정보’와 ‘당시 이용 가능한 정보’의 평가 설계.

### T4 · 한국어 주장에 결정적인 근거를 찾아 검증하기 {#task-T4}

**Task 정의:** 한국어 주장과 고정된 문서 모음에 대해, 근거를 검색하고 필요하면 질문을 바꿔 재검색하여 판정과 근거 묶음을 반환한다.

- **입력:** “A시설은 주말에도 이용할 수 있다.”
- **자료 예:** 검색 상위에는 시설 소개가, 다른 문서에는 ‘토요일 운영·일요일 휴관’ 시간표가 있다.
- **출력:** 문맥에 맞춰 명확히 한 주장 조건, 지지/반박/근거 부족, 시간표의 근거 구간, 사용한 검색 질의.
- **Agent의 선택:** 현재 문서가 질문에 답하는지 검사하고, ‘이용 안내→운영시간→휴관일’로 질의를 구체화하거나 종료한다.
- **도구:** Kiwi+BM25 검색, dense/hybrid 검색, 문서 구간 읽기, 근거 충분성 상태표.
- **50개 구성:** 직접 어휘 일치 15 / 표현 차이 15 / 두 문서 결합 10 / 유사하지만 틀린 문서 5 / 문서 모음에 답이 없음 5.
- **비교군:** 1차 실험은 같은 고정 판정기에 BM25·dense·hybrid를 연결한다. 2차 실험은 한 검색기를 고정하고 한 번 검색 vs Agent 재검색을 비교한다.
- **주 지표:** 근거 Recall@k, 최소 근거집합 완성률, 판정 Macro-F1, 추가 검색 1회당 회복한 사례 수, 지연·색인 용량.
- **채점 예:** 운영시간 문서를 찾았는지, 정확한 요일 구간을 인용했는지, ‘주말’의 범위를 판정에 반영했는지를 나눠 기록한다.
- **핵심 논문:** CFR E19, Dense X Retrieval P17, 한국어 대조학습 FC31, Fathom FC21, FIRE FC15, Sufficient Context E22.
- **구현 규모:** 중간. 기존 Kiwi 실습을 직접 확장하기 좋다. Colab은 embedding·reranker에 활용한다.
- **배울 것:** 검색 점수가 좋은 문서와 판정에 결정적인 근거의 차이, 검색 최적화가 최종 답에 주는 효과.

### T5 · 기사·게시물의 왜곡 위치를 원문과 짝지어 찾기 {#task-T5}

**Task 정의:** 기사 또는 게시물의 주장과 연결된 원자료를 입력받아, 원자료에 비해 바뀐 수치·조건·범위·인용 부분을 찾아 문구 쌍과 오류 유형으로 출력한다. 추가 원자료가 필요한 경우 Agent가 찾아 대조한다.

- **입력:** 원논문은 “실험 A에서 처리량 40% 증가”, 게시물은 “모든 작업의 성능이 40% 향상됐다”.
- **출력:** 게시물의 ‘모든 작업의 성능’ ↔ 원문 ‘실험 A의 처리량’, 유형=범위 확대·지표 일반화, 판정과 설명, 출처.
- **Agent의 선택:** 숫자·표를 다시 확인할지, 조건·예외 구간을 더 읽을지, 인용 관계를 찾아볼지 선택한다.
- **도구:** 문구 검색, 원문·표 읽기, 조건/지표 대조, 수치 계산.
- **50개 구성:** 정확한 전달 10 / 수치·단위 변경 10 / 조건 누락 10 / 범위 확대 10 / 인용·시간 맥락 변경 10.
- **비교군:** 한 번에 원문 대조 / 고정 분해·대조 / 오류 유형에 맞춰 추가 조사하는 Agent.
- **주 지표:** 오류 유형 Macro-F1, 왜곡 span token-F1, 원문↔게시물 대응 쌍 정확도, 근거 있는 설명 비율, 조사 비용.
- **채점 예:** 단순히 ‘과장’이라고 쓰는 것과, 바뀐 문구·원문 조건을 정확히 짝지어 제시하는 것을 따로 채점한다.
- **핵심 논문:** FactLens P15, TRACER P16, Claimify E01, LoCal FC17, Evidence Attribution E37.
- **구현 규모:** 중간~높음. span과 생략 조건의 사람 annotation이 핵심이다. 원자료와 기사/게시물의 쌍을 먼저 확보하면 실험 단위를 작게 고정할 수 있다.
- **배울 것:** 참거짓 분류를 넘어 ‘어디가 어떻게 달라졌는가’를 설명하는 검증, 오류 유형별 적응적 조사.

### T6 · 검증된 소식에서 후속 업무를 선택하고 상태를 갱신하기 {#task-T6}

**Task 정의:** 검증 결과·사용자 관심·위임된 업무 범위를 입력받아, 후속 Mission의 생성 여부와 유형을 선택하고 작은 실행 환경에서 결과와 변경 상태를 확인한다.

- **입력:** ‘행사 일정이 11월 10일에서 12일로 변경됨’이라는 검증 결과 + 해당 행사 추적 상태 + 일정 관리 권한.
- **출력:** Mission=일정 갱신, 기존 항목 ID, 변경 필드, 실행 후 확인 상태, 브리핑 항목.
- **Agent의 선택:** 새 업무/기존 업무 수정/추가 조사/추적 등록/행동 없음 중 선택한다.
- **도구:** 추적 상태 읽기, 공식 공지 검색, 테스트 일정·파일 생성/수정, 실행 결과 재조회.
- **50개 구성:** 행사·일정 10 / 활용 기회 10 / 자료 제작 10 / 변경·취소 10 / 정보 부족·중복·행동 없음 10.
- **비교군:** 키워드 규칙 / 단발 LLM 분류 / 검증·상태 조회를 결합한 Agent. 실행형 표본은 로컬 테스트 일정과 파일로 채점한다.
- **주 지표:** Mission 유형 Macro-F1, 실행 성공률, 중복 작업률, 상태 갱신 정확도, 범위 밖 행동률.
- **채점 예:** 이미 등록된 행사를 새로 추가하면 중복 오류다. 날짜를 바꾸고 다시 조회해 새 값이 확인되면 실행 성공이다.
- **핵심 연결:** 헌수님의 STEP 3–4·Tracking, ReAct FC10, Time Matters FC24. 연구의 중심을 후속 업무 선택에 둘 때 직접적인 Mission benchmark도 추가로 읽는다.
- **구현 규모:** 높음. 실행형 기능은 일정 관리 한 종류로 시작하면 상태 전후를 자동 채점하기 좋다.
- **배울 것:** 검증 결과를 실제 행동으로 연결하기, 정보의 참거짓과 업무의 완료 여부를 각각 평가하기.

## 04. 선행연구는 어떤 문제를 각각 풀었나? {#map}

논문을 ‘좋은 모델 순위’로 읽기보다, **팩트체크의 어느 고장을 고치는 연구인가**로 읽으면 우리 설계와 연결하기 쉽다.

| 고장 또는 질문 | 대표 연구의 접근 | 우리 후보와 연결 |
|---|---|---|
| 실제 주장·근거·정답을 어떻게 묶는가? | AVeriTeC: 주장에 검증 질문·답·웹 근거·판정 결합 | 모든 후보의 데이터 schema |
| 일단 작동하는 검증기를 어떻게 만드는가? | Fathom: 질문 확장→BM25·semantic retrieval→판정 | 공통 고정 baseline |
| 자료를 더 찾을지 언제 멈출지? | ReAct·QACheck·FIRE: 관측에 따른 다음 행동 | T4, 그리고 T1–T3의 제어 정책 |
| 분해한 답이 원래 주장과 맞는가? | ProgramFC·LoCal: 하위 작업과 논리적 종합 | T2 |
| 의미가 비슷한 문서가 진짜 근거인가? | CFR·한국어 대조학습·Dense X: 근거 선택·단위 개선 | T4 |
| 숫자·날짜를 읽었다고 검증이 끝나는가? | QuanTemp·TSVer·Time Matters·ChronoFact | T1·T3 |
| 맞는 판정에 좋은 설명이 따라오는가? | ALCE·Evidence Attribution: 인용을 별도 평가 | 모든 후보의 설명 평가 |
| 문장 일부는 맞는데 무엇을 숨겼는가? | FactLens·TRACER: 세부 사실·누락 맥락 분석 | T5 |
| 조작된 근거가 주어지면 어떻게 되는가? | VitaminC·CrossAug·Fact2Fiction: 대조 자료·근거 오염 | 아래 2×2 공통 실험 |

### 관심 태스크에서 고르는 논문

#### FC03 · AVeriTeC — 실제 뉴스 주장을 채점하려면 정답 말고 무엇을 적어야 할까?

**AVeriTeC: A Dataset for Real-world Claim Verification with Evidence from the Web** · 평가 데이터 · T1, T2, T3, T4, T5

- **논의:** 실세계 주장에는 검증에 쓴 질문·답·근거와 시점이 함께 필요하다.
- **구조:** 실제 주장 → 검증 질문 → 웹 근거가 붙은 답 → 종합 판정·설명
- **논문 결과:** 50개 팩트체크 기관에서 모은 실제 주장 4,568개를 구성하고, 질문–답·웹 근거·설명과 판정 평가 체계를 제시했다.
- **우리 적용:** 우리 50개 사례의 schema를 만들 때 가장 직접적인 참고다. 주장마다 ‘무엇을 알아야 판정할 수 있는가’를 먼저 적게 해 준다.
- **읽을 곳:** Abstract → 데이터 수집·annotation → 라벨·평가식 → 실제 QA 사례
- **읽고 남길 것:** 팀 공용 사례 양식 1개와 사람 검수 기준 5줄.

[공식 서지·원문](https://proceedings.neurips.cc/paper_files/paper/2023/hash/cd86a30526cd1aff61d6f89f107634e4-Abstract-Datasets_and_Benchmarks.html) · [PDF](https://proceedings.neurips.cc/paper_files/paper/2023/file/cd86a30526cd1aff61d6f89f107634e4-Paper-Datasets_and_Benchmarks.pdf)

#### FC10 · ReAct — 검색 결과를 본 뒤 다음 행동을 바꾸는 것이 어떻게 가능한가?

**ReAct: Synergizing Reasoning and Acting in Language Models** · Agent 실행 방식 · T1, T2, T3, T4, T6

- **논의:** 추론과 외부 행동을 번갈아 수행하면 새로운 정보를 반영해 계획을 갱신할 수 있다.
- **구조:** 현재 관측 해석 → 도구 행동 → 결과 관측 → 다음 행동 또는 최종 답
- **논문 결과:** HotpotQA·FEVER에서 Wikipedia API와 상호작용하는 검증을 실험하고, ALFWorld·WebShop에서도 추론과 행동 결합의 효과를 보고했다.
- **우리 적용:** 우리 Agent loop의 출발점이다. 첫 검색 후 원문 열기·재검색·계산·종료 중 무엇을 고르는지 기록한다.
- **읽을 곳:** 방법 그림 → Wikipedia 도구 예시 → reasoning/acting 비교 → 실패 사례
- **읽고 남길 것:** 도구 3–4개의 입력·출력과 종료 조건을 그린 한 장.

[공식 서지·원문](https://react-lm.github.io/) · [PDF](https://raw.githubusercontent.com/CJI0718/uos-nlp-2026-team5/main/docs/research/fact_checking/team_guide/papers/FC10_2023_ReAct_Synergizing_Reasoning_and_Acting_in_Language_Models.pdf)

#### FC21 · Fathom — 작은 공개 모델로 비교 기준이 될 검증기를 만들 수 있을까?

**Fathom: A Fast and Modular RAG Pipeline for Fact-Checking** · 고정 RAG pipeline · T1, T4, T5

- **논의:** 질문 확장과 검색을 모듈로 묶어 가벼운 모델로 실제 주장 검증을 수행한다.
- **구조:** HyDE식 질문 확장 → BM25 검색 → 의미 유사도 검색·선별 → 작은 LLM의 판정·근거 설명
- **논문 결과:** AVeriTeC 평가에서 test score 0.2043, dev score 0.378을 보고했다. 초록은 각 split에서 기준선 대비 개선을 제시한다.
- **우리 적용:** Agent와 비교할 작동 가능한 고정 절차의 청사진이다. 같은 검색·판정 모듈을 공유하고 행동 선택 부분을 바꿀 수 있다.
- **읽을 곳:** System description → retrieval 단계 → 결과의 dev/test 조건
- **읽고 남길 것:** 우리 고정 baseline의 모듈 목록과 Agent가 변경할 선택 표시.

[공식 서지·원문](https://aclanthology.org/2025.fever-1.20/) · [PDF](https://raw.githubusercontent.com/CJI0718/uos-nlp-2026-team5/main/docs/research/fact_checking/team_guide/papers/FC21_2025_Fathom_A_Fast_and_Modular_RAG_Pipeline_for_Fact-Checking.pdf)

#### FC15 · FIRE — 항상 많이 검색하는 것보다 필요한 순간에 더 찾는 편이 나을까?

- **읽고 남길 것:** 텍스트 주장과 이미지 주장에서 달라지는 도구 목록.

## 05. 진짜/가짜 주장 × 진짜/가짜 근거: 네 가지 시나리오 {#four-cases}

**연구 질문:** 그럴듯한 가짜 근거가 주어졌을 때도 Agent가 원출처를 다시 찾아 올바른 판정을 회복할 수 있는가? 이 비교 축을 T1·T2·T4·T5에 공통으로 적용할 수 있다.

### 같은 사실에서 네 입력을 만든다

먼저 사람이 확인한 기준 자료를 고정한다. 아래 설명용 기준 자료의 값은 **2024년 100, 2025년 110**, 실제 증가율은 **10%**다.

- 진짜 주장 Cₜ: “2025년 값은 전년 대비 10% 증가했다.”
- 가짜 주장 C𝒻: “2025년 값은 전년 대비 20% 증가했다.”
- 진짜 근거 Eₜ: 원자료 구간 “2024=100, 2025=110”.
- 가짜 근거 E𝒻: 실험용으로 바꾼 구간 “2024=100, 2025=120”.

| 시나리오 | 모델에게 주는 주장·근거 | 제공 문맥만 계산하면 | 기준 자료에 따른 주장 판정 | 재검증 Agent의 목표 |
|---|---|---|---|---|
| ① 진짜 주장 + 진짜 근거 | 10% 주장 + 100→110 | 지지 | **지지** | 올바른 값·출처를 유지해 설명 |
| ② 진짜 주장 + 가짜 근거 | 10% 주장 + 100→120 | 반박 | **지지** | 조작 값을 원출처와 대조해 판정 회복 |
| ③ 가짜 주장 + 가짜 근거 | 20% 주장 + 100→120 | 지지 | **반박** | 주장과 근거가 함께 속이는 상황에서 원출처 확인 |
| ④ 가짜 주장 + 진짜 근거 | 20% 주장 + 100→110 | 반박 | **반박** | 근거에 따라 거짓 주장 반박 |

이 표의 흥미로운 부분은 **②·③에서 제공된 문맥의 결론과 기준 자료의 결론이 서로 달라진다**는 점이다. ‘문맥에 충실한 답변’과 ‘현실을 확인한 답변’을 따로 측정할 수 있다.

### 세 개의 정답 필드를 따로 둔다

| 필드 | 무엇의 정답인가? | 위 ③의 값 |
|---|---|---|
| `claim_truth` | 기준 자료에 대한 주장의 사실 여부 | false |
| `evidence_integrity` | 제공 근거가 검증한 원자료와 일치하는가? | altered |
| `context_relation` | 제공 근거의 내용만으로 주장을 지지·반박하는가? | supports |

Agent가 읽는 입력에는 이 정답 필드를 넣지 않고, 검수 파일에서만 보관한다. 원자료 Eₜ와 가공본 E𝒻를 연결하는 `source_id`, 변경 위치, 변경 전후 값도 기록한다.

### 무엇을 비교하고 어떻게 채점할까?

| 비교 조건 | 모델에게 주는 접근 범위 | 평가하는 능력 |
|---|---|---|
| 문맥 판정기 | 주장 + 제공 근거 | `context_relation` 정확도 |
| 고정 재검증 | 위 입력 + 원출처를 한 번 조회하는 절차 | 현실 판정·출처 확인의 기본 효과 |
| 적응적 재검증 Agent | 같은 검색 도구·예산, 관측에 따라 원출처·반대 근거·계산 선택 | 조작 근거 탐지·판정 회복·비용 |

**주 지표:** 네 시나리오별 판정 정확도, 조작 근거 탐지 F1, 원출처 재확인 성공률, 그룹 전체 정답률, 재검증 호출 수. 가짜 근거에서 오답을 내던 사례 중 재검증 후 정답으로 돌아온 비율을 **회복률**로 기록한다.

### 50개와 네 시나리오를 함께 구성하는 방법

**기준 사실 50개 × 4조합 = 시스템별 입력 200개**로 설계할 수 있다. 독립 사례 단위는 원 사실 50개이며, 같은 사실에서 파생한 네 입력은 동일 `group_id`로 묶는다. 시작은 개발용 기준 사실 5개 × 4조합으로 잡으면 네 칸의 정답과 동작을 함께 점검하기 좋다.

팀원이 제시한 왜곡 조사와 연결하면, E𝒻가 ‘무엇이 바뀐 근거인지’도 출력하게 할 수 있다. **숫자 변경 → 계산 도구, 조건 생략 → 원문 문맥 읽기, 시점 변경 → 과거 버전 조회**처럼 오염 유형에 따라 조사 행동이 달라지는지가 연구 포인트다.

관련 읽기: VitaminC P02(근거의 작은 차이), CrossAug E06·FEVER Symmetric P01(대조 평가), Fact2Fiction P04(Agent가 읽는 근거 오염), LoCal FC17(분해·종합 검증), FactLens P15·TRACER P16(왜곡 위치·맥락).

## 06. 50개 평가 사례와 metric을 만드는 법 {#evaluation}

### 한 사례의 정답을 먼저 직접 작성한다

각자 **17개·17개·16개**를 작성하고, 다음 사람이 원문과 판정 이유를 교차 검수한다. 처음 6개는 두 개씩 가져와 세 사람이 함께 판정 기준을 맞춘다. 개발용 5개는 별도로 두고, 평가 50개의 구성은 선택한 태스크 표에 맞춘다.

```json
{
  "id": "T1-001",
  "claim": "A시의 2025년 대출량은 전년 대비 20% 늘었다.",
  "as_of": "2026-01-31",
  "required_slots": ["A시", "대출 건수", "2024", "2025", "동일 집계 범위"],
  "gold_verdict": "refuted",
  "gold_evidence_sets": [["table-2024-row-a", "table-2025-row-a"]],
  "gold_calculation": "(110-100)/100*100 = 10",
  "reason": "동일 단위의 두 값으로 계산한 증가율은 10%다."
}
```

모델 입력은 주장·기준일·도구 사양으로 구성하고, `gold_*`와 검수 메모는 평가 파일에 둔다. 각 근거에는 원문 URL, 인용 구간, 발행·효력 시점, 수집일을 연결한다.

### 최소 네 가지 숫자로 첫 결과를 설명한다

| 지표 | 정확히 세는 것 | 50개에서 읽는 법 |
|---|---|---|
| 판정 Macro-F1 | 지지·반박·근거 부족 각각의 F1 평균 | 자주 나오는 라벨에만 강한지 확인 |
| 근거집합 완성률 | 정답을 뒷받침할 최소 근거집합을 모두 회수한 사례 비율 | 35/50이면 70%; 한 문서만 찾은 경우를 구분 |
| 인용 지지율 | 설명의 각 인용이 연결된 주장을 실제로 뒷받침하는 비율 | 참인 설명에도 틀린 인용이 붙는지 확인 |
| 실행당 자원 | LLM·검색·도구 횟수, token, 시간 | 같은 판정 점수에서 얼마의 자원을 쓰는지 비교 |

T1은 계산·단위, T2는 조건 보존·종합, T3는 시점 정합성, T4는 Recall@k, T5는 왜곡 문구의 Span F1과 원문 연결 정확도, T6는 Mission 선택 Macro-F1과 실행 성공률을 추가한다. **정답 판정과 좋은 근거를 각각 점수화하면, 개선할 모듈이 보인다.**

### 분석은 곧 다음 실험의 설계다

| 첫 실행에서 볼 오류 | 수정할 한 가지 | 다시 비교할 지표 |
|---|---|---|
| 관련 기사는 찾지만 정작 표를 놓침 | 검색 질의에 지표·연도 추가 | 근거 회수·판정·검색 수 |
| 값은 맞고 단위가 다름 | 도구 관측에 단위·집계 범위 필드 추가 | 단위 오류·계산 정확도 |
| 분해하며 ‘모두’ 또는 예외가 사라짐 | 원래 조건과 하위 주장 대조 단계 추가 | 조건 보존·종합 오류 |
| 근거가 모자라는데 확정 판정 | 충분성 체크에 따라 재검색/보류 선택 | 오답률·coverage·호출 수 |

기말 발표에서는 **어떤 오류를 발견했는가 → 무엇을 바꿨는가 → 어떤 지표가 얼마나 바뀌었는가**를 실제 실행 기록으로 설명한다.

## 07. 세 사람이 어떻게 시작할까? {#team}

| 역할 | 처음 맡을 일 | 공통 산출물과 연결 | 교차 검수 |
|---|---|---|---|
| A · 태스크·데이터 | 주장 유형, 원문 수집, gold 기준 | 직접 작성 사례 17개, annotation guide | B의 검색 근거 점검 |

### 다음 회의 45분

1. **10분:** 도입 사례를 함께 읽고 입력·출력을 한 문장씩 설명한다.
2. **15분:** T1–T6 중 두 후보와 2×2 적용 여부를 비교한다. 데이터 50개를 직접 만들기 쉬운지, 행동 선택이 어디에 있는지 본다.
3. **10분:** 한 후보와 주 지표 3–5개, 비교 시스템 2–3개를 선택한다.
4. **10분:** 각자 읽을 논문 두 편, 수집할 예시 두 개, 다음 공유 시간을 정한다.

### 평가에서 고정할 조건

- 비교군의 모델·도구·문서 모음·검색 상한·token 상한·sampling 설정을 고정한다. 기능 ablation과 자원 상한을 맞춘 비교를 구분하고 실제 소비량도 보고한다.
- 50개 평가 문항과 개발 예시는 분리한다. 변형 문항은 원 주장·사건의 그룹을 보존해 분할하고, 평가를 보고 수정했다면 그 절차를 기록한다. 평가 50개에서 한 사례의 accuracy 차이는 2%p다.
- T1의 수치 허용 오차·반올림·단위 규칙, T2의 AND/OR·부분 지지·NEI 종합표, T3의 기준일·효력일·문서 접근 가능 시점, T4의 근거 단위를 사전에 정의한다. ‘주말’처럼 범위가 모호한 사례는 입력 문맥을 보완하거나 별도의 모호성 유형으로 처리한다.
- 2×2에서 ‘가짜 근거’는 실험용으로 내용을 조작한 문서 구간을 뜻한다. 실제 출처의 진위·내용의 사실성·주장과의 관계는 서로 다른 변수다. 아무 진짜 주장과 아무 진짜 근거를 짝지으면 지지 관계가 보장되지 않으므로, 같은 기준 사실에서 대응 쌍을 만든다.
- 위 네 칸의 지지/반박 관계는 숫자를 통제해 만든 예시다. 일반적인 문서 쌍에는 관련 없음·근거 부족도 있다. 원출처 접근이 막힌 조건에서는 조작 탐지·현실 정답을 무조건 기대하지 않고 보류와 문맥 관계를 별도로 채점한다.
- 2×2 구조 자체의 최초성은 주장하지 않는다. 한국어·오류 위치·오염 유형별 조사 정책·원출처 재검증 비용의 조합에서 차이를 구체화한다. 모방한 가짜 URL·문서는 닫힌 실험 자료로 관리하며 실제 웹에 게시하지 않는다.
- T6의 작은 실행 평가는 테스트 환경을 사용한다. 실제 외부 신청·발송·결제·계정 변경은 권한과 승인을 갖춘 별도 실행 범위다. Mission 중심의 연구를 택하면 전용 선행연구를 더 조사한다.
- 지지·반박·근거 부족의 3분류는 우리 기본 설계다. AVeriTeC의 라벨 체계와 변환해 비교할 때는 대응 규칙을 명시한다. 상충 근거는 질·시점·범위를 점검하고, 확정 근거가 부족하면 보류로 처리한다.
- gold·판정 기사의 결론·미래 문서가 모델 입력에 새는지 검사한다. T3는 모델 내부 지식의 시간 누출까지 완전히 제거한다고 주장하지 않는다. 동일 뉴스의 재전송은 독립 근거로 중복 계산하지 않는다.
- API 오류·빈 응답·형식 실패는 실행 상태로 따로 남긴다. semantic NEI와 실행 오류를 같은 라벨로 합치지 않는다. LLM Judge는 사람 검수 표본과 대조한다.
- risk=확정 답변 중 오답 비율, coverage=전체 중 확정 답변 비율을 함께 보고한다. 확정 답변이 0개인 risk는 N/A다. 새롭게 발견한 타당한 근거는 gold 검수 절차로 반영한다.
- 무료 모델의 가용성·검색 API 이용조건·GPU 자원은 실행 전에 확인하고, 호출 상한·재시도 정책을 정한다. ChatGPT 구독과 외부 API 사용 비용은 별개다.
