## 1. 서비스 아이디어와 연구 질문을 분리하기

**서비스 아이디어:** 뉴스를 받아 여러 출처를 대조하고 근거가 있는 판정을 제공한다.

**연구 질문 후보:** 같은 검증 자원 아래에서 질의·도구·출처·검색 종료를 적응적으로 선택하는 것이 고정된 검증 절차보다 언제 유리한가?

규칙으로 계산 가능한 부분은 코드로 수행하고 Agent는 무엇을 확인해야 하는지 결정한다. 사람은 gold와 증거를 검수한다. 사람·규칙이 불가능해서 Agent를 쓰는 것이 아니라, 불확실한 상태에서 다음 확인 행동을 고르는 능력의 가치를 측정한다. FEVER에는 이미 고정 pipeline 기준선이 있고, ReAct는 FEVER에서 행동/관찰을 활용한다. [FC02](literature.md#fc02), [FC10](literature.md#fc10)

## 2. 업무를 어떻게 정의할까?

### 입력과 출력

- 입력: 짧은 주장, 또는 기사 URL/공유 가능한 본문과 판정 기준 시점·범위.
- 주 실험의 최소 입력 제안: 사람이 확정한 독립 주장 하나. 기사에서 주장을 추출하는 능력과 검증 능력을 먼저 분리한다.
- 출력: 정규화한 주장, 검증 질문, 판정, 근거 ID·문장/셀, 대상 시점, 계산 결과, 반대 근거, 남은 불확실성, 종료 사유.
- 장문 설명의 유창성보다 **판정과 인용된 근거가 맞는지**를 우선 평가한다. ALCE는 답의 정확성과 citation 품질을 분리하는 참고다. [FC27](literature.md#fc27)

### 역할 분리

| 구성          | 역할                               | 하지 말아야 할 해석                                 |
| ------------- | ---------------------------------- | --------------------------------------------------- |
| 기사·RSS     | 검증할 주장·발표를 발견           | 기사 수가 많으면 사실이라는 투표                    |
| 공식 문서/API | 직접 근거·정의·수치·버전을 확보 | 공식 출처이므로 모든 주장에 자동 정답               |
| 검색기        | 관련 문서·반대 증거·원출처 탐색  | 관련 문서를 찾으면 입증 완료                        |
| 결정론적 도구 | 단위 변환·비율·기간 비교         | 계산 입력의 의미까지 코드가 자동 보증               |
| Agent         | 부족한 정보와 다음 행동 선택       | 미리 정한 전체 순서를 반복하는 것만으로 적응성 주장 |
| 보고서 생성   | 근거에 제한된 판정과 한계 설명     | 근거 없이 그럴듯한 이야기 채우기                    |

### 예시 — 전부 가상의 값이며 실제 뉴스가 아님

입력: “A시의 올해 상반기 관광객은 지난해 상반기보다 20% 늘었다.”

Agent가 확인할 것은 ‘관광객이 늘었다’라는 기사 하나가 아니라 지역 범위, 집계 기준, 기간, 단위, 잠정/확정 수치다. 두 기간이 각각 120만·100만으로 **같은 기준**일 때 계산 도구는 `(120−100)/100×100=20%`를 반환한다. 서로 다른 기간의 값을 얻었다면 재조회해야 하고, 일치하는 자료를 확보하지 못했다면 그 한계를 표시한다.

이 예시는 행동 순서를 강제하는 prompt가 아니다. 직접적인 충분한 근거가 있으면 적게 확인하고, 기간·정의가 충돌하면 다른 도구를 쓰도록 설계한다.

## 4. 연구 질문 후보 — 주된 비교 축은 하나부터

| 연구 질문                     | 통제하여 비교할 조건                                          | 관찰할 것                                     |
| ----------------------------- | ------------------------------------------------------------- | --------------------------------------------- |
| RQ-A. 적응적 도구 선택        | 같은 도구·LLM·최대 예산, 고정 workflow vs ReAct             | grounded success, 잘못 선택한 도구, 낭비 호출 |
| RQ-B. 분해·반증 탐색         | 원문 질의 vs 하위 질문 vs 반대 근거를 추가 탐색               | 복합 주장 누락, 근거 충분성, 비용             |
| RQ-C. 날짜·단위 확인         | 일반 검색 vs 시점/단위 메타데이터 확인·계산 도구             | 기간/분모/%p 혼동, 숫자 정합성                |
| RQ-D. 근거가 충분할 때 멈추기 | 고정 검색량 vs 근거 상태 기반 추가 검색/보류                  | 비용–성공률 곡선, 보류, 오류성 확신          |
| RQ-E. 검색기와 Agent 정책     | Kiwi+BM25/dense/hybrid를 고정 정책에서 비교 후 정책 하나 변경 | evidence recall과 최종 판정의 관계            |
| RQ-F. 자료의 갱신·충돌       | 동일 snapshot 내 구버전·동일 전재·상반 근거 포함 여부       | 중복을 독립 증거로 세는 오류, 시점 오판       |

FIRE는 반복 검색과 종료, ProgramFC/FOLK는 분해와 논리, TSVer/QuanTemp는 시계열·수치, Fathom/HerO 2는 강한 pipeline 비교에 연결된다. [FC11](literature.md#fc11), [FC12](literature.md#fc12), [FC15](literature.md#fc15), [FC21](literature.md#fc21), [FC22](literature.md#fc22), [FC23](literature.md#fc23), [FC26](literature.md#fc26)

## 5. 기존 연구와 차별화할 여지

**문헌에서 확인한 사실:** 한국어 검증 필요성 탐지와 다중 검색·LLM 판정을 연결한 국내 연구가 있다. 그러므로 ‘한국어 RAG 팩트체크 최초’는 주장하지 않는다. [FC30](literature.md#fc30)

**팀의 제안이며 아직 검증되지 않은 것:**

1. 한국어 기사에서 ‘전년 동기’, ‘증가율’, ‘증가 폭’, 지역·연령·명목/실질 등의 조건이 빠질 때 공식 자료 API와 정의 문서를 함께 확인하는 정책.
2. 정답이 쉬운 주장에는 검색을 줄이고, 시점·출처가 충돌할 때만 추가 검증하는 비용–성능 비교.
3. Kiwi+BM25로 잘 찾는 직접 근거와 dense/hybrid가 필요한 의미 변형 사례를 분리해 Agent의 선택과 연결.
4. 판정이 맞더라도 인용·계산·시점이 틀리면 실패로 보는 근거 동반 평가.

이는 새 알고리즘임을 증명한 주장도, 다른 연구에 없다고 확인한 novelty 주장도 아니다. 관련 연구의 방법·데이터·baseline과 대조해 가장 작은 기여를 정한다.

## 6. 당장 만들지 않을 것

전 분야 실시간 뉴스 서비스, 대규모 자동 크롤러, 모든 언어·모달리티 지원, 자체 벡터 DB 제품, 무제한 multi-agent 토론, 대형 모델 RL 학습, 공개 자동 ‘가짜뉴스’ 게시 기능은 현재 목표가 아니다.

과제의 최소 산출물은 **검수된 주장 묶음 + 제한된 도구 + 비교 가능한 두세 방법 + 근거/행동 기록 + 평가·오류 분석**이면 된다. 원시 문서가 필요한 경우에도 접근·저장·공개 권한은 별도로 확인한다.

## 7. 다음 팀 회의에서 결정할 순서

1. 팀원이 찾은 선행연구와 검증하고 싶은 실제 주장 3~5개를 공유한다.
2. 각 주장에 대해 사람이 정답·충분한 근거·기준 시점을 만들 수 있는지 확인한다.
3. track·주 연구 질문·label 정책·최대 도구 범위를 정한다.
4. 작은 개발용 사례로 도구 접근과 채점 가능성을 점검한다. 평가용 50개와 분리한다.
5. **실행 요청과 예산을 별도로 승인한 후** 파일럿을 돌린다.

50개 구성·예산 숫자는 [평가 설계](evaluation.md)에 제안으로 제시했다. 아직 데이터, 모델 요청, GPU 학습, 실험 결과는 없다.

## 8. 구체화한 에이전트 워크플로우 및 세부 태스크 제안: Autonomous News Investigation & Mission Agent

<헌수>

**자율적 정보 수집 · 근거 기반 팩트체크 및 왜곡 조사 · 업무 자동 생성 및 실행 · 지속적 추적**

에이전트의 조사 결과에서 끝내지 않고, 에이전트를 실제 업무 수행까지 연결한다.

### 8.1 프로젝트의 최종 핵심 목표

> 사용자가 지정한 관심 분야와 조사 주기에 따라 Agent가 뉴스, SNS, 블로그 등 다양한 출처의 정보를 자율적으로 수집하고, 원문 및 독립적인 증거를 탐색하여 핵심 주장의 사실 여부를 검증한다.
>
> 검증 과정에서 사실관계 오류, 수치 불일치, 과장, 맥락 누락 또는 왜곡이 발견되면 Agent는 추가 조사를 수행하여 **무엇이 잘못되었는지, 원문과 어떤 부분에서 불일치하는지, 오류나 왜곡이 발생한 원인은 무엇인지** 분석한다. 원본 자료와 기사·게시물의 문장, 수치, 표 등을 대조하여 구체적인 문제 지점과 검증 근거를 제시하고, 실제 정보 전달 경로가 확인되는 경우 왜곡이 발생한 단계까지 추적한다.
>
> 검증 결과를 바탕으로 Agent는 사용자에게 유용한 업무(Mission)를 스스로 발견하고, 정보의 성격과 사전에 위임된 권한에 따라 적절한 Mission을 선택·실행한 뒤 완료 여부를 확인한다.
>
> 사용자는 지정한 주기에 따라 검증된 정보, 오류 및 왜곡 분석 결과, Agent가 수행한 업무와 그 결과를 통합 브리핑으로 제공받는다. 또한 관심 있는 주장이나 사건에 대해 추가 조사 또는 장기 추적을 위임할 수 있으며, Agent는 새로운 증거가 발견되면 자율적으로 재검증하고 변경 사항을 보고한다.

전체 구조는 **5개 핵심 단계(STEP 1~5)** 와 **사용자 최초 설정(STEP 0)**, 그리고 **1개의 장기 추적 경로(Continuous Claim Tracking)** 로 구성된다.

| 단계                | Task                                           | 핵심 역할                                                                         |
| ------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| **STEP 0**    | 사용자 최초 설정                               | 관심 분야 · 조사 주기 · 허용할 업무 범위 설정                                   |
| **STEP 1**    | Autonomous Information Discovery               | 뉴스·SNS·블로그·공식 발표 등 관심 분야의 새로운 정보 자동 탐색                 |
| **STEP 2**    | Fact-Checking & Distortion Investigation       | 진위 검증 + 근거 대조 · 수치 검산 + 무엇이·어디서·왜 잘못됐는지 왜곡 지점 분석 |
| **STEP 3**    | Autonomous Mission Discovery *(핵심 차별화)* | 검증된 정보에서 수행할 가치가 있는 업무를 스스로 발견·선택                       |
| **STEP 4**    | Mission Execution & Evaluation                 | 도구 활용 · 실제 업무 수행 후 성공 및 완료 여부 확인                             |
| **STEP 5**    | Verified Briefing & Action Report              | 검증 결과 · 왜곡 원인 · 수행 업무 · 남은 문제를 정기 브리핑으로 보고           |
| **별도 경로** | Continuous Claim Tracking                      | 사용자가 특정 주장·질문을 선택하면 이후 새 증거를 자율적으로 탐색·재검증        |

### 8.2 단계별 상세 설계

#### STEP 0. 사용자 최초 설정

사용자가 처음부터 자신의 과거 활동이나 개인 문서를 대량으로 제공할 필요 없이 기본적으로 세 가지만 설정한다.

- **① 관심 분야**: `AI / LLM`, `IT / 소프트웨어`, `과학 / 기술`, `경제 / 금융`, `정부 정책`, `행사 / 교육`, `문화 / 생활` 등
- **② 자동 조사 주기**: `매일` / `매주` / `매월`
- **③ 활성화할 Mission 유형**:
  1. `Opportunity Execution`
  2. `News-to-Artifact`
  3. `Event & Change Manager`
  4. `App Trust & Safe Trial`

> **설계 원칙:** Mission 설정을 처음부터 필수로 요구하지 않는다. 사용자가 초기에는 관심 분야와 주기만 설정하고, 나중에 Agent가 적절한 Mission을 제안하도록 만들 수 있다. 반복적으로 유용하다고 판단한 Mission만 사전 위임하면 된다.

#### STEP 1. Autonomous Information Discovery

- **목표**: 사용자가 선택한 분야에 관해 새로운 정보를 알아서 수집한다.
- **수집 대상**: 뉴스 기사, 기술 블로그, 공개 SNS 게시물(X, Threads 등), 논문 소식, 공식 보도자료 등.
- **선별**: Agent는 관련성을 판단하고, 동일한 기사를 반복해서 보여주지 않도록 중복 제거 및 중요도 선별을 수행한다.
- **제약 구분**: 뉴스 검색 주기와 SNS 수집 가능 범위는 구분해야 한다. X나 Threads 등은 접근 권한과 API 제한에 따라 자동 수집할 수 있는 데이터 범위가 달라진다.

#### STEP 2. Fact-Checking & Distortion Investigation (Evidence-Based Distortion Investigation & Fault Localization)

- **목표**: 정보가 정말 사실인지, 무엇이 과장되거나 누락됐는지, 왜곡이 어디에서 나타났는지 확인한다.

| 기능                              | Agent가 수행하는 일                                        |
| --------------------------------- | ---------------------------------------------------------- |
| **Claim Extraction**        | 검증할 수 있는 핵심 주장 추출                              |
| **Source Verification**     | 최초 발표·공식 문서·원본 논문 확인                       |
| **Evidence Retrieval**      | 근거와 반대 증거 탐색                                      |
| **Numerical Verification**  | 비율, 증가율, 단위, 통계 수치 계산                         |
| **Context Verification**    | 비교 기준·기간·조건·예외 확인                           |
| **Distortion Localization** | 원문의 어느 부분과 기사·SNS의 어떤 표현이 충돌하는지 식별 |
| **Verdict Generation**      | 지지 / 반박 / 맥락 왜곡 / 판단 보류 등 판정                |

단순히 "틀린 뉴스인지 판단한다"를 넘어 다음 세 가지를 구분한다:

1. **무엇이 틀렸는가?** — 수치 오류, 과장, 누락된 조건, 잘못된 인용 등을 식별
2. **어디에서 달라졌는가?** — 원본 논문·공식 발표와 기사·SNS의 어떤 문장이나 표가 불일치하는지 특정
3. **왜 문제가 되는가?** — 계산 오류, 비교 기준 혼동, 과도한 일반화 등을 근거로 설명

또한 원문과 SNS 내용의 차이를 발견하는 것과, 그 SNS 게시물이 해당 기사를 실제로 인용해 왜곡했다는 것을 입증하는 것은 구분해야 한다(인용 관계 및 게시 시점 확인 필요).

##### 일반 팩트체크와의 비교 (예: 원본 논문 "특정 실험에서 처리량 40% 증가" → SNS "모든 작업에서 성능 40% 향상")

| 일반 팩트체크            | 우리가 설계하는 Agent                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| 주장이 과장되었다고 판정 | 과장된 표현이 정확히 어디인지 특정                                                          |
| 관련 원문 링크 제공      | 원문 문장·표·셀과 게시물의 문구를 직접 1:1 대응                                           |
| 간단한 설명 제공         | 처리량을 전체 성능으로 일반화한 논리적 오류 설명                                            |
| 검증 결과 저장 후 종료   | 확인된 인용 관계가 있으면 왜곡 전파 과정도 조사하고, 필요시 추가 조사 및 정기 브리핑에 포함 |

> **선행연구와의 관계 및 차별화:** 중요한 맥락이 생략된 주장을 탐지하는 [TRACER (EMNLP 2025)](https://aclanthology.org/2025.emnlp-main.1724/)나 세부 주장 단위의 오류 식별을 다루는 [FactLens (Findings of ACL 2025)](https://aclanthology.org/2025.findings-acl.929/) 등 선행연구가 존재하므로, 오류 위치 식별 자체를 최초의 연구라고 주장하지는 않는다. 대신 **Agent가 오류의 종류에 따라 조사 계획을 바꾸고, 여러 출처를 대조해 증거가 있는 문제 지점만 특정하는 적응적 능력**을 실험으로 검증한다.

#### STEP 3. Autonomous Mission Discovery 

Fact-Checking이 끝나면 Agent는 다음 질문을 판단한다:

> *"이 정보를 단순히 보고하는 것으로 충분한가, 아니면 사용자를 위해 실제로 수행할 만한 업무가 있는가?"*

Agent는 정보의 성격, 사용자의 관심 분야, 허용된 Mission, 필요한 권한, 기대 효용 등을 종합해 업무 생성 여부를 결정한다.

| 발견한 정보                                  | Agent가 선택할 수 있는 Mission          |
| -------------------------------------------- | --------------------------------------- |
| 무료 교육·행사·지원사업 모집               | `Opportunity Execution`               |
| 활용할 수 있는 공개 데이터·새 기술 발표     | `News-to-Artifact`                    |
| 제품 출시일·행사 일정·정책 시행일          | `Event & Change Manager`              |
| 새로운 오픈소스 앱·AI 도구 출시             | `App Trust & Safe Trial`              |
| 사실은 확인됐지만 실행할 일이 없는 일반 뉴스 | **Mission 생성하지 않음**         |
| 미래에 결과가 나오는 주장                    | 사용자에게 **Tracking 등록 제안** |

특히 **Mission을 생성하지 않는 선택**도 중요하다. 관련성이 낮거나 실질적인 결과물을 만들 수 없는 정보에서 불필요한 업무를 자동 생성하면 서비스가 오히려 번거로워진다.

#### STEP 4. Mission Execution & Evaluation

정정 요청 Agent는 제외하고, 다음 네 가지 Mission을 다룬다:

(미션은 아직은 이정도로 하고 나중에 더 늘리거나 줄이거나 유동적으로 해도 될거 같아요.)

- **Mission A — `Opportunity Execution`**: 검증된 기회를 발견하고 실제 활용을 준비하거나 실행
  - *예*: 새로운 무료 AI 콘퍼런스 모집이 확인되면 참가 조건 조사, 필요 자료 준비, 신청 링크 정리, 허가된 신청 단계 실행.
  - *완료 결과*: 신청 준비 완료 또는 사용자 승인 후 실제 신청 접수 확인.
- **Mission B — `News-to-Artifact`**: 검증된 정보를 바로 활용 가능한 결과물로 변환
  - *예*: 새로운 오픈소스 모델 공개 사실을 확인하면 공식 예제를 기반으로 실행 스크립트와 Docker 테스트 프로젝트 제작. 공개 통계가 발표되면 정리된 데이터 파일이나 분석 리포트 생성.
  - *완료 결과*: 실제 사용 가능한 파일·코드·분석 결과와 테스트 기록.
- **Mission C — `Event & Change Manager`**: 검증된 일정과 이후 발생한 변경을 관리
  - *예*: 기술 행사 개최, 제품 출시, 정책 시행 등의 공식 일정을 확인하고 사용자가 허용한 캘린더에 등록. 일정이 변경되면 확인 후 기존 일정을 갱신.
  - *완료 결과*: 정확한 일정 반영, 변경 이력 기록, 필요한 알림.
- **Mission D — `App Trust & Safe Trial`**: 새롭게 등장한 앱의 신뢰성과 보안 위험을 조사하고 제한적으로 체험
  - *예*: GitHub의 AI Agent 앱 출시 소식을 발견하면 README 주장과 실제 구현을 대조하고, 의존성 취약점·API 키 처리·설치 스크립트 등을 분석. 허용된 격리 환경에서 가짜 자격증명으로 테스트.
  - *완료 결과*: 기능 검증 결과, 발견한 보안 위험, 테스트 기록, 미확인 사항. *(취약점이 발견되지 않았다는 것이 완전한 안전성을 보장하지는 않으며, 실제 API 키를 제공하지 않고 격리 범위 안에서 판단한다.)*

##### 실제 실행의 권한 구분 및 완료 검증

| 단계                                      | 기본 정책                            |
| ----------------------------------------- | ------------------------------------ |
| 정보 검색·비교·분석                     | 자동 수행                            |
| 임무 생성·자료 제작·격리 테스트         | 사전 위임된 범위에서 자동 수행       |
| 캘린더·개인 파일 수정                    | 사용자가 미리 허용한 범위에서만 수행 |
| 외부 신청·이메일 발송·결제·실계정 변경 | 개별 승인 필요                       |

Agent가 작업을 수행한 뒤에는 반드시 완료 여부를 검증한다(예: 신청 버튼을 눌렀다는 사실만으로 완료라 하지 않고 접수 확인 결과가 있어야 완료 처리).

#### STEP 5. Verified Briefing & Action Report

사용자가 정한 주기마다 Agent가 검증 결과뿐 아니라 대신 처리한 업무까지 함께 보고한다.

- **브리핑 포함 항목 (예시)**:
  - 검증한 주장 수 / 문제 발견 수 / 생성한 Mission 수 요약
  - **팩트체크 및 왜곡 조사 결과**: 예) AI 모델 성능 뉴스에서 과장 확인 (원본 보고서의 특정 벤치마크 결과가 일반적인 성능 향상으로 표현됨 → 문제 문장과 원본 근거 확보)
  - **Agent가 대신 수행한 업무**: 예) 새 공개 데이터셋 분석 파일 생성 완료, 새 AI 앱 보안 사전점검 완료, 기술 행사 참가 준비 완료(외부 신청 승인 대기)
  - **사용자 후속 행동 선택지**: `주장 추가 조사` · `장기 추적 등록` · `준비된 업무 승인` · `관련 근거 열람`

### 8.3 별도 경로: Continuous Claim Tracking

> 구현시에는 메인 Agent가 추적별 목표와 상태를 생성하고, 재사용 가능한 Tracking 하위 Agent에 위임하는 방식으로 

사용자는 검증한 주장이나 사건뿐 아니라, **관심 있는 제품·후속 시리즈 등 특정 대상에 대한 지속적인 조사**를 위임할 수 있다.

추적은 초기 Fact-Checking 이후 또는 사용자의 직접 요청으로 시작하며, 별도의 Mission을 먼저 실행할 필요는 없다.

1. **추적 대상 등록**: 추적할 주장·제품·질문과 확인하고 싶은 정보, 알림 조건을 정의한다.
2. **조사·검증 계획 생성**: 확인할 출처, 필요한 증거, 예상 발표 시점과 다음 조사 일정을 결정한다.
3. **지속적 재조사**: 공식 발표와 관련 자료를 탐색하고, 새로운 정보의 신뢰성을 검증하여 기존 기록과 비교한다.
4. **결과 및 변경 보고**: 새롭게 확인된 사실이나 중요한 변경 사항을 근거와 함께 알린다. 동일한 내용을 반복 전달하는 중복 알림은 줄인다.
5. **추적 종료 또는 연장**: 목표 달성, 사용자 중지 또는 사전에 설정한 기간·조사 한도에 따라 종료하거나 연장한다.

**예시 1. 발표한 계획의 실제 이행 여부 추적**

기사에서 “A기업이 2027년 1분기에 차세대 배터리를 상용화할 예정이다”라는 주장을 확인한 뒤, 사용자가 **“실제로 상용화되는지 추적”**을 위임한다.

Agent는 ‘상용화 계획을 발표했다’는 사실과 ‘실제로 상용화했다’는 사실을 구분하고, 이후 확보한 증거에 따라 `상용화 완료` · `부분 이행` · `지연` · `취소` · `확인 불가` 등을 보고한다.

**예시 2. 원하는 노트북·전자기기의 다음 시리즈 추적**

사용자가 특정 노트북이나 전자기기의 후속 모델을 기다리는 경우, 다음과 같이 요청할 수 있다.

> “관심 있는 노트북의 다음 시리즈를 기다리고 있어. 후속 모델의 공식 발표, 주요 사양, 국내 출시일과 사전예약 정보가 나오면 알려줘.”

Agent는 해당 제품군을 추적 대상으로 등록하고, 사용자가 원하는 정보를 지속적으로 조사한다. 후속 모델의 이름이나 출시 여부가 아직 공식적으로 확인되지 않았더라도 관심 대상 등록은 가능하다.

| 발견한 정보                    | Agent가 수행하는 일                                                     |
| ------------------------------ | ----------------------------------------------------------------------- |
| 후속 모델 관련 루머·유출 정보 | 최초 출처와 근거를 확인하고, 공식 정보와 구분하여 미확인 상태로 관리    |
| 제조사의 공식 발표             | 후속 모델 여부와 주요 사양을 확인하고, 공개되지 않은 항목은 별도로 표시 |
| 출시일·가격 공개              | 국가·모델별 차이를 확인하고 사용자가 관심 있는 지역의 정보를 정리      |
| 사전예약·출시 혜택 공개       | 일정, 대상 모델, 적용 조건과 제한 사항을 확인하여 알림                  |
| 기존 발표 내용 변경            | 이전 정보와 비교하여 출시 연기, 사양 변경 등 중요한 차이를 보고         |

사용자는 **공식 발표만 알림받을지, 미확인 소식도 신뢰도 표시와 함께 받아볼지** 선택할 수 있다.

필요하면 추적 결과를 바탕으로 기존 제품과 후속 모델의 비교표를 만드는 `News-to-Artifact`, 사전예약 일정을 관리하는 `Event & Change Manager` 등의 Mission으로 연결할 수 있다. 각 Mission은 사용자가 위임한 범위에서 수행한다.

정기 브리핑 주기와 개별 추적의 조사 주기는 독립적으로 관리한다. 중요한 새 정보가 확인되면 사용자가 설정한 조건에 따라 별도로 알리고, 그 외 조사 결과는 정기 브리핑에 포함한다.

### 8.4 논리적 역할 분리와 단계적 개발 순서 - 기말 과제 파트



처음부터 여러 개의 LLM Agent를 분리 구현할 필요는 없으며, 초기에는 하나의 오케스트레이터가 도구와 전문 워크플로를 호출하는 형태로 구성한다.

| 구성                                               | 책임                                         |
| -------------------------------------------------- | -------------------------------------------- |
| **Discovery**                                | 관심 분야 정보 탐색 및 선별                  |
| **Fact-Checking & Distortion Investigation** | 진위 검증, 원문 대조, 계산 및 오류 위치 분석 |
| **Mission Discovery**                        | 검증된 정보로 수행할 업무가 있는지 판단      |
| **Mission Execution**                        | 선택된 업무 실행                             |
| **Mission Evaluator**                        | 결과·성공 조건·권한 위반 여부 확인         |
| **Tracking**                                 | 선택된 주장에 대한 후속 증거 탐색 및 재검증  |
| **Scheduler / Notification**                 | 예약 실행과 브리핑·알림 전달                |

#### 단계별 개발 로드맵 (Phase 1 ~ 7)

| 개발 단계         | 목표                | 완료 조건                                                                             |
| ----------------- | ------------------- | ------------------------------------------------------------------------------------- |
| **Phase 1** | Fact-Checking MVP   | 기사/게시물 입력 → 주장별 판정·원문 근거·오류 위치 식별                            |
| **Phase 2** | 자율적 정기 수집    | 관심 분야와 주기에 따라 자동 수집 및 검증                                             |
| **Phase 3** | Mission Discovery   | 정보의 성격에 맞게 Mission 생성 또는 미생성 판단                                      |
| **Phase 4** | 첫 Mission 실행     | 선택한 Mission 하나(우선 추천: `Event & Change Manager`)를 수행하고 성공 여부 확인  |
| **Phase 5** | Tracking Agent      | 특정 주장의 후속 조사 및 판정 갱신                                                    |
| **Phase 6** | 나머지 Mission 확장 | `News-to-Artifact`, `App Trust & Safe Trial`, `Opportunity Execution` 순차 통합 |
| **Phase 7** | 운영 및 평가        | 반복 실행, 오류 복구, 업무 이력과 실행 품질 평가                                      |

> **수업 연구 과제 범위와의 조율:** 한 학기 수업의 연구 과제에서는 **50개 평가 데이터로 STEP 2(Fact-Checking & Distortion Investigation)의 근거 동반 판정·왜곡 위치 식별 성능과 적응적 조사 정책( 및 STEP 3 Mission 생성 판단)**을 우선 정량 평가하고, STEP 4의 실제 Mission 실행은 별도의 시연 또는 작은 실행형 평가로 분리한다.

### 8.5 이 프로젝트의 세 가지 핵심 가치

1. **Information Reliability**: 신뢰할 수 있는 정보를 제공하고, 틀린 부분과 왜곡 원인을 원문 근거로 설명한다.
2. **Autonomous Task Execution**: Agent가 검증 결과를 활용해 실제 업무를 발견하고, 위임된 범위에서 직접 실행한다.
3. **Continuous Delegation**: 사용자가 매번 다시 요청하지 않아도 정기 조사와 선택된 장기 추적 업무를 지속적으로 관리한다.
