# NLP 5조 — 근거가 잘못되었을 때, 팩트체크 Agent는 무엇을 해야 할까요?

**현재 논의를 한 문장으로 정리하면:** 고정 문서 집합에서 찾은 근거의 부족·충돌·오도가 사실 판정에 미치는 영향을 살펴보고, Agent가 추가 검증과 종료를 선택하여 **근거를 갖춘 올바른 판정**을 만들 수 있는지 연구하려고 합니다.

이 문서는 세 팀원이 같은 출발점에서 Task를 논의하기 위한 정리입니다. 중간 발표는 논문을 하나씩 소개하는 목록보다 **어떤 의문이 생겼고, 선행연구를 읽으며 그 의문을 어떻게 좁혔는지**를 보여주는 흐름으로 구성합니다.

## 1. 처음 합류하셨다면: 무엇을 만드는 연구인가요?

처음의 큰 방향은 **기사·뉴스·주장을 검증하는 팩트체크 Agent**였습니다. 검색, 공식 자료/API 조회, 근거 대조를 수행한 뒤 주장에 대한 판정과 이유를 제시하는 시스템입니다. 최근 논의에서는 그중 **근거의 상태가 좋지 않을 때의 판단과 행동**에 초점을 맞추었습니다.

다음은 구조를 설명하기 위한 가상 예시입니다.

| 단계 | 예시 |
|---|---|
| 입력 주장 | “기관 A는 2022년에 설립되었습니다.” |
| 고정 corpus 검색 | 소개문 세 개는 2022년을 말하지만, 연혁 문서는 2010년이라고 말합니다. |
| Agent가 결정할 일 | 대상 기관·시점이 같은지 확인하고, 충돌을 해소할 추가 자료를 찾을지 선택합니다. |
| 추가 도구 | 공식 연혁·등록 자료 검색, 원문 페이지 열람, 필요하면 날짜·수치 계산 |
| 출력 | Refuted, 실제 설립연도 2010년, 이를 입증하는 근거, 2022년 자료가 재출범 시점을 가리킨다는 설명 |
| 평가 | 판정이 맞는지, 인용 근거가 충분한지, 충돌 이유를 맞게 설명했는지, 검색에 얼마나 비용을 썼는지 |

단순히 검색 결과에 있는 문장을 복사하는 문제보다 어렵습니다. **주제 관련성, 사실성, 근거 충분성, 출처 독립성**은 서로 다릅니다. Agent는 이 차이를 보고 계속 찾기·다른 출처 확인·판정·보류 중 어떤 행동이 적절한지 선택합니다.

수업과의 연결도 구체적입니다. **정보검색(retrieval)**은 corpus에서 문서를 선택하는 부분, **RAG**는 선택한 문서를 판정에 사용하는 부분, **ReAct**는 도구 관찰을 바탕으로 다음 행동을 정하는 부분입니다. 최종 설명 생성과 정량 평가까지 함께 들어가므로 전반부 수업 내용을 하나의 Task에 연결할 수 있습니다.

## 2. 우리의 질문은 어떻게 좁혀졌나요?

| 논의의 단계 | 생긴 질문 | 연구 방향에 남긴 것 |
|---|---|---|
| 팩트체크 Agent | 검색하면 참거짓을 알 수 있을까요? | 주장·판정·근거를 분리하는 FEVER/AVeriTeC 틀 |
| 세 정보 경로 | 모델의 기존 답, given 근거, 새 검색이 다르면 무엇을 믿을까요? | 검색 없는 진단, 고정 corpus, 추가 검증의 비교 |
| 오염 근거 | 잘못된 문서를 주면 답이 얼마나 바뀔까요? | 문서 조건과 정답→오답 손상 분석 |
| Fixed-corpus RAG | 관련 문서 자체를 못 찾은 것과 찾고도 잘못 쓴 것을 어떻게 나눌까요? | retrieval 노출과 판정의 분리 |
| 충분성과 독립성 | 여러 문서가 같은 말을 하면 검증이 끝난 것일까요? | 출처 의존성·정보 부족·충돌에 따른 행동 분석 |
| 능동 검증 | 추가 검색이 회복을 돕는지, 다시 오도하는지 어떻게 볼까요? | 회복률과 손상률을 함께 측정 |
| 제어기 | 계속 검색할 가치가 있을 때만 행동하게 할 수 있을까요? | 프롬프트·규칙·학습 정책의 확장 후보 |

유사한 선행연구를 발견할 때마다 연구의 의미가 사라진 것이 아니라, **무엇을 이미 알고 있으며 어디를 더 명확히 관찰할지**가 구체화되었습니다. 중간 발표에서는 이 과정 자체가 Task 선택의 근거가 됩니다.

## 3. 세 정보 경로를 어떻게 다룰까요?

| 경로 | 관측할 수 있는 것 | 실험에서 맡는 역할 |
|---|---|---|
| Closed-book response | 외부 문서 없이 모델이 내놓은 답 | 모델의 기존 행동을 확인하는 기준선 |
| Retrieved given evidence | 고정 corpus에서 선택된 문서와 순위 | 우리가 통제하는 초기 근거 조건 |
| Actively fetched evidence | 도구로 새롭게 확보한 문서·출처·시점 | 추가 검증의 효과와 비용 |

모델이 어떤 사실을 ‘학습했는지’를 직접 확인하기보다, **같은 사실을 외부 근거 없이 안정적으로 맞히는가**를 조작적 기준으로 사용합니다. Dated Data와 Real Documents가 이 구분에 도움을 줍니다. 최신 주장이라는 이유만으로 모든 모델이 모른다고 단정하는 대신, 시점 정보와 실제 closed-book 응답을 함께 기록합니다.

정답 기준은 별도의 사람이 검수한 자료와 판정 규칙에 둡니다. 모델의 기억, 검색 결과의 다수 의견, 공식 사이트라는 이름 중 하나를 자동으로 정답으로 삼지 않습니다. 공식 자료도 대상 시점·단위·조건을 맞춰 읽습니다.

## 4. 현재 관심의 중심: 네 가지 초기 근거 조건

같은 원자적 주장(atomic claim)에 대해 근거 조건을 바꾸면, 주장 난이도 차이와 근거 효과를 더 잘 구분할 수 있습니다.

| 조건 | 예시 | 관찰할 행동 | 주요 실패 |
|---|---|---|---|
| Valid and sufficient | 설립일을 명시한 일관된 유효 자료 | 근거를 사용하고 적절히 종료 | 과잉 검색으로 정답 손상 |
| Missing decisive evidence | 활동 내용은 있지만 설립일이 없음 | 빠진 정보를 특정해 검색 | 관련성만으로 결론 |
| Conflicting evidence | 2010년과 2022년 자료가 함께 존재 | 시점·주체·출처 차이를 조사 | 다수결, 순서 편향 |
| Coherent but misleading evidence | 여러 문서가 같은 잘못된 설립일을 반복 | 독립적인 근거로 재검증 | 일치성을 진실성으로 오인 |

**수량과 출처는 다른 축입니다.** 원문 하나를 재인용한 문서 10개와 서로 독립적으로 확인한 문서 10개는 같은 근거량이 아닙니다. 오도 문서 1/5와 1/10의 비교도 문서 길이·관련성·정답 근거 수를 맞춰야 해석할 수 있습니다.

팀 초기에 이야기한 **진짜/가짜 주장 × 진짜/가짜 근거의 네 조합**도 유지합니다. 다만 지금 표와 같은 분류는 아닙니다. 앞의 축은 주장·문서의 진실성이고, 이 표는 Agent가 받는 근거의 구성입니다. 참인 문서가 거짓 주장을 반박할 수 있으며, 문서에 오류가 있어도 특정 주장을 판정하는 데 결정적이지 않을 수 있습니다. 데이터에는 `claim_label`, `document_validity`, `claim_evidence_relation`, `evidence_condition`을 나눠 기록하는 안이 적합합니다.

## 5. Task 확정 논의를 위한 공통 문안

> **Evidence-Grounded Fact Verification under Imperfect Retrieved Evidence**
>
> Given an atomic claim, a fixed document corpus, and access to external verification tools, an agent must retrieve and assess evidence, decide whether further verification is warranted, and return a verdict supported by sufficient, time-appropriate evidence under a bounded tool budget.

한국어로는 **“불완전한 검색 근거 아래에서 추가 검증 여부를 판단하고, 충분한 근거를 동반한 사실 판정을 수행하는 Task”**입니다. 여기서 입력·행동·출력은 다음과 같이 구체화합니다.

| 요소 | 현재 정리안 |
|---|---|
| 입력 | 정규화한 단일 주장, 주장 대상 시점, 접근 가능한 고정 corpus, 허용 도구와 예산 |
| 핵심 행동 | 관련 문서 검색, 정보 부족·충돌 확인, 추가 출처 탐색 여부와 종료 선택 |
| 출력 | Supported / Refuted / Not Enough Evidence, 인용 근거, 짧은 판정 이유, 필요하면 정정 사실 |
| 기록 | 검색 질의, 문서 ID·출처·시점, 도구 호출, 근거 채택/배제 사유의 짧은 요약, 비용, 실행 상태 |
| 성공 기준 | 올바른 판정과 충분하고 시점에 맞는 근거를 함께 제시 |

**‘무엇을 해결할지’가 Task이고, BM25·dense retrieval·프롬프트·규칙·RL은 방법 후보입니다.** 중간 발표에서 Task를 설명하기 위해 구현 방법을 모두 확정할 필요는 없습니다.

### PPT 뒤에 붙인 세 후보는 어떻게 다른가요?

| 후보 | 초점 | 주로 보는 평가 | 구현 부담 |
|---|---|---|---|
| A. Fact-checking under imperfect evidence | 네 근거 조건에서 검색·판정·추가 검증 비교 | Grounded Success, verdict quality, recovery / harm | 고정 corpus와 판정 기록을 먼저 구성하기 좋음 |
| B. Independent verification under false corroboration | 복제·재인용 출처를 독립 근거로 오인하는가 | Source independence, recovery, grounded verdict | 출처 관계를 사람이 검수하는 부담이 큼 |
| C. Selective verification under a search budget | 더 찾을 가치가 있는 사례에서만 검색하는가 | Quality–cost curve, recovery, unnecessary search | 제어 정책 비교와 비용 기록 필요; RL은 선택적 확장 |

A를 공통 Task 틀로 놓고 B·C 중 하나를 핵심 연구 질문으로 좁히는 구성이 가능합니다. 세 후보 모두를 별도 프로젝트처럼 끝까지 구현하는 구조로 읽을 필요는 없습니다.

## 6. 비교 조건: 무엇을 바꾸고 무엇을 고정할까요?

아래 C0–C2는 **이 문서의 비교 이름 제안**입니다. 기존 팀 평가 문서의 B0–B2와 다른 목적의 번호이므로 함께 설명합니다.

| 조건 | 접근 정보·정책 | 주된 질문 |
|---|---|---|
| C0 · Closed-book | 동일 주장, 외부 문서·도구 없음 | 모델은 처음에 어떤 판정을 하나요? |
| C1 · Fixed-corpus RAG | 고정 corpus를 검색하여 판정 | 초기 근거 조건이 검색과 판정을 어떻게 바꾸나요? |
| C2 · Active verification | C1과 같은 시작점 + 추가 검증 도구 | 추가 검증이 회복·손상·비용을 어떻게 바꾸나요? |

이 비교만으로 ‘Agent의 판단 덕분’이라고 결론 내리면 정보량 증가 효과와 섞입니다. 그래서 **C2 안에서 고정 검색 절차와 적응형 정책을 같은 모델·도구·최대 예산으로 비교**하면 좋습니다. 이는 팀원의 기존 B1 고정 workflow / B2 적응형 Agent 비교와 연결됩니다.

초기 관심은 C1의 문서 구성에 있습니다. 다만 판정 단계만 보고 싶을 때는 **같은 근거 묶음을 직접 제공하는 진단 실험**을, 검색까지 보려면 **공통 corpus에서 실제로 찾게 하는 실험**을 구분해 둡니다. Corpus 오염 비율과 top-k 결과에 실제 노출된 오염 비율을 각각 기록하면 retrieval 실패가 연구 주제를 가리는 대신 설명 변수가 됩니다.

검색 정책을 비교할 때 retriever를 고정하고, BM25 대 dense 비교를 할 때 정책·생성기를 고정하는 식으로 한 번에 바꾸는 축을 제한하는 구성이 해석하기 쉽습니다.

## 7. 팀원 50개 자료를 어떻게 살릴까요?

현재 저장소에서 확인한 팀원 기여는 **HeonSu의 `c2dbe3b` 커밋**, `evaluation.md` §9의 실제 글 기반 50개입니다. 문서 50개·선정 주장 50개·분할 그룹 47개이며, 기사/정보글 37개, Threads 9개, X 4개입니다. 원 자료와 정규화한 주장, 참조 근거, 사례별 평가 포인트가 연구의 출발 자산입니다. [팀원 평가 자료](../evaluation.md) · [해당 커밋](https://github.com/CJI0718/uos-nlp-2026-team5/commit/c2dbe3b)

| 묶음 | 활용 방향 | 원 자료에 추가할 기록 |
|---|---|---|
| 최신·시점 민감 주장 | 외부 자료가 판정에 중요한 사례 | 발표일·대상 기간·허용 근거 시점·closed-book 응답 |
| 수치·단위·조건 주장 | 근거 비교와 결정적 오류 설명 | 원 수치, 단위, 분모, 조건, 계산 정답 |
| 안정적 사실 | 모델의 기존 응답과 주어진 근거 충돌 관찰 | 반복 closed-book 결과; 필요하면 FEVER 일부 보충 |
| 동일 사건·유사 사례 | group 단위 분할과 paired 분석 | 원 ID 유지, 동일 사건 그룹, 변형 부모 ID |

모든 기존 자료를 버리고 새 benchmark로 바꾸기보다 **원 ID를 유지하고 적합성 태그를 붙인 뒤 일부를 보충·교체하는 안**이 좋습니다. FEVER를 쓸 경우에도 고정된 사실이라는 이유만으로 모델이 알고 있다고 간주하지 않고 실제 응답을 확인합니다.

근거 변형은 원본과 별도 버전으로 저장합니다. 예를 들어 원 주장 하나에 clean/missing/conflict/misleading 네 조건을 만들더라도 **서로 독립인 주장 네 개가 된 것은 아닙니다.** 핵심 50개와 조건별 실행 수를 따로 집계합니다. 팀원 자료의 47개 그룹 정보는 개발·평가 누출과 오차 추정에 그대로 활용할 수 있습니다.

## 8. 평가 초안: 결과·행동·비용을 연결합니다

팀원 문서의 정확성·근거 적절성·오류 설명·비용 지표를 바탕으로 다음과 같이 정리합니다. 영어 명칭은 발표 화면과 실험표에서 공통으로 사용하기 좋습니다.

| Metric | 정의 또는 계산 | 이 Task에 어울리는 이유 |
|---|---|---|
| Verdict Accuracy / Macro-F1 | gold verdict와 비교; label별 결과 함께 보고 | 라벨 불균형과 기본 사실 판정 성능 |
| Grounded Success Rate (GSR) | 올바른 verdict **AND** 충분한 근거 **AND** 시점 정합 / 전체 시도 | 맞는 답만 찍는 경우와 근거를 갖춘 검증 구별 |
| Recovery Rate | C1 오답 중 C2가 정답으로 바꾼 수 / C1 오답 수 | 잘못된 근거를 받은 후의 교정 |
| Harm Rate | C1 정답 중 C2가 오답으로 바꾼 수 / C1 정답 수 | 추가 검색의 역효과 |
| Evidence Recall@k | 검수한 필요 근거 집합 중 top-k가 회수한 비율 | 고정 corpus에서 검색 실패 구분 |
| Misleading Exposure Rate | 오도 문서를 한 개 이상 받은 사례 / 전체 사례 | corpus 오염이 실제 모델 입력까지 도달했는지 |
| Verification / Recovery Transition | 검색 발동 → 독립 근거 확보 → 판정 교정의 단계별 비율 | 검색했지만 회복 못한 원인 분리 |
| Tool / Token / Time Cost | 검색·fetch·LLM 횟수, 토큰, wall time | 같은 정확도에서 필요한 자원 비교 |
| Execution Failure Rate | timeout·파싱 오류 등 / 전체 시도 | 시스템 실패를 사실 판정 실패와 구분 |

Recovery/Harm은 먼저 **verdict 기준**으로 계산하고, 같은 전이를 **grounded success 기준**으로도 나눠 보고할 수 있습니다. 분모가 0이면 0%가 아니라 N/A로 표시합니다. 출처 독립성을 주제로 고르면 ‘URL 개수’ 대신 원자료 계보·재인용 관계를 검수합니다.

오류 설명은 팀원 제안대로 **문제 위치 → 오류 이유 → 정정 내용**의 세 항목을 봅니다. 정답 판정이어도 인용이 잘못되거나 설명이 새 오류를 만들 수 있으므로 이를 별도로 확인합니다.

비용은 임의 가중합 하나만 보고하기보다 **품질–비용 곡선(Quality–Cost Curve)**과 같은 예산에서의 성공률을 먼저 제시하면 좋습니다. 비용 계수를 둔 reward나 utility는 추가 선택입니다.

## 9. 선행연구를 발표에서 어떻게 묶을까요?

| 논문의 역할 | 함께 읽을 연구 | 우리가 가져가는 논지 |
|---|---|---|
| 기본 구조 | RAG, ReAct, FEVER, AVeriTeC | retrieval·action·claim·evidence·verdict 정의 |
| 연구 설계의 안전장치 | Dated Data, Real Documents, ClaimDecomp, Decomposition Dilemmas, ALCE, Ev2R | 기존 지식의 관측, 평가 단위, 근거 채점 |
| 오염 조건의 설계 | VitaminC, FaithEval, HAE-GEO, Fact2Fiction, Evidence Laundering | 국소 수정, 맥락 조건, 공격 구조, 출처 상관 |
| 가장 가까운 비교 | Flip Risk, RAGuard, DRNoise, ClashEval, Adaptive Chameleon | 비율·순서·자연 오도·검색 실패·판정 손상 |
| 교정과 행동 | CRITIC, Astute RAG, CRAG, Self-RAG, FIRE, ClaimCLAIRE | 외부 feedback, 근거 통합, 검색 발동과 종료 |
| 효율과 확장 | Sufficient Context, Search Wisely, BeliefRAG, Stop-RAG | 충분성, 검색 가치, 상태와 제어 정책 |

한 논문은 설계 참고와 가설의 출발점을 동시에 맡을 수 있습니다. 예를 들어 FIRE는 도구·종료 설계의 참고인 동시에 충분성과 비용에 관한 연구 질문을 만들어 줍니다. 위 표는 우열·배타적 분류가 아니라 발표에서의 역할입니다.

**차별성을 말할 때의 중심:** 외부 검색 자체의 새로움보다, **초기 근거 조건을 통제하면서 검색 노출 → 검증 발동 → 독립 근거 확보 → 회복/손상을 연결해 분석하는 구성**을 제시합니다. RAGuard의 CRAG 웹 검색 결과를 포함한 가까운 논문을 정면으로 비교하면 이 주장이 더 설득력 있습니다.

## 10. 중간 발표의 구성과 팀 논의 순서

PPTX 앞 15장은 논문 캡처를 주제별로 묶었습니다. 뒤의 16–18장은 A/B/C Task 후보입니다. 이 18장 파일은 토론·편집용이며, 실제 발표에 사용할 Task 슬라이드는 팀 논의 후 선택하는 구조입니다.

1. **Task A/B/C의 초점 선택:** 네 조건 전반, 출처 독립성, 비용 대비 선택적 검증 중 주 질문을 정합니다.
2. **평가 단위 확인:** 원자적 주장과 근거를 동반한 판정이 팀원의 50개 자료를 어떻게 이어받는지 확인합니다.
3. **비교의 목적 확인:** C0/C1/C2는 정보 접근의 차이, 고정 workflow/적응형 Agent는 정책의 차이라는 점을 합의합니다.
4. **중간 발표에서 받을 피드백:** 창의성을 조건 통제·행동 진단·회복 분석의 결합으로 제시해도 충분한지, 무엇을 줄이면 명확해지는지 질문합니다.

그다음 작은 개발용 사례에서 도구·기록 형식을 확인하고, 평가 자료 검수를 거쳐 비교 범위를 고정하는 순서가 자연스럽습니다. 역할 분담은 자료·실험·평가/발표라는 작업 단위를 기준으로 세 사람이 조정할 수 있습니다.

## 11. 범위·출처·현재 결정 상태

이 문서는 **기사·뉴스·주장을 검증하는 Agent라는 팀의 큰 방향** 위에, 이후 대화에서 발전한 연구 질문을 팀 논의용으로 정리한 것입니다. Task 공통 문안과 A/B/C 후보는 **확정 논의를 위한 안**이며, 세부 방법·RL 도입·모델·예산이 팀 전체에서 합의되었다는 기록은 아닙니다. 현재 결과표는 선행연구의 결과이고 우리 팀의 실험 결과는 없습니다.

팀원의 실제 50개 자료는 **지지 37·반박 11·NEI 후보 1·판정 보류 1**이며 독립 검수 전 초안입니다. 보류는 네 번째 사실 라벨이 아닙니다. 50개 문서와 47개 분할 그룹의 차이, 접근·시점·정답 검수 상태는 기존 `evaluation.md`를 기준으로 이어갑니다. 이 문서는 그 자료를 덮어쓰거나 새로운 실험 성과로 표시하지 않습니다.

이번 정리 시점에 원격 main과 `docs/factcheck-details`를 대조했고, 반영 기준 커밋은 `c2dbe3b`, 문헌 가이드 기준 main은 `6a67e0c`입니다. 이후 팀원 변경은 별도 갱신으로 이어가면 됩니다.

라이브 웹 검색은 결과가 바뀔 수 있으므로 허용된 범위의 snapshot·시점·해시·도구 결과를 기록하고, 고정 재생 실험과 실제 웹 실행을 구분하는 것이 좋습니다. 처음부터 모든 오염 축·모델·retriever·정책을 조합하는 대신 주 질문 하나를 기준으로 비교 범위를 정합니다. RL은 trajectory 수집·reward 검수·별도 학습 자료 비용까지 포함해 선택합니다.
