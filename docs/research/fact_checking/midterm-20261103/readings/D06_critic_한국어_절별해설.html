먼저 붙잡을 질문

모델이 자기 글을 비평할 때 외부 도구는 어떤 새로운 정보를 주나요?

왜 선택했나 — 외부 도구를 이용한 자기교정의 기본 비교 기준. 잘못된 결과를 낸 모델에게 다시 생각하라고만 하는 대신, 검색·코드 실행 등 관측 가능한 피드백을 이용해 출력을 검증하고 고친다. 우리 연구의 ‘fetch해서 교정한다’는 아이디어에 대한 직접적인 선행연구다.

논문의 논증을 먼저 따라가기

첫 답을 생성하는 능력과 그 답을 확인하는 능력은 다를 수 있다. CRITIC은 먼저 일반적인 방식으로 답을 만들고, 어떤 부분을 검사할지 모델이 비평하는 과정에 외부 도구를 넣는다. 그때 얻은 관찰과 비평을 원래 질문·답과 함께 다음 입력으로 주어 수정한다. 초기화부터 다시 풀 때와 달리 무엇을 확인해서 어디를 고쳤는지 한 회차씩 추적할 수 있다.

과제에 따라 새 정보의 성격이 다르다. 개방형 QA에서는 검색한 자료가 사실 확인의 근거이고, 수학 프로그램에서는 코드를 실행한 결과가 출력이나 오류를 보여주며, 유해 표현 감소 과제에서는 외부 평가 도구의 피드백을 받는다. §4는 과제별 결과와 도구 없이 비평한 조건을 비교한다. 도구가 존재한다는 설명만으로는 한 번 더 생성한 효과와 실제 피드백의 효과를 구별할 수 없기 때문이다.

결과표의 별표 조건은 특히 주의해서 읽어야 한다. 이미 정답인 항목을 알 수 있어 그 항목을 수정 대상에서 제외하면 정답 훼손 위험이 사라진다. 일반 CRITIC은 그 유리한 정보를 갖지 않는다. 우리 과제에서도 모든 비교 정책에 같은 출발 답을 주고, 어느 답이 틀렸는지는 평가자만 보아야 교정률과 보존율을 모두 해석할 수 있다.

§§1–2, Figure 1 · 첫 답을 검토할 근거를 어디서 얻나

PDF pp. 1–4

처음 생성한 답을 읽고 비평문을 쓰는 것만으로는 처음 오류를 반복할 수 있습니다. CRITIC은 외부 도구의 반환값으로 초기 답을 점검하고, 구체적인 비평에 따라 수정합니다. 각 과제에서 의미 있는 도구가 무엇인지는 달라집니다.

§3 · 생성·검증·수정의 한 번의 순환

PDF pp. 4–5

질문과 초기 답을 넣고 도구를 호출해 사실이나 실행 결과를 확인합니다. 모델은 그 관찰이 기존 답에 주는 피드백을 쓰고 다음 답을 만듭니다. 같은 모델을 사용하더라도 전 단계 이후 관찰이 추가됐으므로 정보 조건은 달라집니다.

§§4.1–4.3 · 서로 다른 세 과제에서 도구의 역할

PDF pp. 5–8

자유형 QA에는 검색 결과가, 수학 프로그램에는 실행 결과가, 독성 감소에는 콘텐츠 평가 신호가 쓰입니다. 프로그램이 실제로 어떤 값을 내는지는 검사할 수 있지만, 검색된 문장의 진위는 별도 검토가 필요합니다. 모든 도구가 동일하게 신뢰할 만한 정답 판별기는 아닙니다.

§4.4 · 별표와 도구 제거 비교를 읽기

PDF pp. 8–9

도구를 빼거나 반복 단계를 바꾸어 관찰의 역할을 점검합니다. CRITIC*처럼 정답인 항목의 수정을 건너뛰는 oracle 조건은 실행 전 정오를 모르는 일반 모델보다 유리합니다. 어떤 열이 실제 정책이고 어떤 열이 성능 상한을 보여주는지 분리하세요.

§5 · 우리 C2의 외부 관찰이 제 역할을 했는지

PDF p. 9

추가 검색 후 오류를 바꿨다면 새 문서에서 어떤 결정적 사실을 얻었는지 남깁니다. 검색해도 같은 오보를 되풀이하는 페이지가 나올 수 있습니다. 호출 발생과 근거 개선을 별개로 기록할 이유입니다.

논문 결과와 우리 설계의 경계

원문에서 보고한 결과. 논문은 여러 QA·프로그램·독성 감소 실험에서 개선을 보고하며 도구 제거 조건의 효과는 작거나 불안정하다고 분석한다. 반복 수정의 추가 이득도 점차 줄어든다.

우리 연구로 가져올 부분. 같은 초기 응답에서 도구 확인 정책만 달리하고, 정답 여부는 에이전트에게 알려주지 않는다. 표를 사용할 때 기본 답·일반 교정·oracle 교정을 함께 보여준다. 우리는 찾아온 피드백 자체가 오도될 수 있는 조건까지 추가하여 근거 검증과 전이를 연결한다.

팀에서 풀어 볼 질문. C2가 오답을 고쳤을 때 새 근거를 읽고 고친 경우와 같은 모델에게 다시 물었더니 고친 경우를 어떻게 구분할까요?

CRITIC의 feedback은 정확히 무엇인가요?

30초 답변: “도구와 상호작용하여 기존 출력을 확인하고 critique를 만든 뒤, 그 지적을 바탕으로 답을 고치는 과정입니다.”

풀어서 설명: Figure 1의 외부 도구는 knowledge base, code interpreter, text API 같은 검증 자원입니다. Verify → critique → correct를 반복합니다. CRITIC은 논문·방법 이름이며, 이를 RL의 actor–critic에서 말하는 가치함수 critic과 자동으로 동일시하면 안 됩니다.

연구 연결: 도구 결과 자체도 틀릴 수 있으므로 검색 호출 성공과 교정 성공을 나눕니다. 질문에 관련 없는 결과를 가져온 경우, 잘못된 자료를 재확인한 경우도 분석 대상입니다.
