# 검색이 잘못됐을 때, 어떻게 고칠 것인가?

**Corrective Retrieval Augmented Generation — CRAG**
Shi-Qi Yan · Jia-Chen Gu · Yun Zhu · Zhen-Hua Ling · 2024 · arXiv v3(2024-10-07) 기준

CRAG는 검색기가 가져온 자료를 그대로 생성 모델에 넘기기 전에 **검색 결과를 평가하고, 정제하거나 웹 검색으로 보완하는 구조**입니다. 우리의 “근거가 부족하거나 의심스러울 때 추가로 조사한다”는 방향을 구현 관점에서 이해하는 데 중요합니다.

[원문 PDF](https://arxiv.org/pdf/2401.15884v3) · [공식 코드](https://github.com/HuskyInSalt/CRAG) · [연구 방향과 문헌 지도](연구방향_문헌지도.html) · [먼저 읽기: Flip Risk](Flip_Risk_한국어_절별해설.html)

## 1. 먼저 5분: CRAG는 어디에 끼어드는가

일반 RAG를 단순화하면 **질문 → 문서 검색 → 질문과 검색 문서를 넣어 답 생성**입니다. 검색 결과가 엉뚱해도 마지막 생성 모델은 그 문서에서 답을 만들라는 압력을 받습니다.

CRAG는 검색과 생성 사이에 **평가와 수정**을 넣습니다.

<div class="flow"><span>질문 + 검색 문서</span><b>→</b><span>관련성 평가</span><b>→</b><span>정제 / 웹 보완 / 둘 다</span><b>→</b><span>답 생성</span></div>

**해설용 예시:** “A기관의 설립연도는?”을 물었는데 검색기는 이름이 비슷한 B기관의 문서를 가져옵니다. CRAG는 이 자료의 관련성이 낮다고 평가하고 검색어를 다시 구성해 웹에서 A기관 자료를 찾습니다. 반대로 A기관 연혁이 충분히 검색되었다면 관련 부분만 추려 답합니다.

이 구조를 읽을 때 **검색 결과가 질문에 관련 있는가**와 **그 내용이 사실인가**를 구분해야 합니다. “A기관은 2022년에 설립됐다”는 매우 관련성 높은 거짓 문서도 있을 수 있습니다. 이 차이가 우리의 오염 근거 실험과 연결되는 핵심입니다.

## 2. Introduction·Related Work: 왜 검색 후 평가가 필요한가

[원문 PDF pp. 1–3, §1–2](https://arxiv.org/pdf/2401.15884v3#page=1)

저자들은 RAG의 장점을 인정하면서, 검색 실패가 생성 실패로 곧바로 이어지는 결합 구조를 문제 삼습니다. 모델의 파라미터 지식이 부족해서 외부 지식을 가져왔는데, 외부 지식이 부적절하면 RAG가 오히려 오류를 강화할 수 있다는 것입니다.

Self-RAG 같은 접근은 검색 필요 여부나 생성 과정의 자기평가를 다룹니다. CRAG는 그중 **이미 가져온 검색 결과가 유용한지 점검하고 수정하는 단계**에 집중합니다. 생성 모델이 특수한 자기평가 토큰을 출력하도록 반드시 학습시키지 않아도, 앞단의 평가·수정 절차를 붙일 수 있도록 설계합니다.

논문의 제목에 “Corrective”가 들어간 이유는 자료를 더 많이 검색하는 것만으로 끝나지 않기 때문입니다. 현재 결과가 어떤 상태인지에 따라 **기존 자료의 정제, 외부 자료로 대체, 양쪽 결합**을 다르게 선택합니다.

우리 발표에서는 이 부분을 “검색했으니 근거가 확보됐다”라는 단순 연결을 끊는 선행연구로 소개할 수 있습니다. 이어서 “그런데 관련성이 높은 거짓 자료도 이 평가를 통과할 수 있지 않은가?”라는 연구 질문으로 이동할 수 있습니다.

## 3. Task Formulation: corpus와 top-k를 분리하기

[원문 PDF p. 3, §3](https://arxiv.org/pdf/2401.15884v3#page=3)

입력 X, 접근 가능한 문서 집합 C, 검색기 R, 생성기 G가 있습니다. 검색기는 C 전체에서 X와 관련된 상위 문서 D를 고르고, 생성기는 X와 D를 바탕으로 출력 Y를 만듭니다.

| 기호 | 쉬운 표현 | 우리 실험에서 바꿀 수 있는 것 |
|---|---|---|
| C | 검색 대상 전체 저장소 | 오염 문서 삽입, 출처 구성 |
| D | 실제로 검색된 top-k | 순위·문서 수·관측 오염 비율 |
| G | 근거를 받아 답하는 모델 | 동일 모델 고정, 판단 정책 비교 |
| Y | 최종 출력 | 주장 라벨·근거·설명 |

저장소 C의 20%가 거짓이어도 D의 거짓 비율이 20%인 것은 아닙니다. 검색기가 특정 유형을 집중적으로 고를 수 있기 때문입니다. 우리는 **저장소 조작 → 실제 선택된 근거 → 최초 판정 → 추가 조사 → 최종 판정**을 구분해서 기록할 수 있습니다.

논문 §3의 수식은 검색과 생성이 이어진다는 큰 틀을 표현합니다. 일반적인 잠재 문서 주변화 확률 모형의 엄밀한 유도와는 구분해서 읽고, 여기서는 실제 알고리즘의 입력과 출력에 집중하는 것이 좋습니다.

## 4. Overview: Figure 2와 Algorithm 1을 따라가기

[원문 PDF pp. 3–5, §4.1–4.3](https://arxiv.org/pdf/2401.15884v3#page=4)

<!-- FIGURE:crag_arch -->

먼저 질문과 검색 문서를 하나씩 짝지어 평가합니다. 문서별 점수를 모아 전체 검색 결과를 세 상태 중 하나로 분류합니다. 그 상태에 따라 근거를 가공한 뒤 마지막에 생성 모델이 답을 만듭니다.

| 상태 | 원문의 발동 조건 | 다음 동작 |
|---|---|---|
| Correct | 문서 중 **하나라도** 점수가 상한보다 높음 | 기존 문서를 세부 구간으로 정제 |
| Incorrect | **모든** 문서 점수가 하한보다 낮음 | 기존 검색 결과 대신 웹 근거 사용 |
| Ambiguous | 위 두 경우에 해당하지 않음 | 기존 자료 정제 + 웹 근거 결합 |

이 규칙은 “신뢰할 만한 문서의 비율이 50%를 넘는가”라는 다수결이 아닙니다. **높은 점수의 문서가 하나라도 있는지**가 중요합니다. 또한 Ambiguous가 곧 “두 문서의 사실 내용이 모순된다”는 뜻도 아닙니다. 평가 점수로 명확한 양끝 상태를 정하기 어려울 때의 분기입니다.

**우리 연구와의 연결:** 잘못된 문서가 질문과 매우 관련 있어 높은 점수를 받으면, 어떤 행동이 발동할까요? 이 질문은 CRAG가 반드시 실패한다는 결론이 아니라, 관련성 중심 정책을 우리 조건에서 시험할 이유입니다.

## 5. Retrieval Evaluator: 무엇을 학습하고 무엇을 점수화하는가

[원문 PDF pp. 3–4, §4.2 / p. 15, 부록 B.3](https://arxiv.org/pdf/2401.15884v3#page=4)

평가기는 T5-large(약 0.77B)를 미세조정한 모델입니다. 입력은 질문과 문서의 쌍이며, 점수는 관련성을 나타냅니다. 논문은 일반적으로 질문마다 문서 10개를 검색해 개별적으로 평가한다고 설명합니다.

학습 신호는 기존 데이터에서 얻습니다. PopQA가 제공하는 정답 관련 Wikipedia 제목으로 고품질 관련 문서를 추적하고, 검색 결과 중 관련 없는 문서들을 음성 사례로 사용합니다. 부록에서는 PopQA 약 14k 중 Self-RAG와 같은 테스트 1,399개를 제외한 나머지를 미세조정에 활용했다고 설명합니다. 이 평가기를 Bio·PubHealth·ARC에도 옮겨 사용합니다.

양성/음성 학습 라벨은 1과 −1이고, 추론 점수 범위는 −1~1입니다. **이 점수가 0.8이라는 이유로 해당 문장이 참일 확률 80%라고 읽으면 안 됩니다.**

| 대상 | 상한 | 하한 |
|---|---:|---:|
| PopQA | 0.59 | −0.99 |
| PubHealth·ARC | 0.50 | −0.91 |
| Biography | 0.95 | −0.91 |

이 값들은 부록에 제시된 경험적 설정입니다. 모든 분야에 그대로 적용되는 보편적 참·거짓 임계값이 아닙니다. 본문의 명칭은 PubHealth이고, 부록의 해당 문장에는 PubQA라는 표기가 나타납니다.

**학습 여부를 분리해 읽기:** 생성기 자체에 새로운 자기평가 토큰 학습을 요구하지 않는다는 것과, 시스템 전체가 학습을 전혀 하지 않는다는 것은 다릅니다. CRAG의 평가기는 명시적으로 미세조정됩니다. 우리가 학습 없이 LLM 프롬프트로 비슷한 분기를 구현하면 “CRAG에서 영감을 받은 정책”이지 논문의 원형을 그대로 재현한 것은 아닙니다.

## 6. Knowledge Refinement와 Web Search: 실제 자료가 이동하는 과정

[원문 PDF pp. 5–6, §4.4–4.5](https://arxiv.org/pdf/2401.15884v3#page=5)

<!-- FIGURE:crag_method -->

### 6.1 Knowledge strips는 무엇인가

문서 전체를 그대로 쓰지 않고 몇 문장 정도의 정보 단위로 나눕니다. 이미 한두 문장인 자료는 하나의 구간으로 취급할 수 있습니다. 같은 평가기로 구간의 관련성을 점수화하고, 관련 없는 구간을 걸러 남은 것을 이어 붙입니다.

이는 주장 목록을 논리적 원자 사실로 엄밀히 분해하는 절차와 같지는 않습니다. 여기서는 주로 **답에 필요한 문서 부분을 추리는 작업**입니다. 부록은 구간 선택의 top-k를 5, 필터 임계값을 −0.5로 명시합니다.

### 6.2 Internal knowledge라는 표현의 함정

Algorithm 1의 Internal_Knowledge는 **초기 검색 문서에서 정제해 얻은 내용**입니다. Astute RAG에서 모델이 생성한 내부지식 passage나, 우리가 C0로 측정하는 무근거 응답과 같은 뜻이 아닙니다.

| 표현 | 이 문서에서의 의미 |
|---|---|
| CRAG internal knowledge | 초기 corpus 검색 결과를 정제한 텍스트 |
| CRAG external knowledge | 추가 웹 검색으로 확보하고 정제한 텍스트 |
| 우리의 C0 response | 외부 문서를 제공하지 않은 모델 응답 |

### 6.3 웹 검색은 어떻게 하는가

입력 질문을 ChatGPT로 검색 키워드 중심 질의로 다시 쓰고, Google Search API로 URL을 찾습니다. 페이지 내용을 가져온 뒤 같은 정제 과정을 적용합니다. 논문은 Wikipedia 같은 비교적 관리되는 출처를 선호한다고 설명합니다.

Incorrect에서는 이 웹 근거가 기존 자료를 대신하고, Ambiguous에서는 기존 근거와 결합됩니다. **원문의 알고리즘은 세 분기를 가진 평가·보완 절차**입니다. 임의의 도구를 매 단계 선택하며 장시간 조사하는 범용 ReAct 루프와 동일하지 않습니다.

## 7. Experiments: 무엇을 평가했는가

[원문 PDF pp. 6–8, §5.1–5.3](https://arxiv.org/pdf/2401.15884v3#page=7)

<!-- FIGURE:crag_results -->

| 데이터셋 | 문제 유형 | 논문의 지표 |
|---|---|---|
| PopQA | 짧은 사실 질문 | Accuracy |
| Biography | 인물 소개 장문 생성 | FactScore |
| PubHealth | 참·거짓 판정 | Accuracy |
| ARC-Challenge | 객관식 지식·추론 문제 | Accuracy |

따라서 CRAG를 “생성만 하고 팩트체크와 전혀 상관없는 연구”라고 분리하면 지나칩니다. PubHealth도 포함되어 있습니다. 다만 **우리가 제안한 사실 오류 비율·출처 독립성·능동 회복을 교차해 보는 실험**과는 다른 평가입니다.

기본 검색 결과는 Self-RAG에서 제공한 Contriever 결과를 사용해 비교합니다. CRAG는 일반 RAG에 수정 절차를 붙인 것이고, Self-CRAG는 Self-RAG와 결합한 것입니다. 생성기 역시 일반 LLaMA2와 Self-RAG용으로 학습된 LLaMA2를 나눠 비교합니다.

### 7.1 Table 1: 같은 생성기를 고정하고 읽기

아래는 **SelfRAG-LLaMA2-7b를 생성기로 사용한** 원문 Table 1의 수치입니다. 모두 논문 보고 점수입니다.

| 방법 | PopQA Accuracy | Biography FactScore | PubHealth Accuracy | ARC Accuracy |
|---|---:|---:|---:|---:|
| RAG | 52.8 | 59.2 | 39.0 | 53.2 |
| CRAG | 59.8 | 74.1 | 75.6 | 68.6 |
| Self-RAG | 54.9 | 81.2 | 72.4 | 67.3 |
| Self-CRAG | 61.8 | 86.2 | 74.8 | 67.2 |

RAG→CRAG의 PopQA 변화는 52.8→59.8, **7.0%포인트**입니다. PubHealth에서는 36.6%포인트입니다. 같은 생성기 조건 안에서 비교해야 다른 모델의 능력 차이와 섞이지 않습니다.

또한 모든 칸에서 Self-CRAG가 최고는 아닙니다. ARC에서는 CRAG 68.6이 Self-CRAG 67.2보다 높고, Self-RAG 67.3과 Self-CRAG 67.2의 차이도 있습니다. “복잡한 방법일수록 모든 태스크에서 좋아진다”는 읽기는 피해야 합니다.

원문 Table 1에는 직접 재실행한 결과와 선행연구에서 인용한 결과가 함께 있습니다. 별표와 생성기별 구획을 먼저 확인하면 서로 다른 실험을 한 줄의 순위로 읽는 오류를 줄일 수 있습니다.

## 8. Ablation·Robustness·Cost: 성능 향상은 어디서 오는가

[원문 PDF pp. 8–10, §5.4–5.8](https://arxiv.org/pdf/2401.15884v3#page=9)

### 8.1 분기를 제거하면 어떻게 되는가

Correct 또는 Incorrect를 제거할 때는 그 경우를 Ambiguous로 합칩니다. Ambiguous를 제거할 때는 하나의 임계값으로 양분합니다. 단순히 해당 조건의 문제들을 평가에서 빼는 것이 아닙니다.

PopQA에서 SelfRAG-LLaMA2-7b 기반 CRAG는 59.8이며, Correct 제거 58.3, Incorrect 제거 59.5, Ambiguous 제거 59.0입니다. 이 결과는 세 분기를 구분할 실험적 동기를 줍니다.

### 8.2 검색만 잘하면 끝일까

문서 정제, 질의 재작성, 웹 자료 선택을 각각 제거하면 성능이 떨어집니다. 같은 생성기 조건에서 정제 제거는 59.8→54.2, 질의 재작성 제거는 59.8→56.2, 웹 자료 선택 제거는 59.8→58.6입니다.

따라서 추가 자료가 존재하는 것뿐 아니라, **질문에 맞게 찾고 필요한 내용을 정리하는 과정**이 함께 기여합니다.

### 8.3 평가기의 정확도

PopQA의 검색 결과 품질 평가에서 T5 기반 평가기 84.3, ChatGPT 58.0, ChatGPT-CoT 62.4, ChatGPT-few-shot 64.7을 보고합니다. 이것은 **검색 품질 평가 과제의 정확도**입니다. T5가 일반적인 세계 지식의 참·거짓 판정에서 ChatGPT보다 우월하다는 실험이 아닙니다.

### 8.4 “검색이 나빠짐”을 어떻게 만들었는가

§5.6은 정확한 검색 결과 일부를 무작위로 제거해 검색 성능 저하를 모사합니다. Self-CRAG는 Self-RAG보다 생성 성능이 덜 감소합니다.

이 조작은 우리의 핵심 조건과 구분됩니다. **유효한 근거를 없애는 것**과 **관련성은 높지만 사실이 틀린 근거를 넣는 것**은 같은 실패가 아닙니다. 전자는 부족을 만들고, 후자는 자신 있게 틀릴 이유를 제공할 수 있습니다.

### 8.5 항상 웹 자료를 더하면 충분하지 않을까

이 의문은 CRAG 논문도 직접 다룹니다. §5.7, Table 5에서 같은 범위의 웹 근거를 RAG와 Self-RAG에도 제공해 비교합니다. SelfRAG-LLaMA2-7b 생성기의 PopQA 결과는 RAG 52.8, RAG + web 53.8, CRAG 59.8입니다.

이 비교는 우리의 항상 검색 비교군과 연결됩니다. 다만 이 표 하나가 모든 호출 예산을 정확히 일치시킨 비용 효율 실험을 뜻하지는 않습니다. 저자들은 수정 절차의 기여를 지지하는 결과로 해석합니다.

### 8.6 비용 수치를 그대로 가져와도 될까

Table 6의 RAG 0.363초, CRAG 0.512초 등은 **생성 단계의 대략적 비용 추정**이며 검색·데이터 처리 시간을 제외합니다. 따라서 “CRAG의 웹 검색까지 포함해 반초면 끝난다”고 읽으면 안 됩니다.

우리의 비용에는 검색 API, 페이지 fetch, 내용 평가, 최종 판정, 전체 지연을 포함하는 편이 맞습니다. 논문의 측정 범위를 정확히 읽는 것이 새로운 metric을 많이 만드는 것보다 중요합니다.

## 9. 우리 연구에 어떻게 적용할 것인가

CRAG에서 가장 먼저 가져올 것은 “현재 근거를 평가한 후 다음 행동을 정한다”는 구조입니다. 반면 평가의 대상을 관련성에서 더 세분화할 수 있습니다.

| 점검 대상 | 에이전트에게 묻는 질문 |
|---|---|
| 관련성 | 이 문서는 같은 기관·시점·사실을 다루는가 |
| 충분성 | 판정에 필요한 결정적 정보가 실제로 있는가 |
| 충돌 | 같은 사실에 대해 서로 양립하기 어려운 값을 말하는가 |
| 출처 독립성 | 여러 문서가 하나의 원문을 반복하는가 |
| 확인 행동 | 현재 자료로 해결할 수 있는가, 어떤 원문을 더 확인해야 하는가 |

이것들을 모두 학습 모델로 구현할 필요는 없습니다. 우선 동일한 기반 모델을 사용해, 무검색 판정·관련성 중심 보완·충돌 단서 중심 보완을 작은 파일럿으로 비교할 수 있습니다. 여기서 관련성 중심 보완은 원형 CRAG와 구현이 다르면 그 차이를 명시합니다.

**우리 연구의 한 문장 연결:** “CRAG가 검색 실패 이후의 보완 구조를 보여준다면, 우리는 관련성 높은 오도 근거와 출처 중복이 있는 조건에서 조사 발동과 판정 회복을 평가한다.”

## 10. 해석의 범위·확인 상태·남은 점

이 해설은 arXiv 2401.15884v3의 16페이지 PDF와 HTML, 공식 코드 저장소 설명을 대조했습니다. 주요 방법·표·부록 B.3을 확인했고 원본 PDF를 함께 보관했습니다. 코드를 실행하거나 논문 결과를 재현한 문서는 아닙니다.

CRAG는 Corrective Retrieval Augmented Generation을 뜻합니다. 동명의 Comprehensive RAG Benchmark와 다른 연구입니다. Internal Knowledge, Correct, Ambiguous는 일상적 뜻이나 다른 논문의 용어와 혼동하기 쉬우므로 본문에서 정의를 명시했습니다.

관련성 점수가 사실성을 보장하지 않는다는 설명은 우리가 실험을 설계하기 위해 도출한 구분입니다. 이 구분만으로 CRAG가 모든 오염 문서에 실패한다고 결론 내리지는 않습니다. 웹 검색도 잘못된 근거를 가져올 수 있으므로 실제 회복은 결과로 측정해야 합니다.

현재 방향에서 추가 학습 여부, 임계값, 모델 및 호출 예산은 팀과 선택할 구현 항목입니다. 이 해설의 상호작용 예시는 알고리즘을 이해하기 위한 계산이며 모델 추론이나 연구 결과가 아닙니다.
