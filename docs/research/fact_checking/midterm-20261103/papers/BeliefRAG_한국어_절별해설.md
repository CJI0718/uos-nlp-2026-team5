# BeliefRAG — 지금의 근거로 답할까요, 더 찾을까요?

**읽기의 중심 질문:** 관련성·신뢰성·충돌·부족함을 감지한 뒤, 그 정보를 실제 행동으로 어떻게 바꿀까요? 더 검색하는 것이 유용할지까지 판단할 수 있을까요?

Hongji Pu, *BELIEFRAG: Making Adaptive RAG State-Aware under Evolving Evidence*. **2026년 9월 30일 v1, 20쪽**을 기준으로 작성했습니다. [공식 서지](https://arxiv.org/abs/2609.39139v1) · [원본 PDF](https://arxiv.org/pdf/2609.39139v1) · [전체 읽기 지도](연구과정_중간발표_논지.html)

## 1. 이 논문은 앞의 두 논문과 무엇이 다른가요?

DRNoise가 오염된 환경에서 실패를 드러내고 HAE-GEO가 검증과 교정을 나누어 평가했다면, BeliefRAG는 **다음 행동을 고르는 제어기를 어떻게 구성할지** 제안합니다. “검색 결과의 관련성이 낮으면 다시 검색”처럼 신호 하나에 반응하는 방식을 넘어, 지금까지 모은 근거의 상태를 유지하며 수정·검색·응답·종료를 결정하려는 연구입니다.

핵심 문제를 evidence-state fragmentation이라고 부릅니다. 한 번은 관련성을 보고, 다음에는 자신감을 보고, 다른 단계에서는 충돌을 보면서 각 신호가 따로 행동을 유발하면, 전체적으로 무엇을 알고 무엇이 부족한지 이어서 관리하기 어렵다는 문제입니다.

논문의 전체 흐름은 §1–2 기존 적응형 RAG의 문제 → §3 근거 상태와 행동 규칙 → §4 공통 환경의 비교 실험 → §5 정확도·비용·구성요소·보정·오염 분석 → §6 한계입니다. 부록 A는 실제 계수·프롬프트·행동 예시, 후반 부록은 예산과 추가 모델 결과를 제공합니다.

## 2. §3.1 — ‘belief’는 파라미터 속에 있던 지식을 읽은 건가요?

이 논문에서 belief는 **현재 확보한 근거를 바탕으로 시스템이 계산해 유지하는 명시적인 상태값**입니다. LLM의 내부 뉴런이나 학습 데이터에서 믿음 자체를 직접 추출한 것이 아닙니다.

상태는 `질문 q + 현재 보관한 근거 Eₜ + 이전 쿼리·행동 Hₜ + 근거 상태 bₜ`로 구성됩니다. 검색은 Eₜ에 문서를 추가하고, 검증은 도움이 되지 않는 문서를 제거할 수 있습니다. 따라서 Eₜ는 모든 문서를 끝없이 붙여 둔 대화 기록과 다릅니다.

예를 들어 “기관 A의 설립연도는 2010년인가?”를 검증한다고 합시다. 이것은 안내서의 설명용 예시입니다. 첫 검색에서 기관 소개와 2022년을 주장하는 블로그를 얻었다면 ‘주제는 맞음’과 ‘정답을 판단할 수 있음’은 다릅니다. 다음에 공식 연혁이 2010년을 명시하면 충돌을 해결하고 근거 집합을 갱신해야 합니다. BeliefRAG는 이런 상태 변화에 따라 다음 행동을 고르는 구조입니다.

## 3. §3.2 — 먼저 측정하는 일곱 가지 신호

| 진단 신호 | 무엇을 묻나요? | 어떻게 계산하나요? |
|---|---|---|
| Relevance R | 질문과 주제가 얼마나 맞는가 | 검색 점수를 보정하고 가중 평균 |
| Support S | 현재 문서가 완전한 답을 얼마나 뒷받침하는가 | 구조화된 verifier 응답 |
| Conflict C | 문서끼리 또는 문서와 초안 사이에 중요한 모순이 있는가 | 같은 verifier 응답 |
| Uncertainty U | 이 자료만 읽으면 답이 얼마나 불확실한가 | 같은 verifier 응답 |
| Gap G | 질문에 필요한 정보 중 얼마나 비어 있는가 | 같은 verifier 응답 |
| Novelty N | 최근 검색이 기존 자료와 다른 정보를 더했는가 | 새 문서와 기존 문서의 유사도 |
| Cost K | 토큰 예산을 얼마나 썼는가 | 사용 토큰 / 전체 예산 |

네 의미 신호 S·C·U·G는 한 번의 구조화된 verifier 호출에서 함께 나옵니다. R·N·K는 로컬 계산입니다. 전부 LLM이 말한 자신감 숫자가 아니고, 전부 객관적인 정답 판정값도 아닙니다. 검색기 정보·모델 평가·사용량을 조합합니다.

이 표는 우리가 “문서가 믿을 만한가?”를 하나의 모호한 점수로 쓰지 않도록 도와줍니다. 관련성이 높지만 사실이 거짓일 수 있고, 개별 문서는 참이지만 필요한 두 번째 사실이 빠져 있을 수도 있습니다.

## 4. §3.3 — 일곱 진단에서 여섯 상태로, 다시 답변 가능성으로

진단 벡터를 이용해 **충분성·신뢰성·충돌·불확실성·정보 공백·비용**의 여섯 상태를 만듭니다. 비용을 제외한 상태는 가중 결합과 sigmoid를 사용하고, 이전 상태와 현재 관측을 logit 공간에서 섞어 급격한 흔들림을 완화합니다. 비용은 직접 관측합니다.

여기서 특별히 구분할 것이 두 개입니다.

1. **상태 좌표 b_suff:** 현재 근거가 충분한지 요약하는 지속적인 값.
2. **운영상 답변 가능성 p_ans:** 고정된 생성기가 현재 질문·자료·프롬프트에서 정답을 낼 가능성을 별도로 보정한 값.

실제 답변 여부를 결정하는 문은 p_ans를 사용합니다. 생성 프롬프트가 자료가 불완전해도 최선의 짧은 답을 요구하므로, 이 값에는 **생성기의 파라미터 지식으로 맞힐 가능성도 반영**될 수 있습니다. 따라서 p_ans를 “자료만으로 정답이 논리적으로 증명될 확률”로 읽으면 안 됩니다.

이 대목은 우리의 C0·C1 논의와 연결됩니다. 최종 정답이 나온 원인을 문서의 충분성만으로 설명하면 모델의 사전 지식 효과가 섞입니다. C0를 별도로 기록하려는 이유가 여기에 있습니다. 다만 C0 정답 역시 실제 학습 포함 여부의 증명보다는 관찰된 closed-book 성능으로 이름 붙이는 편이 정확합니다.

## 5. §3.4 — 어느 순서로 다음 행동을 고르나요?

행동은 Retrieve, Rewrite, Verify, Answer, Stop, Abstain입니다. 제어기는 고정된 분기 규칙을 사용합니다. **RL로 학습한 행동 정책은 아니며**, 답변 가능성과 추가 획득 가치 추정에 데이터 적합을 사용합니다.

| 판단 순서 | 물어보는 것 | 이어지는 행동 |
|---|---|---|
| 1. 교정 | 문서 간 충돌이 크거나 신뢰성이 낮은가? | Verify → 부적절 문서 제거 → 쿼리 수정 → 대체 근거 검색 |
| 2. 답변 | 현재 상태가 충분히 답변 가능한가? | Answer |
| 3. 획득 가치 | 한 번 더 검색하면 답변 가능한 상태가 될 가능성이 있는가? | 예산 안에서 Retrieve |
| 4. 새로움 | 직전 검색이 새 정보를 거의 주지 못했는가? | 같은 쿼리 반복 대신 Rewrite 후 Retrieve |
| 5. 종료 | 더 얻을 가치가 낮거나 획득 여력이 없는가? | 상태에 따라 Stop 또는 Abstain |

기본값 예시로 충돌 0.50 이상 또는 신뢰성 0.30 미만이면 교정을 검토하고, 답변 가능성 0.50, 추가 검색 가치 0.10, 새로움 0.20을 사용합니다. 실제 분석에서 선택한 값은 부록과 각 실험에 따로 제시됩니다. 핵심은 숫자를 그대로 복사하는 것보다 **어떤 신호를 어느 분기 전에 검사하는가**입니다.

추가 검색 가치 `p_flip`은 “부족한 상태가 다음 검색으로 답변 가능한 상태가 될 확률”을 뜻합니다. 앞서 읽은 Flip Risk의 정답→오답 flip과 방향과 의미가 다릅니다. 이름이 비슷하므로 발표에서 구분하면 좋습니다.

Stop은 현재 확보한 것으로 최선의 답을 작성하며 더 쓰지 않는 행동이고, Abstain은 근거 부족과 낮은 추가 획득 가치가 함께 있을 때 판단을 유보하는 행동입니다. 불확실하면 무조건 검색하거나 무조건 거부하는 규칙과 다릅니다.

## 6. 구현 관점 — ‘에이전트가 한다’와 ‘코드가 한다’의 경계

LLM은 쿼리·답변·verifier의 구조화된 판단을 생성합니다. 하네스는 검색기를 실행하고 문서를 갱신하며 예산을 계산합니다. 제어 규칙은 그 상태를 보고 어떤 호출을 할지 결정합니다. 자유로운 자연어 ReAct만이 에이전트의 유일한 구현 형태는 아닙니다.

우리에게 이 점은 두 가지 선택을 줍니다. 모델이 직접 검색·종료를 고르는 C2와, 명시적인 충돌·부족 신호를 기준으로 선택하는 C2를 비교할 수 있습니다. 반대로 두 구현을 한꺼번에 만들지 않고 한 정책에 집중하더라도, **누가 어떤 판단을 수행하는지** 정확히 기술하면 됩니다.

교정에서 문서 삭제만으로 끝내지 않는 것도 중요합니다. 2022년을 주장한 문서를 지우면 위험한 주장은 사라지지만, 정답 2010년의 근거가 생기지는 않습니다. 삭제 후 쿼리를 바꾸고 대체 근거를 가져와야 정보 공백이 메워질 수 있습니다.

## 7. §4 — 무엇을 고정하고 무엇을 비교했나요?

주요 실험은 HotpotQA·2WikiMultiHopQA·MuSiQue의 다단계 QA 세 개와 Natural Questions·TriviaQA·PopQA의 사실형 QA 세 개입니다. **데이터셋마다 동일한 100문제**를 비교합니다. RGB 오염 실험과 HoloBench 행 집합 검색은 별도의 진단 실험입니다.

같은 모델 안에서는 생성기·검색기·verifier·답변 프롬프트·평가기·예산을 고정하고 제어 방법을 바꿉니다. No-RAG, Static RAG, 항상 반복 검색하는 Iterative RAG, 적응형 방법들과 BeliefRAG를 비교합니다. 최대 검색 3회, 회당 5문서, 제어 행동 6회, 총 토큰 12k를 구분해 제한합니다.

검색은 공통 corpus와 lexical retrieval을 사용하는 통제된 설정입니다. 여기서의 CRAG 비교는 해당 공통 하네스에 맞춘 교정 방식이고, 원래 CRAG의 공개 웹 경로 전체와 동일한 재현으로 읽지 않습니다. Self-RAG*도 검색 발동 기제를 비교하는 변형이며, RL-Search는 상호작용 형식을 따른 프롬프트 제어기입니다. 이름만 보고 원 논문 전체 구현의 승패로 확대하지 않는 것이 정확합니다.

주 지표는 정규화된 token F1이고 EM을 보조로 봅니다. LLM Judge 정확도도 쓰지만 Judge가 평가 대상과 같은 backbone이므로, 모델 간 주 비교에는 결정론적 F1을 사용합니다. 비용은 최종 출력 토큰만이 아니라 **반복 전송된 근거·verifier·쿼리 수정·정책 프롬프트·답변**을 모두 셉니다.

## 8. §5.1 — 평균 성능과 비용은 어떻게 바뀌었나요?

| Backbone | 방법 | 여섯 데이터셋 평균 F1 | 문제당 평균 토큰 |
|---|---|---:|---:|
| gpt-oss-120b | No-RAG | 0.407 | 0.10k |
| gpt-oss-120b | Static RAG | 0.514 | 2.82k |
| gpt-oss-120b | Iterative RAG | 0.555 | 6.35k |
| gpt-oss-120b | BeliefRAG | 0.572 | 3.89k |
| Qwen3-32B | Iterative RAG | 0.523 | 5.81k |
| Qwen3-32B | BeliefRAG | 0.552 | 3.78k |

Table 3 및 부록 Tables 7–8의 비교입니다. gpt-oss에서는 Iterative보다 F1이 0.017 높고 토큰을 약 39% 덜 사용합니다. Qwen에서는 F1이 0.029 높고 토큰이 약 35% 적습니다. gpt-oss의 여섯 데이터셋 모두에서 이긴 것은 아니며 TriviaQA·PopQA에서는 Iterative가 더 높았습니다.

핵심 주장은 “언제나 더 많이 검색해야 한다”가 아니라 **지금 상태에 맞춰 검색하면 평균적인 품질과 비용의 조합을 개선할 수 있다**입니다. 우리 C2도 C1보다 정확한지뿐 아니라, 쉬운 사례에서도 불필요한 호출을 늘리는지 봐야 합니다.

## 9. §5.2–5.4 — 여섯 상태를 많이 만들었기 때문에 좋아졌나요?

구성요소 분석에서는 교정·검증·대체 근거 획득을 제거해 봅니다. 완전한 제어기는 다단계 세 데이터셋의 의미 정확도 0.680, 교정 제거·검증 제거·삭제만 수행하는 조건은 각각 0.630이었습니다. **나쁜 자료를 발견하거나 지우는 것만으로는 부족하고, 빈자리를 채우는 재검색이 기여했다**는 해석입니다. 이 정확도는 앞 표의 token F1과 다른 보조 지표입니다.

또 답변 가능성 점수를 현재 상태에 맞춰 쓰는 경우와, 상태 사이에서 섞거나 고정한 경우를 비교합니다. 이 개입은 p_ans에 대한 것이지 여섯 상태 중 b_suff를 직접 조작한 실험이 아닙니다. 이름이 ‘sufficiency’로 남아 있는 그림 라벨과 실제 구현 대상의 차이를 본문이 설명합니다.

상태를 여러 개 두는 것 자체가 기여는 아닙니다. 여섯 상태를 합친 정답 구분 AUC는 0.816으로 가장 좋은 단일 신호인 불확실성 0.761보다 높지만, 신호 사이에는 중복이 있습니다. 중요한 것은 추가 정보가 있고, 실제 의사결정을 바꾸며, 상태에 따라 의미 있게 작동하는지입니다.

우리에게 적용하면 “출처 점수·충돌 점수·충분성 점수 세 개를 만들었다”보다, 그중 어떤 점수가 검색을 유발했고 실제 교정에 도움이 됐는지를 보아야 합니다. 항상 0 또는 항상 1로 나오는 분기는 적응적인 역할이 거의 없을 수도 있습니다.

## 10. §5.3–5.5 — 점수 보정과 거짓 근거는 얼마나 어려웠나요?

주 답변 가능성 추정기는 HotpotQA 학습 300개에서 logistic calibrator를 맞추고 개발 156개에서 Brier score로 설정을 선택한 뒤, 여섯 평가 데이터셋에 고정해 적용합니다. Qwen에서는 같은 절차를 그 backbone에 맞게 다시 적용합니다. 따라서 생성 LLM을 fine-tuning하지 않더라도 **별도의 점수 보정에 데이터 학습이 들어갑니다.**

보정은 비슷한 환경에서 점수와 임계값의 의미를 안정시키는 데 도움을 줍니다. 하지만 Wikipedia QA에서 RGB 웹 스니펫으로 옮기면 답변 가능성의 평균 AUC가 **0.775에서 0.651**로 하락했습니다. 이는 단순히 0.5를 0.6으로 고치는 문제가 아닙니다. 올바른 상태와 잘못된 상태를 점수로 서열화하는 능력 자체가 떨어진 것입니다.

RGB 진단은 무관한 문서와 의도적으로 잘못된 근거를 구분합니다. 무관 문서 80% 조건에서는 BeliefRAG가 의미 정확도 0.87, Static 0.80, Iterative 0.81, 공통 하네스 CRAG 0.82를 보고합니다. 반면 거짓 답을 지지하는 자료 조건에서 BeliefRAG는 **25%에서 거짓 답을 따르고, 30%에서 참 답을 회복**합니다.

거짓을 따른 비율 25%를 보고 나머지 75%가 정답이라고 읽으면 안 됩니다. 나머지에는 보류와 다른 오답도 있습니다. 이것이 우리가 최종 결과를 ‘정답·주입된 거짓 답·다른 오답·보류’로 나눌 이유입니다.

## 11. 우리 연구에서는 어디까지 가져오는 것이 좋을까요?

**직접 가져오기 좋은 설계 원칙**은 같은 생성기와 예산을 고정한 제어 정책 비교, 교정 시 대체 근거의 실제 획득 여부 기록, 정확도와 누적 비용의 분리, 보류·다른 오답의 분리입니다. C0·C1·C2라는 큰 비교 틀 자체는 이미 이런 연구들에서도 등장하므로, 우리 기여는 초기 오염과 교정 과정을 어떻게 짝지어 분석하느냐에서 찾는 편이 좋습니다.

우리가 지금 꼭 여섯 상태와 보정기를 전부 구현할 필요는 없습니다. 중간 발표에서는 “왜 충분성 하나로는 부족한가”, “어떤 신호를 선택하겠는가”, “그 신호가 실제 분기를 바꾸는지 어떻게 확인하겠는가”를 설명할 수 있습니다. 기말의 범위는 팀이 선택한 가설을 검증하는 최소 구조로 정하면 됩니다.

원자 주장 팩트체크에 적용한다면 다음과 같은 비교 질문을 만들 수 있습니다. **같은 오염된 초기 문서를 받은 상황에서, 항상 추가 검색하는 정책과 충돌·부족을 판단해 추가 검색하는 정책은 정답 보존·교정·호출 비용이 어떻게 다른가?** 이는 BeliefRAG와 연결된 질문이며, 그 자체를 전례 없는 새 정책이라고 주장할 필요는 없습니다.
