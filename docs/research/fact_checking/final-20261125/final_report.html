무엇이 효과가 있었나

  • 서버 게이트가 핵심이에요. Skill이 없자 모델은 예측 주장 3개(FC017, FC026, FC041)를 지지·반박으로 냈어요. 서버가 세 번 모두 돌려보냈고, 모델이 근거 부족으로 다시 내 셋 다 정답이 됐어요. Skill이 있을 때는 모델이 처음부터 근거 부족으로 내서 게이트가 작동할 일이 없었어요. 같은 규칙을 Skill로 안내하든 서버가 강제하든 결과는 같았지만, 서버 강제는 모델이 따르지 않아도 막아 줘요.
  • 인용 규칙도 서버가 강제했어요. 읽지 않은 인용은 33개에서 0~1개로, 순환 검증은 5개에서 0개로 줄었어요.
  • Skill은 정답률 대신 탐색량을 바꿨어요. Skill이 있으면 도구 호출 1.5배, Tavily 1.9배, 비용 2.4배예요. 이번 50개에서는 추가 탐색이 정답을 늘리지 않았어요.
  • 앞선 추론을 바로잡았어요. 실험을 이어 보고 "Skill의 판정 규칙이 핵심"이라 추론했는데, Skill 제거 실험으로 틀렸음을 확인했어요.

서버 게이트가 하는 일

검사막는 경우돌려주는 말 (요약)
원래 글 인용 금지주장이 나온 글을 근거로 인용검증 대상은 근거가 될 수 없음. 다른 출처를 찾거나 근거 부족
인용문 대조지지·반박인데 근거 문장이 없거나, 읽은 본문에 그 문장이 없음. 짧은 조각까지 모두 대조하고, 숫자를 중간에서 자른 인용("199만"의 "99만")도 막음인용 문서의 문장을 그대로 옮길 것. 읽지 않은 문서는 인용 불가
예측 주장 ①미래 일을 주장하는데 인용문(생략한 부분 포함)이 "전해졌다", "전망", "확률" 같은 보도·추측 표현보도·전망은 미래 사실의 근거가 아님. 확정 발표를 인용하거나 근거 부족
예측 주장 ②"전망을 사실처럼 썼다"는 이유로 반박그 이유만으로는 반박 불가. 근거 부족으로 제출
결과물 값 대조결과물(.md, .ics)에 쓴 수치·일시가 인용 문서에도, 그 문서 값으로 한 계산기 결과에도 없음. 반박된 일정은 정정문의 날짜·시각이 다름결과물을 만들지 않고 차단 사유를 기록. 판정은 그대로 남음

판정이 막히면 에피소드는 끝나지 않아요. 에이전트가 이유를 보고 고쳐 다시 내고, 거절 기록은 실행 기록에 남아요. 결과물 값 대조는 판정을 낸 뒤에 작동해서, 결과물만 막고 다시 낼 기회는 없어요.

결과물 값 대조 (2026-11-27 추가, 기존 기록으로 검사)

판정 게이트는 판정만 검사해서, 원문이 "199만 원"이어도 "… 99만 원"이라는 인용이 통과했고, 정정문과 날짜가 다른 일정도 시각만 같으면 통과했어요. 이 빈틈을 막고, 결과물의 값도 원문과 대조하게 했어요. 값은 표기가 아니라 크기로 맞춰요("99만 원" = "990,000원", "26 million" = "2,600만"). 모델은 다시 호출하지 않고 exp-012·014의 기록과 웹 캐시로 검사했어요.

6. 결론

  • 근거를 주면 판단은 거의 다 맞혀요(C1 98%). 다만 이건 근거를 골라 준 조건이에요.
  • 근거를 주지 않아도 스스로 찾아 94%를 맞혀요(C2W, 독립 출처 기준). 도구 없음은 22%예요.
  • 같은 모델, 같은 예산에서 하네스만 바꾸면 독립 출처로 맞힌 비율이 76%에서 94%가 돼요. 효과는 프롬프트가 아니라 서버가 강제하는 검증 규칙에서 나와요.
  • 개선 과정 자체가 결과예요. 높은 점수(94%)를 의심해 순환 검증을 찾았고, 규칙으로 막은 뒤 진짜 실력(82%)을 확인했어요. 이어 예산과 게이트로 94%까지 올렸어요.

7. 한계와 유의사항

  • 실행 횟수: 조건마다 한 번씩 돌렸어요. temperature 0이어도 결과가 조금씩 달라요(v3 재실행에서 4개 맞힘, 2개 틀림). 1~2개 차이는 잡음으로 봐야 해요. 하네스 유무의 9개 차이는 이보다 커요.
  • 개발·평가 분리: 모든 Action Item을 같은 50개의 오답에서 찾았어요. 따로 떼어 둔 개발용 데이터가 없어서, 개선이 이 50개에 맞춰졌을 수 있어요. 규칙은 일반 규칙과 가상 예시로만 썼어요.
  • 게이트는 형식만 봐요: 인용문이 본문에 있는지, 보도 표현이 있는지만 검사하고 그 문장이 판정을 뒷받침하는지는 판단하지 않아요. FC010은 "a new report … set to debut"라는 인용으로 지지가 접수됐어요. 표현 목록에 "report"와 "set to"가 없었기 때문이에요. 평가데이터에 맞추는 일이 되므로 고치지 않았어요. 주장 유형도 문구("~할 것이다")로만 분류해요.
  • 결과물 값 대조는 값을 대상과 묶지 않아요: 문서 어딘가에 같은 값이 있으면 통과해요. FC001의 교육가를 85만에서 86만으로 바꿔도, 같은 기사에 "환산하면 약 86만 원"이 있어 통과했어요. 연도와 작은 수는 더 자주 놓쳐요(192회 중 107회 차단). 숫자 앞의 설명어를 원문과 비교하는 방식도 시험했지만, 정상 결과물 9개를 더 막고 금액 탐지율은 91%에서 92%로 거의 같아 넣지 않았어요. 다음 개선안은 에이전트가 값마다 근거 문장을 붙여 내게 하는 방식이에요. 제출 형식이 바뀌어 50개를 다시 실행해야 해서 이번에는 하지 않았어요. 새 규칙으로 다시 돌린 실험도 없어요.
  • 장치별 분리: Skill은 따로 뺐지만, 도구(find_in_page, 계산기)와 게이트는 따로 떼어 보지 않았어요.
  • 웹 근거의 시점: 웹 페이지는 지금 내용을 가져와요. 발행일 없는 페이지(GitHub 파일 등)는 기준 시점 필터를 통과해, 시점 이후 바뀐 내용이 근거가 될 수 있어요. 반대로 시점 이후 지워진 근거는 웹에서 찾을 수 없어요.
  • 근거 동반 정답(자동)은 참조 근거와의 URL 겹침으로 계산한 근사치이고, 사람 채점은 하지 않았어요.
  • 라벨 경계: 근거 부족 6개가 모두 예측 주장이라 판정 규칙의 효과가 크게 보여요. FC026(확률 전망) 같은 사례는 정답 기준이 논쟁적일 수 있어요.
  • 남은 공통 약점: FC034는 비교 값이 그래프 데이터에만 있어 여러 모델이 공통으로 틀렸어요.
