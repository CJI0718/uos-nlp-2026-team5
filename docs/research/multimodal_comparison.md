# 멀티모달 입력과 기호·도구 기반 생성의 비교 연구

조사일: 2026-10-14. 상태: 팀 논의를 위한 연구 제안, 주제·모델·예산 미선정, 실험 미실행.

핵심 질문은 **같은 일을 시킬 때 이미지를 직접 이해하거나 생성하는 경로와, 기호·코드를 매개로 도구를 사용하는 경로가 정확성·효율·수정 가능성에서 어떻게 달라지는가**이다. 악보, 스프레드시트, 도식은 이를 관찰할 수 있는 서로 다른 후보 도메인이다. 세 도메인을 모두 구현할 필요는 없다.

기존 [30개 후보](candidates.md)에 MM1–MM6을 추가해 총 36개로 확장했다. 모든 후보의 상세 태스크·50개 배분·지표·호출량은 [통합 후보집](candidates.md)과 [JSON 원자료](candidates.json)에 있다. 아래는 후보를 선택하기 전에 공유할 개념, 선행연구와 비교 설계이다.

## 1. 먼저 분리할 네 가지 능력

| 축 | 비교 대상 | 구별해야 하는 점 |
| --- | --- | --- |
| 입력 | 이미지, 자연어 설명, 구조화된 기호, 결합 | CSV·ABC·SVG·MusicXML은 텍스트로 저장해도 자연어 문장이 아니다. |
| 추론 | 모델이 값·관계·지시를 해석하는 과정 | 입력 형식만 바꿨는지, 모델·학습 데이터까지 바꿨는지 구분한다. |
| 출력 | 픽셀 이미지, 기호 코드, 파일 API·UI 동작 | 이미지 입력을 받는 VLM이 이미지 출력도 지원한다고 가정하지 않는다. |
| 검증 | 구조 검사, 실행 결과, 렌더링 재관찰 | 유효한 코드, 올바른 의미, 보기 좋은 결과는 다른 지표다. |

“멀티모달 대 도구”는 배타적인 분류가 아니다. StarVector는 멀티모달 모델이 SVG **코드**를 출력하는 예다. 따라서 이미지 입력 지원 여부와 도구·코드 사용 여부를 독립적인 축으로 기록한다. [P43](https://openaccess.thecvf.com/content/CVPR2025/html/Rodriguez_StarVector_Generating_Scalable_Vector_Graphics_Code_from_Images_and_Text_CVPR_2025_paper.html)

대표적인 생성 경로는 다음과 같다.

```text
같은 자연어 명세
  ├─ 이미지 출력 모델 → raster 결과
  ├─ 언어 모델 → ABC / SVG / 수식·명령 → 렌더러·계산 엔진 → 결과
  └─ 멀티모달 모델 → 같은 기호·명령 → 같은 엔진 → 결과
                                                └─ 선택적 관찰·수정
```

일부 서비스가 파일을 반환하더라도 내부에서 코드와 도구를 실행했을 수 있다. 서비스의 산출물만으로 “모델이 native xlsx를 생성했다”고 분류하지 않는다. xlsx 안의 수식·참조와 악보의 성부·음가를 픽셀 이미지와 같은 자료 구조로 취급하지도 않는다.

## 2. 선행연구가 보여주는 것과 남아 있는 질문

### 입력 표현은 이미 직접 비교된 연구 문제다

**Texts or Images?**는 표 크기와 질문 복잡도에 따라 텍스트·이미지와 모델 조합의 유불리가 달라짐을 보고하고, 표현을 선택하는 FRES를 제안한다. **TabVerse**는 같은 표 내용을 여러 텍스트 형식과 이미지로 정렬해 QA·구조 이해·재구성을 비교한다. 따라서 “이미지 대 텍스트를 비교한다” 자체를 최초 아이디어라고 주장하기는 어렵다. 한국어 단위·계층형 헤더·제약 보존·도구 실행 이후의 업무 완료를 함께 보는 것이 우리에게 가능한 확장 가설이다. [P35](https://aclanthology.org/2025.findings-acl.117/), [P46](https://arxiv.org/abs/2606.09578)

### 생성 도구는 정확한 문법을 제공하지만 의미까지 보장하지 않는다

**VGBench**는 벡터 형식의 이해·생성을, **ChatMusician**은 ABC 기호를 통한 음악 이해·생성을 다룬다. 기호 표현은 렌더링·실행·수정 검사를 가능하게 하지만, 정상적으로 그려지는 틀린 화살표나 유효하지만 요청과 다른 악보도 가능하다. 이 논문들이 직접 이미지 생성보다 모든 면에서 낫다는 결론을 주는 것은 아니다. [P42](https://aclanthology.org/2024.emnlp-main.213/), [P40](https://aclanthology.org/2024.findings-acl.373/)

### Agent의 가치는 실행과 피드백까지 포함해서 확인한다

**SheetCopilot**은 자연어 요청을 스프레드시트의 동작·계획으로 연결한다. **SpreadsheetBench**는 실제 파일 상태를 여러 테스트로 검증하는 관점을 준다. 한편 SVG 반복 개선 연구는 구조 제약과 시각 피드백을 사용해도 자기 수정에 한계가 있음을 보고한다. 따라서 “렌더링을 다시 보여주면 더 좋아진다” 역시 검증할 가설이지 전제가 아니다. [P37](https://proceedings.neurips.cc/paper_files/paper/2023/hash/0ff30c4bf31db0119a6219e0d250e037-Abstract-Conference.html), [P38](https://proceedings.neurips.cc/paper_files/paper/2024/hash/ac840df270ac537dd74530a15c332684-Abstract.html), [P44](https://arxiv.org/abs/2608.28678)

## 3. 여섯 후보의 범위와 갈림길

| ID | 실제 업무 | 주된 비교 축 | 데이터 50개 구성 | 난도와 주요 부담 |
| --- | --- | --- | --- | --- |
| MM1 | 악보 질문에 답하고 근거 마디·성부 제시 | 이미지 직접 처리 대 자동 OMR 기호 입력 | 음높이, 리듬, 임시표, 성부, 반복 각 10 | D3: 악보 정답 검수와 OMR 오류 분리 |
| MM2 | 음악 제약에 맞는 짧은 악보 생성 | 직접 이미지 출력 대 기호 코드·렌더러 | 음역, 박자, 리듬, 조성, 복합 제약 각 10 | D3: 출력 모델 자격 확인과 음악 검수 |
| MM3 | 표에서 근거를 찾아 계산하고 답하기 | 이미지 대 구조 텍스트 대 결합 | 단순 표, 헤더, 단위, 표 연결, 정보 부족 각 10 | D2: 동일 정보의 표현 쌍 만들기 |
| MM4 | 실제 workbook에 표·수식 생성/수정 | 화면 기반 동작 대 구조적 명령 실행 | 표, 집계 수식, 시트 참조, 오류 수정, 보존 제약 각 10 | D3: GUI·계산 엔진·파일 상태 검증 |
| MM5 | 관계가 정확한 도식 생성 | 직접 raster 대 SVG/Graphviz 렌더링 | 노드, 엣지, 배치, 수치, 복합 제약 각 10 | D2부터: native 이미지 대조까지 넣으면 D3 가능 |
| MM6 | 초안을 검토하고 한 번 수정 | 정보 없는 재검토 대 구조 피드백 대 구조+이미지 | 구문, 구조, 시각, 의미 오류와 정상 사례 각 10 | D2: 동일 초안·동일 수정 예산의 비교 |

난도는 기존 후보집의 계획용 분류다. D2 약 5–8인일, D3 약 9–15인일 이상이라는 가정은 Python에 익숙한 사람의 작은 구현에 대한 예시이며, 데이터 작성·논문 읽기·학습 실험·보고서 시간은 별도다. 실제 일정 추정치는 파일럿 후 수정한다.

### 음악 방향

악보 이미지를 보고 설명하는 MM1과, 정확한 악보를 만드는 MM2를 나누면 평가가 명확해진다. 처음에는 짧은 인쇄 악보, 제한된 기보 규칙과 성부 수를 명시한다. 손글씨·전곡·복잡한 반복·기보 관습을 한꺼번에 지원하지 않는다. NOTA와 MSU-Bench는 입력 이해의 선행연구이고, native 악보 이미지 생성의 성공 근거는 아니다. [P39](https://aclanthology.org/2025.findings-naacl.399/), [P45](https://aclanthology.org/2026.acl-long.493/)

음악적 미감보다 음역, 마디 길이, 시작/종료음, 반복 관계 같은 검사 가능한 요구로 시작할 수 있다. 같은 음악을 다르게 적은 표현은 사전에 동치 규칙을 정한다. 박자·임시표의 해석을 단순 음표 개수나 문자열 일치로 대신하지 않는다.

### 스프레드시트 방향

MM3는 입력 구조의 이해, MM4는 파일의 기능적 완료를 본다. MM4의 모든 시스템은 같은 workbook 작업 요구를 받아야 한다. 화면 조작과 파일 API 비교는 지각·행동 인터페이스가 함께 바뀌므로 전체 시스템 비교이며 순수한 시각 능력 실험은 아니다.

수식은 동일한 문자열인지뿐 아니라 여러 입력값에서도 올바르게 계산되는지 검사한다. 보호할 셀·시트·서식 범위를 사전에 적고 비허용 변경을 센다. 파일 작성 라이브러리만으로 수식 계산 엔진을 대체했다고 가정하지 않는다. 실제 계산 엔진을 고정하거나 지원하는 수식 범위를 명시한 evaluator가 필요하다.

### 도식과 검증 방향

MM5는 사용자의 직접 생성 대 도구 생성 질문을 관계 그래프와 라벨 정확도로 구체화한다. 공통 최종 산출물이 이미지라면 양쪽 이미지를 같은 기준으로 평가하고, 편집 가능한 구조의 존재는 별도 지표로 보고한다. 반대로 편집 가능한 파일이 필수인 태스크라면 이를 제공하지 못하는 시스템은 부적격 대조군이며, 이를 억지로 낮은 능력 점수로 만들지 않는다.

MM6는 도메인 하나만 선택해 같은 모델이 같은 초안을 한 번 수정하도록 한다. 구조 피드백과 시각 피드백의 추가 가치를 분리할 수 있다. 수정하지 않아도 되는 정상 사례가 있어야 과도한 수정의 부작용을 볼 수 있다.

## 4. 공정한 비교를 위한 실험 블록

### A. 동일 정보의 표현 비교

가능하면 **동일한 VLM 체크포인트**에 이미지, 구조화 텍스트, 결합 입력을 주고 같은 질문·도구·출력 계약을 유지한다. 텍스트 모델과 별도의 VLM을 바꾸는 비교는 후속 시스템 비교로 둔다. 이름이 비슷한 모델이라도 학습 데이터와 후처리가 다르면 순수한 모달리티 효과가 아니다.

| 원본 확보 조건 | 텍스트 경로에 줄 수 있는 것 | 해석 |
| --- | --- | --- |
| 구조 파일이 원래 존재 | 원본에서 고정 규칙으로 직렬화한 정보 | 표현 차이 비교. 이미지에서도 질문에 필요한 정보가 보이게 해야 함 |
| 이미지만 존재 | 고정 OCR/OMR의 실제 출력 | parser 오류·비용을 포함한 end-to-end 경로 비교 |
| 진단용 oracle | 사람이 정확히 복원한 기호 정보 | 파싱 오류를 제거한 상한/원인 진단. 실사용 경로로 보고하지 않음 |

이미지에 없는 숨김 시트·수식·좌표 메타데이터를 텍스트에만 제공하지 않는다. 필요한 정보가 시각적으로 표현될 수 없는 문제는 입력 공정 비교에서 제외하고 구조 전용 블록으로 분리한다. 자연어로 요약하는 경로를 추가한다면 누가 요약했는지, 손실된 정보, 요약 모델의 호출·비용도 기록한다.

### B. 동일 출력 계약의 생성 경로 비교

1. 공통 사용자 명세와 필수 결과를 고정한다.
2. native 이미지 출력, 언어→코드→엔진, 멀티모달→코드→엔진 중 **실제로 지원되고 수업 정책에 맞는** 조건만 선택한다.
3. 서로 다른 모델이면 모델 규모·학습·출력 기술이 함께 바뀌는 시스템 비교로 해석한다.
4. 코드/파일 경로의 parsing·rendering·계산·검증 시간과 실패도 모두 포함한다.
5. 시각적 유사성, 의미 정확성, 기능적 편집 가능성을 합쳐 임의의 한 점수로 만들지 않는다.

이미지 생성 모델이 없는 경우 “native 생성 실패율 100%” 같은 결과를 만들지 않는다. **실험 조건 미충족으로 미실행**이라고 남기고, 팀의 명시적 선택으로 입력 비교나 피드백 비교를 진행한다.

### C. 같은 초기 결과에 대한 피드백 비교

MM6에서는 초안 50개를 고정하여 공유한다. 각 조건은 같은 모델의 수정 호출 1회를 사용한다. 구조 피드백 조건과 구조+이미지 조건의 차이는 추가 관찰 정보이며, 호출 수 증가 효과와 분리한다. 최초 초안의 성능은 별도 기준선으로 남긴다.

피드백용 검사기는 실제 사용자가 얻을 수 있는 구문·실행 오류만 제공한다. 숨겨진 정답 제약과 테스트 결과 전체를 모델에게 넘겨 정답 유출을 만들지 않는다. 수정 루프가 필요하면 횟수·중단 규칙을 실험 전에 합의한다.

## 5. 평가 데이터와 지표

### 50개는 50개의 독립적인 기본 업무

한 악보를 5번 다른 해상도로 렌더링한 것은 5개의 독립 악보가 아니다. 각 기본 사례의 변형은 동일한 `case_id` 아래에서 대응 비교하고, train/dev/test 분할은 기본 사례·템플릿 단위로 한다. 50개 평가 사례와 별도로 5–10개 개발 사례를 두는 방안을 검토할 수 있다. 데이터 생성에 모델을 쓰더라도 사람의 정답 검수와 직접 작성 요건 충족 여부를 따로 확인한다.

사례마다 다음을 남긴다.

- 사용자에게 보이는 명세, 공개 입력, 요구 산출물, 허용 도구와 금지 변경
- 파서/렌더러 버전, 이미지 해상도·글꼴, 구조 표현 방식
- evaluator 전용 정답·근거·허용 오차·의미 동치·숨겨진 테스트
- 개발/평가 구분과 원본 사례 ID, 데이터 출처·재배포 권한
- 입력·프롬프트·모델 설정 hash와 실제 요청/도구/파일 변경 기록

문제 설명·파일 이름·메타데이터에 정답이나 오류 위치가 새어 들어가지 않게 한다. 공개 benchmark는 설계 참고용이며 직접 작성 데이터를 대체하지 않는다. 공개 GitHub에는 개인 업무자료·수업 원본·권한 없는 악보나 논문 PDF를 올리지 않는다.

### 주요 지표

| 층 | 지표와 분모 | 해석 |
| --- | --- | --- |
| 업무 | 모든 필수 조건을 충족한 사례 / 전체 평가 사례 | 기본 task success. 모든 사례를 분모에 유지 |
| 인식 | 정답 event/셀 대비 pitch·duration·값·헤더·위치 오류 | 인식 오류와 후속 추론 오류 분리 |
| 관계·계산 | 올바른 참조·엣지·음악 관계·실행 결과 | 문자열·픽셀 유사도로 대체하지 않음 |
| 보존 | 비허용 변경 셀·객체 수 / 보호 대상 수 | 분모 0이면 N/A. 정상 사례 손상률도 함께 보고 |
| 완료 보고 | 실패했는데 완료라고 한 사례 / 전체 사례 | false completion; 실패 사례를 분모로 한 조건부 비율은 별도 |
| 효율 | 전체 wall time, 모델별 token/이미지 입력량, GPU 시간, tool 호출 | parser·renderer·실패·검증 비용 포함 |
| 신뢰도 | 사례 단위 paired 차이, bootstrap 구간, 유형별 오류 수 | 반복·시각 변형을 독립 표본처럼 늘리지 않음 |

인프라 timeout과 내용 오류를 별도 유형으로 보존하고, 전체 실행 신뢰도와 응답을 받은 사례의 조건부 품질을 함께 보고한다. 빈 답·잘림·오류를 성공으로 세지 않는다. 성공 0건이면 성공 1건당 비용은 미정의다.

서로 다른 출력 형식의 비교는 공통 렌더링에서 사람이 모델 이름을 가리고 같은 rubric으로 평가하는 것이 작은 50개 연구의 한 선택지다. OCR/OMR을 evaluator로 사용하면 그 오류도 샘플 검수해야 한다. 코드 조건만 구조에서 정확하게 읽고 raster 조건만 불완전한 OCR로 읽어 얻은 차이를 모델 성능 차이로 단정하지 않는다.

### 과제 개선 단계로 이어질 가설

- 헤더 연결이 주된 실패라면 구조 직렬화에 부모 헤더를 명시한다.
- 연산은 맞고 인식만 틀리면 확대·영역 선택·OMR 확인 단계를 실험한다.
- 코드가 실행돼도 의미가 틀리면 일반적인 제약 검사 또는 참조 추적 피드백을 추가한다.
- 시각 피드백이 불필요한 수정을 늘리면 수정 영역을 제한하거나 보류 규칙을 둔다.
- 큰 자료에서만 성능이 나빠지면 관련 영역 선택/검색으로 기존 RAG 후보와 연결한다.

어느 가설도 아직 관찰된 결과가 아니다. 개선 전후에는 같은 평가 계약과 예산을 유지하고, 평가 데이터에 맞춰 반복 튜닝했다면 그 사실과 별도 holdout 여부를 보고한다.

## 6. 비용과 실행 가능성

첫 학기 범위는 기존 모델·라이브러리의 재사용이다. 새 범용 모달리티 인코더나 대규모 end-to-end 사전학습은 전제하지 않는다. Colab 같은 GPU 환경은 추론·작은 추가 학습의 후보이지만 실제 장치, VRAM, 모델 적재와 속도는 실행 전에 확인해야 한다.

| 비교 규모의 가정 | 업무 실행 수 | 모델 요청량 예시 |
| --- | --- | --- |
| 50개 × 2조건 × 1반복 | 100 | 평균 1회면 100회, 평균 3회면 300회 |
| 50개 × 3조건 × 1반복 | 150 | 평균 1회면 150회, 평균 3회면 450회 |
| 동일 설계를 모델 2종으로 확장 | 위 수의 2배 | 모델 축을 독립적으로 더한 경우만 |
| MM6 공통 초안에서 수정 1회 × 3조건 | 150회 수정 | 초안 생성·개발·Judge 비용은 별도 |

수치는 실행 결과나 승인된 예산이 아니라 산식의 예다. 이미지 생성 요청, 언어 모델 요청, OCR/OMR GPU 작업은 단가·연산량이 달라 별도로 기록한다. 금액은 선택한 endpoint의 실행 시점 가격과 이미지 과금 규칙을 확인한 후 계산한다. 수업의 local/free 범위부터 확인하고 유료 모델을 자동으로 대체하지 않는다.

모델 선정 시 다음 자격을 먼저 확인한다: 입력 이미지 지원, 실제 이미지 출력 지원 여부, 텍스트/코드 출력, tool calling 필요 여부, 이용 조건과 수업 허용 여부, 체크포인트/버전, 메모리 요구. 이 문서는 어떤 모델의 현재 무료 제공·가용성도 보장하지 않는다.

실행은 별도 승인을 받은 범위에서 한 번에 한 건씩 시작한다. 실패 기록·완료 산출물을 재사용하고 자동 재시도·자동 모델 변경은 하지 않는다. 모델 호출 없이 validator·renderer·집계 코드의 단위 테스트를 먼저 할 수 있다. 생성 코드와 파일 도구는 임시 폴더·제한된 권한으로 격리한다.

## 8. 기존 다섯 주제와 연결하기

| 연결 주제 | 확장 질문 |
| --- | --- |
| RAG | 큰 표·긴 악보에서 필요한 시트·셀·마디만 골라 주면 정확도와 비용이 어떻게 변하는가? |
| ReAct | 인식 불확실성에 따라 확대, 재파싱, 계산, 렌더링 중 적절한 도구를 선택하는가? |
| 메모리 | 이전 편집의 제약·명명 규칙을 다음 수정까지 보존하는가? |
| Alignment | 문서 속 문구를 사용자 지시로 오인하지 않고 수정 금지 영역을 지키는가? |
| Harness | schema, validator, 시각 피드백과 중단 조건 중 어떤 요소가 실패를 줄이는가? |

이 연결들은 후보를 확장하는 방향이지 모두 교차 실험하라는 요구가 아니다. 팀은 도메인 하나와 주요 독립 변수 하나를 먼저 고를 수 있다.

## 9. 팀에서 결정할 것

1. 최종 사용자가 원하는 것은 읽고 답하기, 인쇄용 이미지, 아니면 계산·편집 가능한 파일인가?
2. 음악·표·도식 중 어느 도메인의 50개 정답을 사람이 검수할 수 있는가?
3. 알고 싶은 것이 입력 표현, 생성 경로, 피드백 중 무엇인가?
4. 수업이 허용하는 모델과 자원에서 대조군이 실제로 가능한가?
5. 성능이 좋아지지 않아도 어떤 오류 분석과 개선 실험을 남길 것인가?

후보를 지금 순위 매기거나 확정하지 않는다. 수업 적합성은 “자연어 지시를 받아 해당 자료를 이해·생성·검증하는 Agent, 직접 작성 평가 50개, 조건별 지표와 개선 실험”이라는 범위로 교수님께 확인할 수 있다.

## 조사 기록

Exa에서 입력 표현, 생성/도구 경로, 음악 기호의 3개 축을 조사했다. 검색 6회에 결과 항목 30개를 요청했으며 중복 URL·동일 논문의 다른 출판 경로를 정리하고 알려진 관련 원문을 함께 확인하여 새 참고자료 12편을 선정했다. 30개의 독립 논문을 정독했다는 뜻은 아니다. 확인 수준은 각 항목에 명시했고, 실험용 모델 호출은 0회다.
