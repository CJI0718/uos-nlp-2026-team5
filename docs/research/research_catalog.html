1. 먼저 분리할 네 가지 능력

축비교 대상구별해야 하는 점
입력이미지, 자연어 설명, 구조화된 기호, 결합CSV·ABC·SVG·MusicXML은 텍스트로 저장해도 자연어 문장이 아니다.
추론모델이 값·관계·지시를 해석하는 과정입력 형식만 바꿨는지, 모델·학습 데이터까지 바꿨는지 구분한다.
출력픽셀 이미지, 기호 코드, 파일 API·UI 동작이미지 입력을 받는 VLM이 이미지 출력도 지원한다고 가정하지 않는다.
검증구조 검사, 실행 결과, 렌더링 재관찰유효한 코드, 올바른 의미, 보기 좋은 결과는 다른 지표다.

“멀티모달 대 도구”는 배타적인 분류가 아니다. StarVector는 멀티모달 모델이 SVG 코드를 출력하는 예다. 따라서 이미지 입력 지원 여부와 도구·코드 사용 여부를 독립적인 축으로 기록한다. P43

대표적인 생성 경로는 다음과 같다.

같은 자연어 명세
  ├─ 이미지 출력 모델 → raster 결과
  ├─ 언어 모델 → ABC / SVG / 수식·명령 → 렌더러·계산 엔진 → 결과
  └─ 멀티모달 모델 → 같은 기호·명령 → 같은 엔진 → 결과
                                                └─ 선택적 관찰·수정

일부 서비스가 파일을 반환하더라도 내부에서 코드와 도구를 실행했을 수 있다. 서비스의 산출물만으로 “모델이 native xlsx를 생성했다”고 분류하지 않는다. xlsx 안의 수식·참조와 악보의 성부·음가를 픽셀 이미지와 같은 자료 구조로 취급하지도 않는다.

2. 선행연구가 보여주는 것과 남아 있는 질문

입력 표현은 이미 직접 비교된 연구 문제다

Texts or Images?는 표 크기와 질문 복잡도에 따라 텍스트·이미지와 모델 조합의 유불리가 달라짐을 보고하고, 표현을 선택하는 FRES를 제안한다. TabVerse는 같은 표 내용을 여러 텍스트 형식과 이미지로 정렬해 QA·구조 이해·재구성을 비교한다. 따라서 “이미지 대 텍스트를 비교한다” 자체를 최초 아이디어라고 주장하기는 어렵다. 한국어 단위·계층형 헤더·제약 보존·도구 실행 이후의 업무 완료를 함께 보는 것이 우리에게 가능한 확장 가설이다. P35, P46

생성 도구는 정확한 문법을 제공하지만 의미까지 보장하지 않는다

VGBench는 벡터 형식의 이해·생성을, ChatMusician은 ABC 기호를 통한 음악 이해·생성을 다룬다. 기호 표현은 렌더링·실행·수정 검사를 가능하게 하지만, 정상적으로 그려지는 틀린 화살표나 유효하지만 요청과 다른 악보도 가능하다. 이 논문들이 직접 이미지 생성보다 모든 면에서 낫다는 결론을 주는 것은 아니다. P42, P40

Agent의 가치는 실행과 피드백까지 포함해서 확인한다

SheetCopilot은 자연어 요청을 스프레드시트의 동작·계획으로 연결한다. SpreadsheetBench는 실제 파일 상태를 여러 테스트로 검증하는 관점을 준다. 한편 SVG 반복 개선 연구는 구조 제약과 시각 피드백을 사용해도 자기 수정에 한계가 있음을 보고한다. 따라서 “렌더링을 다시 보여주면 더 좋아진다” 역시 검증할 가설이지 전제가 아니다. P37, P38, P44

3. 여섯 후보의 범위와 갈림길

ID실제 업무주된 비교 축데이터 50개 구성난도와 주요 부담
MM1악보 질문에 답하고 근거 마디·성부 제시이미지 직접 처리 대 자동 OMR 기호 입력음높이, 리듬, 임시표, 성부, 반복 각 10D3: 악보 정답 검수와 OMR 오류 분리
MM2음악 제약에 맞는 짧은 악보 생성직접 이미지 출력 대 기호 코드·렌더러음역, 박자, 리듬, 조성, 복합 제약 각 10D3: 출력 모델 자격 확인과 음악 검수
MM3표에서 근거를 찾아 계산하고 답하기이미지 대 구조 텍스트 대 결합단순 표, 헤더, 단위, 표 연결, 정보 부족 각 10D2: 동일 정보의 표현 쌍 만들기
MM4실제 workbook에 표·수식 생성/수정화면 기반 동작 대 구조적 명령 실행표, 집계 수식, 시트 참조, 오류 수정, 보존 제약 각 10D3: GUI·계산 엔진·파일 상태 검증
MM5관계가 정확한 도식 생성직접 raster 대 SVG/Graphviz 렌더링노드, 엣지, 배치, 수치, 복합 제약 각 10D2부터: native 이미지 대조까지 넣으면 D3 가능
MM6초안을 검토하고 한 번 수정정보 없는 재검토 대 구조 피드백 대 구조+이미지구문, 구조, 시각, 의미 오류와 정상 사례 각 10D2: 동일 초안·동일 수정 예산의 비교

난도는 기존 후보집의 계획용 분류다. D2 약 5–8인일, D3 약 9–15인일 이상이라는 가정은 Python에 익숙한 사람의 작은 구현에 대한 예시이며, 데이터 작성·논문 읽기·학습 실험·보고서 시간은 별도다. 실제 일정 추정치는 파일럿 후 수정한다.

음악 방향

악보 이미지를 보고 설명하는 MM1과, 정확한 악보를 만드는 MM2를 나누면 평가가 명확해진다. 처음에는 짧은 인쇄 악보, 제한된 기보 규칙과 성부 수를 명시한다. 손글씨·전곡·복잡한 반복·기보 관습을 한꺼번에 지원하지 않는다. NOTA와 MSU-Bench는 입력 이해의 선행연구이고, native 악보 이미지 생성의 성공 근거는 아니다. P39, P45

음악적 미감보다 음역, 마디 길이, 시작/종료음, 반복 관계 같은 검사 가능한 요구로 시작할 수 있다. 같은 음악을 다르게 적은 표현은 사전에 동치 규칙을 정한다. 박자·임시표의 해석을 단순 음표 개수나 문자열 일치로 대신하지 않는다.

스프레드시트 방향

MM3는 입력 구조의 이해, MM4는 파일의 기능적 완료를 본다. MM4의 모든 시스템은 같은 workbook 작업 요구를 받아야 한다. 화면 조작과 파일 API 비교는 지각·행동 인터페이스가 함께 바뀌므로 전체 시스템 비교이며 순수한 시각 능력 실험은 아니다.

수식은 동일한 문자열인지뿐 아니라 여러 입력값에서도 올바르게 계산되는지 검사한다. 보호할 셀·시트·서식 범위를 사전에 적고 비허용 변경을 센다. 파일 작성 라이브러리만으로 수식 계산 엔진을 대체했다고 가정하지 않는다. 실제 계산 엔진을 고정하거나 지원하는 수식 범위를 명시한 evaluator가 필요하다.

도식과 검증 방향

MM5는 사용자의 직접 생성 대 도구 생성 질문을 관계 그래프와 라벨 정확도로 구체화한다. 공통 최종 산출물이 이미지라면 양쪽 이미지를 같은 기준으로 평가하고, 편집 가능한 구조의 존재는 별도 지표로 보고한다. 반대로 편집 가능한 파일이 필수인 태스크라면 이를 제공하지 못하는 시스템은 부적격 대조군이며, 이를 억지로 낮은 능력 점수로 만들지 않는다.

MM6는 도메인 하나만 선택해 같은 모델이 같은 초안을 한 번 수정하도록 한다. 구조 피드백과 시각 피드백의 추가 가치를 분리할 수 있다. 수정하지 않아도 되는 정상 사례가 있어야 과도한 수정의 부작용을 볼 수 있다.

4. 공정한 비교를 위한 실험 블록

A. 동일 정보의 표현 비교

가능하면 동일한 VLM 체크포인트에 이미지, 구조화 텍스트, 결합 입력을 주고 같은 질문·도구·출력 계약을 유지한다. 텍스트 모델과 별도의 VLM을 바꾸는 비교는 후속 시스템 비교로 둔다. 이름이 비슷한 모델이라도 학습 데이터와 후처리가 다르면 순수한 모달리티 효과가 아니다.

원본 확보 조건텍스트 경로에 줄 수 있는 것해석
구조 파일이 원래 존재원본에서 고정 규칙으로 직렬화한 정보표현 차이 비교. 이미지에서도 질문에 필요한 정보가 보이게 해야 함
이미지만 존재고정 OCR/OMR의 실제 출력parser 오류·비용을 포함한 end-to-end 경로 비교
진단용 oracle사람이 정확히 복원한 기호 정보파싱 오류를 제거한 상한/원인 진단. 실사용 경로로 보고하지 않음

이미지에 없는 숨김 시트·수식·좌표 메타데이터를 텍스트에만 제공하지 않는다. 필요한 정보가 시각적으로 표현될 수 없는 문제는 입력 공정 비교에서 제외하고 구조 전용 블록으로 분리한다. 자연어로 요약하는 경로를 추가한다면 누가 요약했는지, 손실된 정보, 요약 모델의 호출·비용도 기록한다.

B. 동일 출력 계약의 생성 경로 비교

1. 공통 사용자 명세와 필수 결과를 고정한다.
2. native 이미지 출력, 언어→코드→엔진, 멀티모달→코드→엔진 중 실제로 지원되고 수업 정책에 맞는 조건만 선택한다.
3. 서로 다른 모델이면 모델 규모·학습·출력 기술이 함께 바뀌는 시스템 비교로 해석한다.
4. 코드/파일 경로의 parsing·rendering·계산·검증 시간과 실패도 모두 포함한다.
5. 시각적 유사성, 의미 정확성, 기능적 편집 가능성을 합쳐 임의의 한 점수로 만들지 않는다.

이미지 생성 모델이 없는 경우 “native 생성 실패율 100%” 같은 결과를 만들지 않는다. 실험 조건 미충족으로 미실행이라고 남기고, 팀의 명시적 선택으로 입력 비교나 피드백 비교를 진행한다.

C. 같은 초기 결과에 대한 피드백 비교

MM6에서는 초안 50개를 고정하여 공유한다. 각 조건은 같은 모델의 수정 호출 1회를 사용한다. 구조 피드백 조건과 구조+이미지 조건의 차이는 추가 관찰 정보이며, 호출 수 증가 효과와 분리한다. 최초 초안의 성능은 별도 기준선으로 남긴다.

피드백용 검사기는 실제 사용자가 얻을 수 있는 구문·실행 오류만 제공한다. 숨겨진 정답 제약과 테스트 결과 전체를 모델에게 넘겨 정답 유출을 만들지 않는다. 수정 루프가 필요하면 횟수·중단 규칙을 실험 전에 합의한다.

5. 평가 데이터와 지표

50개는 50개의 독립적인 기본 업무

한 악보를 5번 다른 해상도로 렌더링한 것은 5개의 독립 악보가 아니다. 각 기본 사례의 변형은 동일한 case_id 아래에서 대응 비교하고, train/dev/test 분할은 기본 사례·템플릿 단위로 한다. 50개 평가 사례와 별도로 5–10개 개발 사례를 두는 방안을 검토할 수 있다. 데이터 생성에 모델을 쓰더라도 사람의 정답 검수와 직접 작성 요건 충족 여부를 따로 확인한다.

사례마다 다음을 남긴다.

- 사용자에게 보이는 명세, 공개 입력, 요구 산출물, 허용 도구와 금지 변경
- 파서/렌더러 버전, 이미지 해상도·글꼴, 구조 표현 방식
- evaluator 전용 정답·근거·허용 오차·의미 동치·숨겨진 테스트
- 개발/평가 구분과 원본 사례 ID, 데이터 출처·재배포 권한
- 입력·프롬프트·모델 설정 hash와 실제 요청/도구/파일 변경 기록

문제 설명·파일 이름·메타데이터에 정답이나 오류 위치가 새어 들어가지 않게 한다. 공개 benchmark는 설계 참고용이며 직접 작성 데이터를 대체하지 않는다. 공개 GitHub에는 개인 업무자료·수업 원본·권한 없는 악보나 논문 PDF를 올리지 않는다.

서로 다른 출력 형식의 비교는 공통 렌더링에서 사람이 모델 이름을 가리고 같은 rubric으로 평가하는 것이 작은 50개 연구의 한 선택지다. OCR/OMR을 evaluator로 사용하면 그 오류도 샘플 검수해야 한다. 코드 조건만 구조에서 정확하게 읽고 raster 조건만 불완전한 OCR로 읽어 얻은 차이를 모델 성능 차이로 단정하지 않는다.

과제 개선 단계로 이어질 가설

- 헤더 연결이 주된 실패라면 구조 직렬화에 부모 헤더를 명시한다.
- 연산은 맞고 인식만 틀리면 확대·영역 선택·OMR 확인 단계를 실험한다.
- 코드가 실행돼도 의미가 틀리면 일반적인 제약 검사 또는 참조 추적 피드백을 추가한다.
- 시각 피드백이 불필요한 수정을 늘리면 수정 영역을 제한하거나 보류 규칙을 둔다.
- 큰 자료에서만 성능이 나빠지면 관련 영역 선택/검색으로 기존 RAG 후보와 연결한다.

어느 가설도 아직 관찰된 결과가 아니다. 개선 전후에는 같은 평가 계약과 예산을 유지하고, 평가 데이터에 맞춰 반복 튜닝했다면 그 사실과 별도 holdout 여부를 보고한다.

6. 비용과 실행 가능성

첫 학기 범위는 기존 모델·라이브러리의 재사용이다. 새 범용 모달리티 인코더나 대규모 end-to-end 사전학습은 전제하지 않는다. Colab 같은 GPU 환경은 추론·작은 추가 학습의 후보이지만 실제 장치, VRAM, 모델 적재와 속도는 실행 전에 확인해야 한다.

수치는 실행 결과나 승인된 예산이 아니라 산식의 예다. 이미지 생성 요청, 언어 모델 요청, OCR/OMR GPU 작업은 단가·연산량이 달라 별도로 기록한다. 금액은 선택한 endpoint의 실행 시점 가격과 이미지 과금 규칙을 확인한 후 계산한다. 수업의 local/free 범위부터 확인하고 유료 모델을 자동으로 대체하지 않는다.

모델 선정 시 다음 자격을 먼저 확인한다: 입력 이미지 지원, 실제 이미지 출력 지원 여부, 텍스트/코드 출력, tool calling 필요 여부, 이용 조건과 수업 허용 여부, 체크포인트/버전, 메모리 요구. 이 문서는 어떤 모델의 현재 무료 제공·가용성도 보장하지 않는다.

실행은 별도 승인을 받은 범위에서 한 번에 한 건씩 시작한다. 실패 기록·완료 산출물을 재사용하고 자동 재시도·자동 모델 변경은 하지 않는다. 모델 호출 없이 validator·renderer·집계 코드의 단위 테스트를 먼저 할 수 있다. 생성 코드와 파일 도구는 임시 폴더·제한된 권한으로 격리한다.

무엇을 연구하면 좋은가

큰 시스템을 만드는 것보다 관찰 결과에 따라 다음 행동을 바꾸는 능력이 실제로 필요한 작은 업무를 만들고, 그 효과를 통제 비교하는 것이 중심이다. “에이전트가 필요하다”는 것은 논리적으로 다른 모든 프로그램이 불가능하다는 뜻이 아니다. 같은 정보 접근권과 자원에서 고정 절차보다 적응적 행동이 유리한지 검증하는 연구 질문이다.

기존 로컬 후보집 36개를 확인했다. 아래는 완전히 새로운 7개 분야를 발견했다는 주장이 아니라, 기존 검색·기억·도구·하네스 관심을 완료 가능한 업무와 좁은 가설로 구체화한 제안이다. 선행논문은 인접 연구의 근거이며 아래 실험의 성능을 보장하지 않는다.

공통 비교 원칙

- 기준선 1: 같은 모델이 처음에 계획/답/명령을 한 번 만든다. 상태 변경 업무는 동일한 executor로 명령을 실행해 평가한다. 실행 능력을 아예 주지 않은 모델과 비교해 승리를 만들지 않는다.
- 기준선 2: 같은 도구·자료에 접근하는 고정 workflow 또는 해당 분야의 강한 비-LLM 알고리즘.
- 실험 조건: 중간 관찰·실패·질문 답변에 따라 다음 행동을 선택하는 단일 agent.
- 같은 기본 문제와 성공 조건, 비슷한 도구/시간/token 예산을 유지한다. 모든 정보를 미리 제공하는 oracle은 진단용 상한이지 동일 비용 기준선이 아니다.
- 주된 독립 변수 하나를 먼저 선택한다. 모델 크기·기억·멀티에이전트·학습까지 동시에 바꾸지 않는다.
- 채점은 최종 DB/파일 상태·정답 수치·금지 변경·문서 근거를 우선한다. Judge는 일부 애매한 의미 판정만 보조한다.
- 50개는 선택할 한 태스크의 평가 사례 구성안이다. 새 요구사항 원문은 이번에 재검토하지 않았으므로 “50개”의 과제상 정확한 단위는 교수님 지침과 대조해야 한다.

A. 실패를 보고 다음 실험을 고르는 한국어 검색 연구원

질문: 동일한 제한 실험 예산에서, 검색 오류를 읽고 다음 설정을 고르는 agent가 random search나 고정된 튜닝 순서보다 좋은 설정을 찾는가?

구체 장면: “조사 제거는 성능을 올렸는데 어미까지 제거하니 낮아졌다. 어떤 질의 유형에서 변화가 생겼고, 다음에는 무엇을 하나만 바꾸어야 할까?”

행동: 실패 질의/문서 표본 조회 → 오류 가설 작성 → 허용 설정 하나 변경 → dev 평가 → 이전 결과와 비교 → 다음 실험 또는 중단. Kiwi 품사 필터, BM25 설정, hybrid 가중치 중 작은 범위만 노출한다. 임의 Python 코드를 계속 생성하게 하는 과제는 아니다.

최소 범위: corpus 하나, 고정된 6–12개 설정, episode당 실험 최대 3–5회. 미리 구현한 평가 함수를 tool로 제공한다. dense embedding은 한 번 계산하고 캐시하며 구축 비용을 별도 기록한다.

50개 설계: 전문어/수치·단위/형태 변형/동의 표현/문서 경계 문제의 5유형 × 10개 작은 튜닝 mission. 각 mission에는 제한된 dev 질의와 별도 숨긴 평가 질의가 필요하다. 검색 질의 50개를 만들었다고 agent의 독립적인 튜닝 episode 50개가 되는 것은 아니다. 이 데이터 비용은 다른 후보보다 높다. 동일 corpus를 재사용하면 corpus별 일반화를 주장하지 않는다.

비교: random search, 전문가가 정한 고정 설정 순서, 오류 분석 기반 적응 선택. 모든 조건에 같은 평가 횟수를 준다. 작은 설정 공간의 전수 평가 결과는 agent에게 숨긴 oracle로 사용 가능하다.

지표: 숨긴 test의 nDCG@10/MRR/Recall@k, dev에서의 최적 설정 대비 regret, 최적 성능까지의 실험 횟수, 전체 GPU/CPU 시간. Agent에 test 점수를 반복해서 보여주지 않는다. 통계적 일반화와 개발 목표 최적화를 구분한다.

GPU: dense/reranker 추론, 모델 반복 실행. 추가 학습은 선택사항. 부담: 구현 중간, 평가 mission 작성 중간~높음.

선행연구: DS-Agent, ICML 2024는 사례 기반 추론과 피드백을 통한 데이터 과학 반복 실험을 다룬다. 한국어 검색 설정 선택은 여기서 제안하는 축소·응용 실험이며 논문의 직접 결과가 아니다.

B. 질문할 줄 아는 데이터 분석가

질문: 언제 사용자의 의도를 확인하고, 언제 DB를 조회하며, 언제 답을 멈춰야 하는가?

장면: “이번 학기 활동 적은 회원을 추려줘.” 활동은 출석인가 회비 납부인가? 휴학생은 제외하는가? 기준이 정해져야 올바른 SQL과 결과가 달라진다.

행동: schema 조회 → 부족한 정의 식별 → 사용자 질문 또는 데이터 탐색 → query 실행 → 결과 검증. 모든 질문을 매번 묻는 것도, 근거 없이 추정하는 것도 실패 비용이 있다.

최소 범위: 가상 동아리/수업 DB 하나, SQLite, 4개 정도의 도구. 실제 개인정보와 계정은 쓰지 않는다. 함수형 simulator가 시나리오에 적힌 숨은 사용자 조건만 답하고 임의로 정답을 만들어내지 않게 한다.

50개 설계: 용어 정의/대상 범위/기간/조건 충돌/이미 충분히 명확한 요청 각 10개. 문장만 바꾼 동일 시나리오는 독립 표본으로 세지 않는다.

비교: 질문 없이 추정, 정해진 체크리스트 질문, 적응적 질문. 질문 수/턴/token을 제한하며 동일한 숨은 사용자 조건을 공유한다.

지표: 정답 result set 또는 DB 상태, 잘못된 대상 처리율, 불필요한 질문 수, 성공까지의 턴 수, 조건 누락. 필요한 질문을 0번 하는 시스템에 유리한 단일 비용 점수를 쓰지 않고 성공-질문 수 곡선을 함께 제시한다.

GPU: 공개 모델 동일 조건 반복 추론, 선택적으로 질문 필요 여부의 작은 분류기. 부담: 중간. 자동 평가와 발표 데모가 비교적 명확하다.

선행연구: BIRD-INTERACT, ICLR 2026는 모호한 요구, 사용자 clarification, 실행 오류와 CRUD 상태 평가를 결합한다. 전체 benchmark를 그대로 재현할 필요는 없다.

C. 변경사항을 전파하는 지식 유지보수 agent

질문: 사실 하나가 바뀔 때, 오래된 설명과 파생 계산을 필요한 곳만 수정할 수 있는가?

장면: “행사 인원이 30명에서 24명으로 바뀌었어. 장소 안내, 식비, 준비물 수량을 갱신하되 이미 확정된 대관료와 과거 회의록은 바꾸지 마.”

행동: 원본 변경 확인 → 관련 문서/규칙 탐색 → 영향받는 항목 추론 → patch 생성 → 전체 일관성과 보존 조건 검사 → 필요할 때만 수정. 생성된 결론의 근거가 달라지면 파생 결론도 재검증해야 한다.

최소 범위: 가상 프로젝트당 Markdown/JSON 5–10개. 처음에는 Excel·캘린더·메일 실서비스를 붙이지 않는다. 도구는 파일 읽기, 검색, 허용 patch, 검증 정도로 제한한다.

50개 설계: 단일 사실/파생 수치/예외·보존/상충된 출처/취소·과거 이력 각 10 episode.

비교: 전체 문서 일괄 재작성, 검색으로 관련 파일만 편집, 의존성과 검증을 사용하는 agent. 고정된 명시적 의존성 그래프의 규칙 기반 갱신도 강한 기준선으로 둔다. 그래프가 완전히 주어지는 경우 agent가 불필요할 수 있다.

지표: 필요한 변경의 precision/recall, 파생 값 정확도, 변경 금지 영역 보존, 남은 모순 수, 잘못된 완료 보고. 정답 파일 문자열 하나 대신 허용 상태와 의미적 동치를 정의한다.

GPU: 의미적 영향 대상 판별·reranking·공개 모델 반복 평가. 부담: 중간. NLP 의미 판단과 상태 평가를 연결하기 좋다.

선행연구: MemTxn, arXiv 2026는 출처가 뒷받침하는 기억 갱신, 충돌 버전 선택, 상태 복구를 다룬다. preprint 초록을 확인했으며 문서 전반의 변경 전파를 완전히 해결한 논문으로 확대 해석하지 않는다.

D. 무엇을 사람에게 물어볼지 고르는 라벨링 연구원

질문: 제한된 사람 라벨 예산을 단순 불확실도 순서보다 잘 쓸 수 있는가?

장면: 한국어 문의를 환불/변경/정보요청 등으로 분류하는데, agent가 모델의 실패와 중복을 보고 사람에게 라벨을 요청할 예시를 고르고, 필요하면 label 정의의 모호함을 확인한다.

행동: 예측/오류 분포 조회 → 다음 예시 선택 → oracle 라벨 요청 → 분류기 갱신 또는 ICL 예시 갱신 → dev 평가 → 다음 예산 배분. 단순히 기존 active learning 코드의 출력을 말로 읽어주는 경우 agent의 기여가 없다.

최소 범위: 분류 태스크 하나, 고정 label taxonomy, 공개 또는 직접 작성한 training pool. taxonomy 개정은 난도를 올리는 후속 실험으로 남긴다. 학부 프로젝트는 사람이 붙인 oracle을 파일로 숨겨두고 선택된 사례만 공개하는 방식으로 비용을 줄일 수 있다.

50개 설계: 평가용으로 명확/복합 의도/경계/드문 클래스/분포 변화 각 10개. training pool과 개발셋은 별도로 필요하다. 평가 50개만으로 학습과 선택 정책 개발까지 하면 안 된다.

비교: random, uncertainty sampling, diversity/coverage 기반 선택, agent 선택. 라벨 개수뿐 아니라 추가 LLM 호출과 학습 비용도 기록한다.

지표: macro-F1, 클래스별 recall, 동일 라벨 예산에서의 성능, 예산-성능 곡선 아래 면적, 중복 선택률, 전체 비용. 라벨링 에피소드는 몇 차례 반복하되 50개 평가 문장이 50개 독립 선택 정책 실행은 아니라는 점을 구분한다.

GPU: 작은 텍스트 분류기 학습/임베딩, 선택적 경량 fine-tuning. 부담: 중간~높음. 모델 학습을 실제로 배우고 싶을 때 적합하다.

선행연구: LLM-driven active learning, LAW 2024는 LLM과 사람 주석의 결합을 다룬다. CoverICL, EMNLP 2024는 적은 주석 예산에서의 적응적 예시 선택을 다루므로 agent가 반드시 넘어야 할 강한 알고리즘 기준선의 참고가 된다.

E. 한국어의 완곡한 요청을 실제 행동으로 옮기는 agent

질문: 명령문에서는 잘하는 모델이 생략·정정·완곡 표현·예외가 들어가면 잘못 행동하는가?

장면: “그분은 이번에는 빼는 게 낫겠네요. 아, 명단에서 지우라는 건 아니고 알림만요.” agent가 대상·행위·범위를 확인하고, 삭제하지 않은 채 모의 알림 설정만 수정해야 한다.

행동: 지시 해석 → 대상/현재 상태 조회 → 필요할 때 확인 질문 → 수정 → 상태 확인. 단순 문장 분류와 실제 실행을 분리해 어디서 실패했는지 본다.

50개 설계: 생략/간접 요청/정정/부정·예외/대상 모호성 각 10개. 각 사례의 직접적 명령 버전과 자연스러운 한국어 버전을 paired로 비교한다. 50쌍이면 100회 조건 입력이지만 기본 사례는 50개다.

비교: 원문 직접 실행, 구조화된 의도/제약 추출 후 실행, 불확실한 경우 확인하는 agent. 같은 tool set과 요청 의미를 유지하고 원문 자체가 애매하면 clarification을 정답 행동으로 인정한다.

지표: 의도 슬롯 F1, 올바른 최종 상태, 비허용 행동률, 질문 효율, 표현 변형에 따른 성공률 차이. 해석 단계가 맞는데 실행만 실패한 경우를 별도 집계한다.

GPU: 공개 모델 반복 평가; training/evaluation 표현 틀을 분리한 작은 의도 모델 학습은 확장 후보. 부담: 중간. 한국어 데이터 검수 부담이 있지만 NLP 수업과의 연결이 직접적이다.

선행연구 연결: tau 계열의 사용자-도구-상태 평가를 한국어 화용적 변형에 적용하는 제안이다. 이번 조사에서 이 정확한 한국어 가설을 검증한 논문이나 최초성을 확인한 것은 아니다.

F. 사용자를 안내하며 원인을 좁히는 실습환경 진단 agent

질문: 모든 해결책을 나열하는 답변보다, 진단 질문과 안전한 확인 명령을 골라 원인을 좁히는 방식이 실제 복구에 유리한가?

장면: “노트북에서 import가 안 돼요.” interpreter 불일치, 미설치, 작업경로, 파일명 충돌, 실행 순서 중 무엇인지 처음에는 모른다. 한 번의 관찰 결과가 다음 확인을 결정한다.

최소 범위: Windows/Docker 전체를 원격 관리하지 않고, 가짜 환경 상태와 안전한 함수 또는 disposable Python sandbox로 다섯 종류의 장애만 구현한다. 실제 PC 삭제·계정 변경·유료 호출은 금지한다.

50개 설계: 환경 불일치/패키지/경로/이름 충돌/실행 상태 각 10개. 같은 오류 문구에 서로 다른 원인을 배정해 패턴 암기로 답을 맞히지 못하게 한다.

비교: 고정 troubleshooting checklist, 첫 설명만 보고 일괄 처방, 관찰 기반 진단 agent. 사용자 역할은 상태에 근거한 함수형 simulator를 우선한다.

지표: 원인 식별, 실제 복구, 진단/수정 횟수, 불필요한 설치·변경, 위험한 행동, 완료 보고 정확도. 코드 실행 오류와 simulator 설계 오류를 분리한다.

GPU: 공개 모델 반복 추론 중심; 필수는 아님. 부담: 중간~높음. simulator를 좁히면 학부 프로젝트가 되지만 실제 운영환경까지 연결하면 크게 팽창한다.

선행연구: tau2-Bench, ICML 2026는 사용자와 agent가 함께 상태를 바꾸는 dual-control 환경에서 소통·조정·추론을 나누어 평가한다. 최신 저장소를 무조건 옛 논문 버전과 동일하다고 보지 말고 사용할 commit을 고정한다.

G. 그럴듯한 실험 결론을 반박하는 재현성 감사 agent

질문: 결과 표만 보면 그럴듯한 NLP 개선 주장을, 추가 실험과 설정 검증으로 반박하거나 확인할 수 있는가?

장면: “조사를 제거하면 한국어 검색은 언제나 좋아진다.” agent가 query 유형별 분석, 예외 사례, 같은 조건 재실행을 골라 주장이 관찰 범위를 넘어섰는지 판단한다.

최소 범위: 검색 또는 텍스트 분류 중 하나. 작은 설정/결과 파일과 실행 가능한 고정 함수만 제공한다. 자유로운 논문 재현/코드 작성 전부를 맡기지 않는다.

50개 설계: split 누수/중복 데이터/평가 분모/통제되지 않은 설정/정상 주장 각 10개. 정상 사례를 넣어 무조건 “문제 있다”고 말하는 시스템을 배제한다. 가짜 오류를 주입한 사례는 합성 benchmark임을 명시한다.

비교: 보고서 읽기만 하는 reviewer, 고정 진단 검사 목록, 관찰에 따라 재실험을 선택하는 agent. 추가 평가 횟수와 접근 가능한 파일을 통제한다.

지표: 잘못된 주장 탐지 precision/recall, 정상 주장 오탐, 원인 위치 정확도, 반례/재실행의 유효성, 추가 실험 비용. 단순 서술형 Judge 점수보다 실제 로그와 재실행 결과를 우선한다.

GPU: 작은 NLP 모델/검색기의 재실행과 조건 비교. 부담: 중간~높음. agent 개발보다 진단 사례의 현실성과 명확한 gold 설계가 중요하다.

선행연구: Curie, arXiv 2025는 실험의 신뢰성·통제·해석 가능성을 다룬다. 이번에 확인한 OpenReview 검색 결과는 withdrawn submission으로 표시되어 학회 채택 논문으로 표기하지 않았다. 여기의 오류 주입 감사 태스크는 별도 제안이다.

Pro와 GPU를 쓰는 방법

개발자 측 활용과 평가 대상 시스템을 분리한다.

- ChatGPT Pro/Codex: 논문 설명, 가설의 허점 검토, 구현·테스트·오류 분석 지원. 도구/환경 코드는 강한 개발 보조 모델로 미리 만든다.
- GPU: checkpoint·prompt·설정을 고정한 공개 모델 반복 평가, embedding/reranker 사전 계산, 필요 시 작은 분류기 학습. GPU를 쓰기 위한 불필요한 fine-tuning을 넣지 않는다.
- 평가 대상 agent: 이미 구현된 좁은 도구를 선택해 태스크를 수행한다. 매 문제마다 실행 인프라부터 새로 만들게 하지 않는다.
- 강한 모델 대조를 추가하면 별도 축으로 기록한다. 서로 다른 시스템/harness 결과를 모델 크기 효과 하나로 해석하지 않는다.
- Pro가 자동으로 모든 API 호출 비용을 대신하는 것은 아니다. 공식 OpenAI 문서는 구독 사용량과 API 요금을 구분한다. 실제 사용할 인증/실행 경로와 제공 한도를 별도로 확인해야 한다. 공식 가격 안내

GPU 종류와 남은 크레딧을 이번에 확인하지 않았으므로 특정 모델 적재 가능성·학습 시간·총비용은 확정하지 않는다.

최소 실험 규모와 실패 방지

우선 개발 사례 5–10개로 도구·채점기를 검증하고, 평가 사례는 별도로 잠근다. 기본 설계는 모델 1종 × 조건 3개 × 평가 50개 = 150 episode다. 평균 4번 모델을 부르면 약 600회이며 simulator/Judge/학습자료 생성/개발 호출은 별도다. 3회 반복하면 약 1,800회가 된다. 이 숫자는 측정치나 실행 승인이 아니라 비용 산식이다.

Active learning처럼 평가 문장과 agent episode의 단위가 다른 태스크에는 위 산식을 그대로 적용하지 않는다. IR 튜닝도 검색 질의와 튜닝 mission을 구분한다. 시간·token뿐 아니라 유효한 tool 실험 횟수와 CPU/GPU 비용을 기록한다.

1. 모델이 없어도 동작하는 고정 도구와 정답 검사기부터 만든다.
2. 한 모델·한 조건·한 사례를 먼저 실행해 실제 소요를 계측한다.
3. 태스크 성공, 모델 응답 실패, 도구/환경 실패, evaluator 실패를 별도 저장한다.
4. 각 요청/도구 단계 직후 기록한다. 자동 재시도·모델 변경은 기본값으로 끈다.
5. 새로운 실험 실행은 사용자 승인과 호출/시간 예산을 받은 뒤 수행한다.
6. 50개에서 작은 성능 차이를 보편적 우월성으로 주장하지 않는다. 짝지은 사례별 차이와 유형별 실패를 함께 보고하고 데이터 생성 원본/템플릿을 묶어서 불확실성을 추정한다.

1. 연구의 중심

“모델이 한 번에 답하는 것보다, 관찰을 추가하고 행동을 바꾸는 정책이 언제 유리한가?”를 묻는다. 에이전트가 유일한 해결 방법이라고 전제하지 않는다. 고정 파이프라인, 결정론적 규칙, 비학습 탐색도 강한 비교 대상이다.

- NLP: 자연어의 의미 차이가 목표·검색 근거·필요한 행동을 실제로 바꾸어야 한다.
- 멀티모달: 이미지·레이아웃·시각 환경이 실제 입력 또는 피드백으로 쓰여야 한다. 그림 파일을 출력한다는 사실만으로 시각 피드백 에이전트가 되지는 않는다.
- Agent: 관찰 → 행동/도구 → 새로운 관찰 → 후속 결정이 있어야 한다.
- RL: 보상에 따라 행동 정책의 파라미터를 실제로 갱신해야 한다. 프롬프트 수정·자기 성찰·재시도만 하는 것은 이번 프로젝트에서 수행한 RL 학습이 아니다.

2. 실현 가능한 기본 구조

자연어 요청 ─→ 고정 텍스트 인코더 ─┐
관찰 이미지 ─→ 고정 시각 인코더 ───┼→ 작은 정책 → 도구/행동
이전 관찰·행동·남은 예산 ──────────┘              │
                              다음 관찰 ← 환경/도구 실행

정책 입력을 z_t = concat(E_text(question), E_image(observation_t), history_t, budget_t)로 만들고 πθ(action | z_t)가 행동을 고르게 한다. 학습 대상은 θ이며 기존 LLM/VLM 가중치는 고정할 수 있다. concat하므로 텍스트·이미지 벡터 차원이 같을 필요는 없다.

“합계 얼마야?”라는 질문에 아직 숫자를 못 읽었다면 확대/OCR의 가치가 높고, 숫자를 확보했다면 계산/종료의 가치가 높다. 이런 장기적 성공 가능성과 비용을 행동 가치 또는 정책으로 학습한다.

주의:

1. 임베딩 하나가 자동으로 Markov state가 되지는 않는다. 부분 화면 관찰은 POMDP에 가깝고 이력·메모리 또는 순환 정책이 필요할 수 있다.
2. 처음에 도구 하나를 고르고 끝난다면 contextual bandit으로 충분할 수 있다. 다단계 RL과 구분한다.
3. 인코더가 한국어 지시·작은 기호를 구분하지 못하면 작은 정책도 복구할 수 없다. 지각 성능을 먼저 확인한다.
4. 작은 정책도 매 step마다 VLM을 호출하면 비싸다. 정책 계산과 환경 실행 비용은 다르다.
5. 이산 소규모 상태에는 tabular Q-learning, 벡터 입력에는 작은 정책망/DQN/PPO 등을 검토할 수 있다. 상태·행동 규모를 보고 선택한다. 이 목록이 수업의 현재 진도를 뜻하지는 않는다.

A. 어디를 더 봐야 하는지 학습하는 독해 에이전트

예시: “이 표에서 전년 대비 증가율이 가장 높은 항목과 수치를 알려줘.”

축소 이미지와 질문에서 시작한다. 확대 위치는 사전 격자나 탐지된 영역으로 제한한다. 자유로운 좌표·코드 생성까지 처음부터 학습시키지 않는다.

- 관찰: 질문, 확인한 영역, OCR 결과, 남은 예산.
- 행동: 확대, OCR, 다른 영역 확인, 확보한 숫자 계산, 답 제출.
- 보상: 정답 여부를 중심으로 행동 비용 차감. 정답은 채점기에만 제공.
- 비교: 전체 이미지 1회 / 모든 영역 고정 스캔 / 규칙 기반 선택 / 학습 정책. 가능하면 프롬프트 기반 적응 정책 추가.
- 평가 50개: 숫자 읽기·두 값 비교·비율 계산·범례 연결·작은 글씨/복잡한 배치 각 10개. 원본 문서별 train/test 분리.
- 지표: 정답률, 숫자 허용오차 내 정답률, 근거 영역 적중, 도구 횟수, 비용, 지연시간.
- 확장: 해상도, distractor 수, OCR 오류, 관찰 예산.

문헌: V는 고해상도 이미지의 중요한 세부를 찾는 guided visual search를 제안한다. DeepEyes는 이미지 기반 능동 관찰을 end-to-end RL로 학습한다. 작은 정책망을 사용하는 것은 우리 팀의 축소 설계이며 논문 결과가 그대로 이전된다는 뜻이 아니다. V, CVPR 2024, DeepEyes

B. 검색 경로와 종료 시점을 학습하는 멀티모달 RAG

예시: “두 상품 설명은 비슷한데, 표에서 유지비가 낮고 그래프에서도 안정적인 쪽을 찾아줘.”

텍스트·표·차트가 섞인 컬렉션을 고정한다. Kiwi/BM25와 이미지 임베딩 검색을 장단점이 다른 행동으로 본다.

- 관찰: 질의, 검색 점수·후보, 확인한 시각 근거, 사용 예산.
- 행동: BM25, 이미지 검색, 질의 수정, 후보 페이지 확대, 결과 확정.
- 보상: 올바른 문서·근거 또는 최종 정답, 검색/추론 비용 차감.
- 비교: BM25 / dense / 고정 hybrid / 규칙 라우터 / 학습 라우터. 순차 정책이면 고정 순서 탐색도 비교.
- 평가 50개: 어휘 일치·의미적 재표현·표 수치·시각 속성·복수 근거 결합 각 10개.
- 지표: Recall@k, MRR 또는 nDCG, 정답률, 근거 정확도, 호출 수, 지연시간, 인덱스 메모리·구축 비용.
- 확장: 문서 수, 시각 정보 비중, 노이즈.

한 번의 경로 선택은 contextual bandit으로 시작할 수 있다. 검색 결과를 본 뒤 다시 행동하면 sequential RL이다. 학습 비용과 조회당 비용을 분리해야 효율화 주장이 성립한다.

문헌: V-Retrver는 후보 검색 후 시각적 증거 확인과 재순위화를 결합하고 SFT·rejection refinement·RL의 단계적 학습을 제안한다. 우리의 고정 모델+작은 라우터는 별도 가설이다. 확인 자료는 arXiv preprint다. V-Retrver

C. 한국어 지시를 따르는 작은 시각 세계

예시: “파란 공은 건드리지 말고, 문을 연 다음 빨간 상자 옆의 열쇠를 가져와.”

작은 GoTo/Pickup에서 시작해 관계·순서·부정 조건을 추가한다. 한국어 표현과 새로운 금지 조건은 기존 영어 환경을 실행하는 것만으로 생기지 않으므로 별도 구현·검증이 필요하다.

- 관찰: 지시, 현재 시야 이미지, 방향·이전 행동 등 허용 정보.
- 행동: 이동, 회전, 집기, 놓기, 문 열기 등 선택한 환경의 행동.
- 보상: 목표 충족, 금지 행동 위반 패널티, 행동 비용.
- 비교: 동일 관찰의 비학습 정책 / imitation learning / RL. 구조화된 목표와 전체 환경을 받는 planner는 privileged 상한 참고로 구분.
- 평가 50개: 속성 지시·공간 관계·순서·부정·표현 변형 각 10개. 새 배치와 새 표현 조합을 분리해 일반화 평가.
- 지표: 성공률, 금지 행동률, 평균 step, 환경 step 대비 성능, 미관측 조합 성공률.
- 확장: 직접 한국어 인코딩 vs 명시적 목표로 변환, 전체 vs 부분 시야, 언어/시각 제거 실험.

주의: MiniGrid의 기본 image 배열은 이름과 shape만 보고 RGB라고 생각하면 안 된다. compact object/color/state encoding과 RGB wrapper를 구분한다. 실제 시각 비교는 RGB, 상징 관찰은 별도 조건으로 표시한다. mission을 없애는 wrapper도 있으므로 입력 구성을 확인한다. 공식 wrappers 문서

문헌: BabyAI는 언어 지시를 환경 행동에 접지하는 grounded language learning과 sample efficiency를 연구한다. BabyAI 환경은 현재 MiniGrid에서 유지된다. BabyAI, MiniGrid, 환경 목록

D. 질문할까, 그냥 행동할까?

예시: 여러 상품이 있는 그림에서 “저번 것보다 작은 빨간 걸 골라줘.”

정보가 부족한 경우와 그림을 더 보면 해결되는 경우를 섞는다. 무조건 질문하거나 추측하는 정책을 둘 다 실패하게 설계한다.

- 관찰: 장면, 발화, 이전 대화에 공개된 단서.
- 행동: 속성 확인 질문, 영역 확대, 후보 선택, 필요 시 보류.
- 보상: 올바른 선택, 잘못된 실행 패널티, 질문/관찰 비용.
- 비교: 질문 안 함 / 항상 질문 / 불확실성 임계값 / 학습 정책.
- 평가 50개: 명확한 지시·언어적 모호성·시각적 모호성·복합 모호성·질문해도 해결 불가 각 10개.
- 지표: 성공률, 잘못된 실행률, 불필요한 질문률, 해결 가능한 문제의 과잉 보류율, 질문 수.
- 최소 환경: 물체·색·크기·좌표로 합성 장면을 만들고 숨겨진 의도에 일관되게 답하는 규칙 simulator 사용.

질문 목록과 simulator를 고정하면 사용자 역할 LLM의 비일관성과 비용을 줄인다. 자유 대화 전체로 일반화하지 않는다. 한국어 지시어·생략·간접 요청으로 NLP 성격을 강화할 수 있다. grounded language/active information acquisition에서 확장한 제안이지 동일 논문 재현이 아니다.

E. 자연어 조건에 맞게 만들고, 보고, 수정하기

예시: “막대그래프 항목명이 겹치지 않게 하고, 강조 대상만 파란색으로 표시해줘.”

SVG 차트 한 종류 또는 제한된 레이아웃 하나로 시작한다. 편집기 전체나 자유 코드 생성을 RL로 학습시키지 않는다.

- 관찰: 요청, 렌더 이미지, 공개 검증 결과.
- 행동: 글꼴 축소/여백 증가/레이블 회전/색 변경/재렌더/종료.
- 보상: 수치·요구 조건 충족, 겹침·잘림 감소, 수정 비용.
- 비교: 단발 생성 / 구조 검증만 사용 / 시각 피드백 고정 정책 / 학습 수정 정책.
- 평가 50개: 라벨 겹침·잘림·색 조건 오류·수치 오류·복합 오류 각 10개.
- 지표: 모든 조건 충족률, 정상 영역 손상률, 수정 횟수, 수치 정확도, 시간.
- 채점: 원자료와 수치 비교, 렌더/기하 검사로 배치·잘림 확인. 미적 품질은 블라인드 사람 평가를 보조로 사용.

시각 입력이 항상 우월하지 않다. 숫자·기호 조건은 구조 도구가 더 정확할 수 있다. “어떤 오류에 어떤 피드백이 필요한가?”가 질문이다. 시각 입력 제거와 강한 결정론적 수정기를 포함한다. VisTA의 도구 선택 관점은 참고하되 생성·수정 성능을 해당 논문이 검증한 것으로 주장하지 않는다.

F. 악보의 어느 부분을 다시 읽을지 학습하기

예시: “이 선율에서 세 번째 마디의 음과 박자를 읽어줘.”

인쇄 단선율 4~8마디, 제한된 조표/박자로 좁힌다. 손글씨·합주 총보·오디오·생성을 모두 다루지 않는다.

- 관찰: 악보 이미지, 질문, OMR 후보, 박자·음역 검증 결과.
- 행동: 마디 확대, OMR 재실행/다른 전처리, 후보 비교, 답 제출.
- 보상: 음정·길이·마디의 정확성, 처리 비용 차감.
- 비교: 전체 이미지 VLM / OMR→기호 처리 / 고정 전처리 / 선택적 재독해.
- 평가 50개: 음높이·음길이·쉼표·임시표·마디/박자 조건 각 10개. 원본 선율 단위 분리.
- 지표: pitch/duration 정확도, note tuple F1, 요청 대상 정확도, 도구 횟수. 박자 합만 맞는 오답은 성공이 아니다.
- 데이터: 직접 생성하거나 이용 조건을 확인한 기호 악보를 렌더링하고, 원본 기호는 채점기에만 둔다.

성패는 기존 OMR/인코더가 기호를 읽는지에 좌우된다. RL 전에 지각 성능을 확인한다. 음악 도구·데이터셋 라이선스와 직접 선행연구는 이번 조사에서 확정하지 않았다. 능동 관찰을 음악에 적용하는 가설이지 관련 연구가 없다는 신규성 주장이 아니다.

5. 50개 평가와 RL 학습은 별개

- 최종 50개는 정책 학습·프롬프트 튜닝·reward 계수 선택에 사용하지 않는다. train/dev를 별도 구성.
- RL에는 많은 상호작용이 필요할 수 있다. 합성 환경, 고정 도구 출력 캐시, 기존 train split 우선 검토.
- 동일 문서·장면·선율의 표현만 바꾼 사례가 train/test에 걸치지 않게 원본별 group split.
- 번역본을 만든 것만으로 한국어의 모든 현상을 연구한 것은 아니다.
- 동일 시험 사례의 정책별 성공/실패를 짝지어 비교하고 가능하면 여러 학습 seed 사용. 50개 중 1개는 2%p이므로 작은 차이를 확정적 우열로 해석하지 않는다.
- 파생 질문이 연관되면 원본 단위 집계 또는 bootstrap.
- 최종 성공률과 비용을 함께 보고 누적 보상은 보조 지표로 사용. reward hacking 확인.
- 학습 곡선은 wall-clock과 환경 step/에피소드/도구 호출을 함께 기록.

6. 비용 통제

개발용 5~10개로 환경·지각 상한 확인 → 비학습 baseline 완성 → RL 추가 순서로 진행한다. 같은 관찰·행동 예산을 제공한다.

예시 계산이며 승인된 실행 예산은 아니다:

- 50개 × 3조건 = 150개 평가 에피소드. 모두 3회 반복하면 450개.
- 모든 에피소드가 평균 5회 유료 VLM 호출을 요구하면 각각 750회/2,250회. 로컬 정책 step과 API 호출은 다르다.
- RL 학습·데이터 생성·검증 모델 비용은 별도이며 더 클 수 있다.
- 특정 학습 정책만 여러 seed로 반복하면 실제 조합대로 다시 계산한다.

절약:

1. 답변 모델·OCR·렌더러 고정.
2. 가능한 이미지 특징과 도구 출력 캐시. 시험 캐시는 시험 입력으로만 생성하고 정답은 노출하지 않음.
3. 작은 정책 또는 작은 CNN+정책을 로컬/Colab에서 학습. 대형 모델 호출은 제한된 비교 조건에 사용.
4. 실제 온라인 지연시간과 캐시 실험 시간을 분리하고 캐시 준비 비용 기록.
5. 최대 step·호출 수·GPU 시간·비용 상한을 정하고 파일럿 뒤 확대 결정.

ChatGPT Pro는 연구 설계·코드 검토·오류 분석 등 개발 보조로, 반복 학습은 별도 GPU/로컬 런타임으로 설계한다. 구체적 상품 가격과 남은 GPU 크레딧은 확인하지 않았다.
