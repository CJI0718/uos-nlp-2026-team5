이 후보집을 읽는 방법

목표는 ‘유행하는 방법을 구현하기’가 아니라 Agent가 맡을 업무를 정하고, 조건을 바꾸었을 때 무엇이 좋아지거나 나빠지는지 설명할 수 있는 연구를 찾는 것이다. 지금은 한 주제로 좁히지 않는다.

범위: 5개 주제 × 6개 후보 = 30개. 각 후보의 50개 구성은 앞으로 직접 작성할 평가 시나리오의 설계안이다. 데이터나 실험 결과가 이미 만들어졌다는 뜻이 아니다. 비교 조건 3개, 개발용 사례, 반복 실험 등은 제안이며 과제의 추가 의무가 아니다.

각 후보 제목을 누르면 업무 예시, 50개 유형별 배분, 정답 정보, 비교 조건, 지표, 구현 부담, 확장 방향이 펼쳐진다. 마지막에는 논문 링크와 해석 시 주의점을 모았다. 주제 사이 경계는 겹친다. RAG를 메모리에 쓰거나, ReAct 실행을 harness가 관리하는 연구도 가능하다.

  • 50개는 무엇인가? 선택한 한 태스크의 평가 사례 50개다. 5개 주제를 모두 구현하거나 50개의 서로 다른 서비스를 만들자는 뜻이 아니다. 과거 이력 → 새 요청 → 기대 상태로 묶인 하나의 에피소드도 사례가 될 수 있다.
  • Agent성은 어디에 있는가? 근거 수집, 다음 도구 선택, 상태 갱신, 검증, 중단 중 무엇을 시스템이 결정하는지 드러낸다. 단순 검색 성능 측정도 중요한 구성요소 실험이지만, 최종 업무 성공에 어떻게 연결되는지까지 보여주면 Agent 과제로 설명하기 쉽다.
  • 다중 Agent가 필수인가? 일반적인 Agent 연구가 반드시 multi-agent일 필요는 없다. 수업에서 별도 요구한 경우만 따르며, 이 후보집의 대부분은 단일 Agent로도 가능하다.
  • 논문과 실험 제안은 구분: ‘비교 조건’과 ‘50개 구성’은 이 과제에 맞춘 제안이지, 인용 논문의 실험을 그대로 옮긴 것이 아니다. 논문 방법 전체의 재현이나 추가 학습도 기본 전제가 아니다.

무엇을 근거로 가져와야 정확하고 효율적으로 업무를 끝낼 수 있는가?

정답과 판정 코드는 평가기 쪽에 두고 해결 Agent에게 노출하지 않는다. 공개 데이터셋은 문제 형식과 평가 규칙의 참고 자료로 쓸 수 있지만, 그대로 50개를 잘라 쓰는 것이 ‘직접 작성’ 요건을 만족한다고 단정하지 않는다. 모델을 초안 작성에 보조로 쓰는 허용 범위도 교수님께 확인할 사항이다.

평가 제작 순서 제안

  1. 업무 범위와 성공 조건: 무엇을 입력받고 어떤 최종 상태면 성공인지 먼저 적는다.
  2. 작은 개발용 사례: 평가 50개와 별도의 몇 개로 도구와 채점기가 작동하는지 확인한다. 이것은 제안이지 추가 과제 요구가 아니다.
  3. 50개 설계: 유형별 사례, 정답, 허용 대안, 근거, 실패 분류를 작성한다. 같은 문장을 숫자만 바꾼 사례가 대부분을 차지하지 않게 한다.
  4. 교차 검토: 다른 조원이 Agent를 실행하지 않고도 정답을 판정할 수 있는지 확인한다. 모호한 사례는 평가 전에 고친다.
  5. 평가본 고정: 조건별로 같은 50개와 동일한 자료·도구 상태를 제공한다. 결과를 보고 불리한 사례를 빼지 않는다.
  6. 실패 분석 후 개선: 한 가지 원인을 겨냥한 변경을 한 뒤 같은 고정 평가본에 재평가하되, 그 평가본에 맞춘 개선이라는 한계를 명시한다. 가능하면 추가 독립 사례로 확인한다.

50개와 실행 횟수는 다르다. A1의 경우 50개 기본 업무 각각에 정상 자료와 방해 자료를 붙이면 조건당 100회 실행한다. 여전히 독립적인 기본 사례는 50개다. 메모리에서도 같은 사람의 연속된 질문 50개를 독립적인 50명/50에피소드와 동일하게 취급하지 않는다.

작성 시간도 별도 비용이다. 예를 들어 사례당 10–30분이라는 가정을 두면 50개 초안만 약 8.3–25인시이며, 교차 검토와 수정은 추가다. 긴 이력·표·브라우저 작업은 이 범위를 넘을 수 있다. 실제 제작 시간을 측정한 추정치가 아니다.

무엇을 metric으로 측정할까?

모든 후보에 지표 10개를 붙일 필요는 없다. 주된 업무 성공 지표 1개 + 원인 진단 1~2개 + 비용 지표로 시작하고, 안전성 연구에서는 정상 업무 효용도 함께 둔다. 아래 정의는 과제 설계를 위한 제안이다.

비교가 흔들리지 않게 하는 최소 장치

  • 한 번에 하나의 축: 같은 base model, 문제, 자료, 도구 권한, 출력 요구를 유지한다. 모델까지 비교하면 별도 실험 축으로 보고한다.
  • 실제 자원 제한: 같은 호출 수만으로 공정하지 않을 수 있다. 입력/출력 token과 지연도 기록한다. 서브에이전트가 더 많은 호출을 쓰면 그 증가를 숨기지 않는다.
  • 채점의 우선순위: 상태 검사·정답 수치·명시적 제약 → 사람이 검증 가능한 rubric → 필요한 부분만 LLM judge. Judge를 곧 정답으로 취급하지 않는다.
  • Judge 통제: 사용하는 경우 모델/프롬프트를 고정하고, 시스템 이름을 가리고, 답 제시 순서를 통제한다. 일부를 사람이 다시 보며 일치·불일치를 기록한다.
  • 실패 보존: 빈 답, 잘림, 파싱 오류, timeout을 성공에서 제외하고 원인을 남긴다. 인프라 오류와 과제 수행 실패를 나누되 전체 시도 수를 숨기지 않는다. 재실행 정책은 결과를 보기 전에 정한다.
  • 50개의 한계: 사례 하나가 성공률 2%p다. 독립 사례 50개에서 성공률이 50% 근처면 단순 근사 95% 불확실성 폭이 약 ±14%p일 수 있다. 작은 차이를 ‘우월함 입증’으로 표현하지 않는다. 같은 사례를 공유하는 조건은 paired 비교/사례 단위 bootstrap을 고려한다.
  • 반복 실행: 확률적 변동을 보려면 반복이 유용하지만 비용도 곱해진다. pass@k(여러 시도 중 하나라도 성공)와 tau-bench의 pass^k(여러 시도 모두 성공)는 서로 다른 질문이다. 기본 성공률만으로 시작해도 된다.

구현 난이도와 비용의 읽는 법

아래 수치는 실행 결과나 모델 견적이 아니다. Python에 익숙한 사람이 작은 로컬·모의 환경을 만든다는 가정 아래의 계획용 구간이다. 논문 재현 수준의 구현, 공개 서비스, 모델 학습은 포함하지 않는다.

표시주요 구현 부담작동하는 작은 비교 실험까지의 예시 범위
D1 · 비교적 낮음간단한 함수·schema·상태 검사, 짧은 문맥, 외부 시스템 의존이 작음약 2–4인일 가정
D2 · 중간검색 인덱스, 다단계 도구, 시간·기억 관리, 비교 조건 및 검증 코드약 5–8인일 가정
D3 · 높음그래프/위키 구축, 복잡한 PDF·UI, 다중 역할, 장애 후 재개·일관성약 9–15인일 이상 가정

인일은 하루 1명의 작업량이라는 계획 단위이며 실제 일정 보장이 아니다. 데이터 50개 작성·교차 검토, 논문 읽기, 발표·보고서 준비는 별도다. 동일 후보도 모의 환경으로 좁히면 난도가 내려가고 실서비스 연결을 요구하면 크게 올라간다.

예를 들어 150회 요청에 매번 입력 8,000·출력 1,000 token을 쓴다면 입력 약 120만·출력 15만 token이다. 금액은 실제로 선택한 모델의 그 시점 단가를 넣어야 한다. 여기서는 모델을 선택하지 않았으므로 달러 금액이나 무료 한도를 추정하지 않았다.

모델 2종이나 corpus 규모 3단계를 모두 교차 비교하면 해당 축도 곱해야 한다. 각 후보 카드의 호출량은 이런 추가 축을 제외한 3조건 기준이므로, 관심 변수를 모두 한꺼번에 넣으면 예산이 빠르게 커질 수 있다.

  • 무료 API: 요금이 0이어도 할당량·대기·중단 비용은 있다. 제공 여부와 제한은 실행 직전에 확인한다.
  • 로컬 모델: API 금액 대신 장비 메모리·시간·동시 실행 수가 제약이다. 현재 장비에서 속도나 모델 적재를 검증하지 않았다.
  • 검색과 Agent 호출을 분리: 로컬 BM25 검색이나 Python 계산은 보통 LLM 요청이 아니다. 외부 검색 API에는 별도 요금/제한이 있을 수 있다.
  • 비용이 가려지기 쉬운 곳: GraphRAG/Wiki의 최초 구축, 문서 업데이트, 메모리 저장, 매번 재전송되는 긴 이력, judge, 오류 후 반복 요청.
  • 상한을 먼저 정하기: 최종 선택 뒤 작은 파일럿으로 사례당 호출·token·시간을 측정해 전체 예산을 다시 계산한다. 이번 조사는 실험 호출을 수행하지 않았으며 자동 재시도·모델 전환도 하지 않았다.

조원들과 비교할 질문 — 아직 순위를 매기지 않기

  1. 어떤 실패가 가장 궁금한가? 못 찾는가, 순서를 틀리는가, 잊는가, 권한을 넘는가, 실행 환경이 방해하는가?
  2. ‘업무 한 건’의 끝은 무엇인가? 문서/답만 내는지, 모의 DB 상태를 바꾸는지, 다음 세션까지 이어가는지 정한다.
  3. 50개를 사람이 검증할 수 있는가? 모델 평가 없이도 정답 상태·근거·계산값을 확인할 수 있는 부분을 찾는다.
  4. 독립 변수 하나를 말할 수 있는가? ‘복잡한 Agent 대 단순한 Agent’보다 검색 방식, 기억 갱신, tool schema처럼 무엇을 바꾸는지 구체화한다.
  5. 좋아지지 않아도 배울 수 있는가? 어느 유형에서 왜 실패했는지와 개선 행동으로 이어지는지 확인한다.
  6. 수업과 어떻게 차별화되는가? 이미 배운 ReAct/BM25를 쓰더라도 한국어·시간 변화·권한·비용 조건 아래의 비교 가설이 새로울 수 있다. 새로운 프레임워크 자체가 필수는 아니다.
관심 있는 후보에 표시만 하고, 각각 “이 업무를 맡기는 사용자 → 실패 원인 가설 → 통제된 비교 → 정답을 아는 50개 → 개선 1가지”를 한 문단으로 써보면 논의가 구체화된다. 지금은 특정 후보를 선정하거나 우선순위를 부여하지 않았다.
