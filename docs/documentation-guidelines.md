# 팀 연구 문서 작성 지침

2026-10-29 팀 공유 안내 개편을 기준으로 정한 문서 작성 방식이다.

## 1. 처음 읽는 사람이 무엇을 하자는지 이해하게 한다

도입에서 프로젝트의 입력·행동·결과를 한 가지 사례로 보여준다. 우리가 배운 개념 중 무엇을 사용하는지, Agent의 판단이 어느 지점에 필요한지, 학부 프로젝트와 과제 요구에 왜 맞는지 설명한다. 새 팀원의 사전 지식과 지난 회의 참여를 전제하지 않는다.

## 2. Task와 metric을 함께 제시한다

각 후보는 아래 항목을 같은 순서로 설명해 비교할 수 있게 한다.

| 항목 | 작성할 내용 |
|---|---|
| 연구 질문 | 무엇을 바꾸면 어떤 능력이 달라질 것으로 보는가? |
| Task | 입력을 받아 어떤 출력을 만드는가? |
| 예시 | 실제 형태의 입력, 도구 관측, 정답과 채점 이유 |
| Agent 판단 | 도구·추가 조사·분해·종료 등 어디에서 선택하는가? |
| 데이터 | 평가 50개의 유형과 분포, 개발용 사례, 정답 검수 |
| 비교군 | 같은 모델·도구·자료·예산에서 비교할 정책 |
| metric | 무엇을 분자/분모로 세고, 어떤 실패를 구별하는가? |
| 구현 부담 | 필요한 모듈, 사람 검수, 호출·GPU 부담 |
| 다음 작업 | 작은 파일럿에서 확인할 완료 기준 |

## 3. 논문을 읽을 이유를 설명한다

각 논문은 **핵심 질문 → 구조 → 논문 결과 → 우리 적용 → 읽을 부분 → 읽고 남길 것**으로 소개한다. 결과는 해당 논문의 모델·데이터·척도와 연결하고, 우리의 예상 결과로 바꾸어 쓰지 않는다. 공식 초록·원문 Method/Results 등 확인한 자료에 연결한다.

전체 논문 목록 앞에 공통 핵심 소수와 Task별 읽기 경로를 둔다. 자세한 설명은 펼침 영역으로, 전체 목록은 검색 가능한 자료실로 제공한다.

## 4. 유의사항은 한 장으로 모은다

미실행 상태·확인 범위·해석 한계·추가 확인 항목·공유 조건을 마지막의 **범위·출처·유의사항** 장에 모은다. 본문 곳곳에서 “아직 없다”, “하지 않았다”, “필요하다”를 반복하지 않는다. 본문에서는 실제로 정리한 내용과 선택 가능한 설계를 직접 설명한다.

## 5. Markdown과 HTML을 같은 내용으로 유지한다

- Markdown을 먼저 수정하고 HTML을 생성한다.
- 목차, 후보 비교, 태스크별 논문 필터, 접는 자료실을 활용한다.
- 네 가지 주장/근거 조합처럼 선택에 따라 결론이 달라지는 설명에는 작은 상호작용을 쓴다.
- 파일·앵커 링크와 변경한 상호작용을 확인한다. 원문 PDF 파일명과 안내문의 링크를 함께 유지한다.
- 팀원 수와 현재 과제 범위를 반영한다. 관련 branch와 commit을 확인해 팀원의 최신 제안을 빠뜨리지 않는다.
- 새 문서와 과거 탐색 기록의 위치를 구분하고, README에서 현재 안내문으로 바로 진입할 수 있게 한다.
