05 / RESEARCH DESIGN

데이터·평가·비용을 먼저 설계한다

50개의 단위부터 명확하게

  1. 입력 → 초기 상태 → 가능한 행동 → 성공 상태를 정의한다.
  2. 평가 사례와 gold를 작성하고 다른 조원이 검수한다.
  3. 개발·학습 사례와 최종 평가를 분리한다.
  4. 원본 문서·장면·선율 단위로 split한다.
  5. 동일 사례를 동일 도구·예산으로 비교한다.
  6. 실패를 API·도구·정책·채점기 오류로 분해한다.

X1의 검색 질의는 튜닝 mission이 아니다. X4의 평가 문장 50개는 agent 선택 episode 50개가 아니다. RL의 시험 50개는 학습 상호작용을 대체하지 않는다.

에이전트에 유리한 비교를 만들지 않기

  • 한 번 만든 계획도 같은 executor에서 실제 실행하게 한다.
  • 규칙·고정 workflow·비학습 알고리즘을 강한 기준선으로 둔다.
  • 모델·도구·예산을 한꺼번에 바꾸지 않는다.
  • gold는 evaluator에만 두고 prompt·feedback에 누설하지 않는다.
  • 정상 사례도 포함해 무조건 질문·거절·수정하는 정책을 막는다.
  • LLM Judge보다 상태·수치·제약 검사를 우선한다.

지표 사전

평가 호출량 계산기 견적·실행 승인이 아닌 산식

150 episodes · 600 모델 요청 가정

학습·인덱스·캐시·기억 구축·judge·사용자 simulator는 별도. 모델 종류·paired 입력 등 추가 축은 해당 조건에 맞게 곱한다. X4에는 이 산식을 그대로 쓰지 않는다. 로컬 policy step과 API 호출은 다르다.

GPU 활용: 고정 공개 모델의 반복 평가, embedding 캐시, 작은 분류기·정책 학습. 큰 모델을 재학습해야 연구가 되는 것은 아니다. 실제 적재 가능성·남은 크레딧·비용은 미확인이다.

진행 원칙: 개발용 5–10개 → 결정론적 도구·검사기 → 강한 기준선 → 승인된 작은 파일럿 → 비교 확장. 모든 실험 요청은 별도 승인과 호출/시간 예산 후 수행하며 자동 재시도·모델 변경은 기본값으로 켜지 않는다.
