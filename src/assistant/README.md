# 일정 비서 (schedule assistant)

Task A의 검증 서버·Skill·게이트를 응용한 로컬 웹 앱입니다.
에이전트가 테크 행사·신제품 발표와 게임 쇼케이스·출시일을 찾고, 공식 출처로 확인한 일정만 앱 안 달력에 넣습니다.

예를 들어 "닌텐도 다이렉트 9월 9일 오후 4시"라는 기사가 있으면, 비서는 공식 공지에서 그 시각이 파리 기준임을 확인합니다.
그리고 한국시간 23:00으로 정정해서 달력에 넣고, 일정에 근거를 붙입니다.
공식 발표가 아직 없으면 넣지 않고 기다렸다가 다시 확인합니다.

## 실행

```bash
uv run python scripts/assistant_app.py serve --demo      # 가상 데이터와 가짜 모델. 비용 없음, 네트워크 없음
uv run python scripts/assistant_app.py serve             # 실제 모드: Mistral + Tavily
uv run python scripts/assistant_app.py run-once          # 터미널에서 한 번 실행
uv run python scripts/assistant_app.py serve --reset     # DB를 지우고 시작
```

- 실제 모드에는 `.env`에 `MISTRAL_API_KEY`와 `TAVILY_API_KEY`가 있어야 합니다. 앱은 이 두 이름만 읽고, 값은 화면과 기록에 남기지 않습니다.
- 브라우저에서 `http://127.0.0.1:8765`를 엽니다. 앱은 내 컴퓨터에서만 열립니다.
- 모델과 검색은 실행할 때만 호출합니다. 실행은 [지금 실행] 버튼, 설정의 "N분 뒤 한 번", "매일 HH:MM" 중 하나로 시작합니다. 자동 실행은 기본으로 꺼져 있습니다.
- 데이터는 `.assistant/demo/` 또는 `.assistant/live/`(Git 제외)에 저장합니다. 설정, SQLite DB, 실행 로그가 들어 있습니다.

## 화면

| 화면 | 내용 |
| :--- | :--- |
| 다가오는 일정 | 월간 달력이 기본이고 목록으로 바꿀 수 있습니다. 상태별 색을 씁니다: 확정(초록), 승인 대기(노랑), 추적 중(점선), 변경?(노랑). 정정됨·시각 미발표 표시가 붙습니다 |
| 일정 상세 | 사용자가 본 주장, 판정, 정정, 게이트와 정책 사유, 읽은 근거(인용 한 문장), 재확인 시각, 기록이 있습니다. 승인·제외·되돌리기·.ics 버튼이 있습니다 |
| 승인 대기 | 비서가 자동으로 넣지 않은 일정과 다시 확인해 보니 바뀐 일정입니다. 바뀐 일정에는 [새 일시로 바꾸기], [기존 유지], [빼기]가 있습니다 |
| 추적 중 | 공식 발표를 기다리는 일정입니다 |
| 실행 기록 | 실행마다 모델 호출 수, 비용, 검색 수가 나옵니다. 누르면 오른쪽 활동창에 단계가 나옵니다 |
| 설정 | 자동 실행, 하루 예산, 관심 분야·키워드·공식 도메인 편집, 모델과 키 유무를 다룹니다 |

오른쪽 **비서 활동**에는 실행 중의 검색, 열람, 시간대 계산, 판정, 결정이 실시간(SSE)으로 쌓입니다.
실제 모드를 처음 열면 관심 분야를 고르는 화면이 한 번 나옵니다.

## 한 번 실행할 때 일어나는 일

1. **정리:** 지난 일정은 '지남', 날짜가 지난 추적 일정은 '만료'로 바꿉니다.
2. **재확인:** 등록된 일정(3일마다, 행사 하루 전)과 추적 중인 일정(매일)을 다시 검증합니다.
3. **찾기:** 관심 분야마다 기본 검색 3개와 키워드 검색을 합니다. 최근 21일 안의 기사만 찾습니다. 모델은 결과에서 앞으로 열릴 일정을 JSON으로 뽑습니다. 지난 일정, 검색 결과에 없는 주소, 형식 오류는 버리고 그 수를 기록합니다.
4. **검증:** 후보마다 Task A 환경(`AgentEnvironment`, C2 웹 전용)에서 `submit_claim`을 하고, 모델이 검증 도구만 써서 판정합니다. 도구는 search_web, fetch_url, read_evidence, calculate_comparison입니다. 시스템 프롬프트는 Skill 본문과 앱 안내입니다. `finish_verification`은 미션 없이 전달하므로 서버는 아무것도 쓰지 않습니다.
5. **결정:** 아래 정책이 자동 등록, 승인 대기, 추적, 제외 중 하나를 정합니다. 달력에 쓰는 것은 정책과 DB뿐이고, 모델은 일정을 직접 쓰지 못합니다.

## 자동 등록 정책 ([policy.py](policy.py))

Task A 게이트가 바닥입니다. 인용한 문서는 이번에 읽은 문서여야 하고, 1차 출처가 있거나 독립 출처군이 2개 이상이어야 하며, 반박이면 정정 시각이 있어야 합니다.
여기에 exp-004와 실제 실행에서 배운 규칙을 더했습니다. 하나라도 어기면 승인 대기로 보내고 사유를 남깁니다.

| 규칙 | 이유 |
| :--- | :--- |
| 날짜·시각이 인용한 읽은 문서 본문에 실제로 있어야 함 | exp-004 RW10: 시각을 발행일 없는 검색 스니펫에서 가져옴 |
| 문서에 날짜만 있으면 시각을 버리고 종일로 등록 | 실제 실행: 모델이 보도자료에 없는 05:00을 지어냄 |
| 행사명의 핵심 단어가 문서에 있어야 하고, 정정이 날짜를 2일 넘게 옮기면 안 됨 | exp-004 RW11: 같은 회사의 다른 행사로 바꿔치기 |
| 공식 출처 = 관심 분야의 공식 도메인 + 보도자료 배포처(PR Newswire 등) + 행사명과 같은 도메인 이름(aws.amazon.com) | 실제 실행: 주최사 페이지와 회사 보도자료를 공식으로 보지 않음 |
| 검증된 한국시간이 주장한 시각과 같으면 '맞음'으로 처리 | 실제 실행: 모델이 단순한 시간대 변환을 '틀림'으로 판정 |
| 근거 부족이면 추적, 반박됐지만 공식 날짜가 없으면 추적 | 공식 발표를 기다림 |
| 이미 등록된 일정은 혼자 바꾸지 않음. 바뀌면 '변경됨'으로 묻기 | 사용자 일정의 무단 변경 방지 |

- 위 수치는 그날 검색 결과에 대한 관찰입니다. 정답 데이터로 잰 평가가 아니므로 정확도로 읽으면 안 됩니다.

## 범위와 한계

- **평가 전입니다.** 정답이 있는 사례로 정책을 잰 결과가 아직 없습니다. 실제 사례 7건(RW04~RW11)으로 잴 계획입니다.
- **공식 페이지를 못 읽는 경우가 있습니다.** 닌텐도 상품 페이지처럼 스크립트로 그려지는 페이지는 본문에서 날짜를 찾지 못해 승인 대기로 갑니다. X(트위터) 공지도 읽지 못합니다.
- **같은 보도자료를 다시 쓴 기사들이** 서로 다른 출처군으로 잡힐 수 있습니다. 그래서 공식 출처 없이 출처 2개로 통과한 일정에는 '공식 출처 없음' 표시를 붙입니다.
- **발행일 없는 검색 결과는 시점 필터에 걸리지 않습니다.** 검색 결과 요약은 근거로 인정하지 않지만, 모델이 판단할 때 볼 수는 있습니다.
- **앱 서버가 켜져 있을 때만** 자동 실행이 돌아갑니다. 서비스 등록이나 클라우드 배포는 하지 않았습니다.
- **같은 행사 판정은 이름과 날짜(±3일)로 합니다.** 이름이 아주 다르게 쓰인 같은 행사는 둘로 보일 수 있습니다.
- **비용 표시는 설정의 가격표로 계산한 추정치입니다.** 실제 청구는 Mistral 콘솔에서 확인합니다.
- **모델과 범위:** Mistral 사용과 앱으로의 확장은 팀 결정이 필요한 사항입니다.
